# GlisWeb — installazione da zero

> Guida completa all'installazione del framework GlisWeb, dal server vuoto al primo login nel CMS.
> Pensata per chi non l'ha mai installato e vuole arrivare in fondo senza sorprese.
>
> **Come si legge:** i capitoli 1–3 servono a scegliere e a preparare il terreno; i capitoli 4–9 sono
> la procedura, da seguire nell'ordine; i capitoli 10–14 sono gli scenari particolari ( Apache, Nginx
> e CloudPanel, Varnish, XAMPP, hosting condiviso ), da leggere solo se ci si trova in quel caso. Il
> capitolo 17 è la checklist finale.
>
> **Convenzione sui percorsi:** tutti i percorsi sono relativi alla *document root* del sito, cioè
> la cartella in cui si scompatta il framework ( quella che contiene `.htaccess`, `_src/`, `_mod/` ).
>
> **E dopo?** Quando il framework risponde, la guida [da zero a hero](010-da-zero-a-hero.html)
> spiega come è fatto e come ci si lavora: questa guida la cita per paragrafo ( *§2.3 di da zero a
> hero* ) invece di ripeterla.

---

## 1. Prima di cominciare: stable o unstable?

GlisWeb vive in due repository, che sono **due fasi di sviluppo dello stesso progetto**:

| | **stable** | **unstable** |
|---|---|---|
| repository | [istricesrl/glisweb](https://github.com/istricesrl/glisweb) | [istricesrl/glisdev](https://github.com/istricesrl/glisdev) |
| cosa contiene | il framework completo, con tutti i moduli e i template, compresi quelli della generazione precedente | il framework riscritto, su cui si concentra lo sviluppo: il codice di glisweb ci viene portato un pezzo alla volta |
| moduli | tutti, compresi i moduli vecchi ( `_mod/_NNNN.*` e `_mod/_XNNN.*` ) | solo i moduli di nuova generazione ( `_mod/_XX000.*` e `_mod/_NNNNN.*` ) |
| Nginx e IIS | no | sì, tramite il front controller `index.php` |
| aggiornamento automatico | `_src/_sh/_gw.upgrade.sh` | non ancora |

Quando il porting sarà finito i due repository torneranno a essere uno solo. Fino ad allora la
regola per scegliere è semplice:

- **un progetto nuovo parte da glisdev**, a meno che non gli serva una funzione che su glisdev non è
  ancora arrivata;
- **se ti serve un modulo che esiste solo su glisweb** ( lo vedi confrontando le cartelle `_mod/` dei
  due repository ), parti da glisweb.

> **nota** — in tutti e due i repository si installa **sempre il ramo `develop`**, che è più
> aggiornato di `master`. I comandi di questa guida lo fanno già.

## 2. I requisiti

### 2.1 Il server

GlisWeb gira su qualunque server con PHP e un web server, ma **tutti gli script di amministrazione
sono scritti per Debian e Ubuntu**, e la raccomandazione è **Debian stable**. Su altre distribuzioni
il framework funziona, ma gli script di `_src/_sh/` potrebbero non farlo.

| componente | requisito | note |
|---|---|---|
| sistema operativo | Debian stable o Ubuntu | su Windows si usa XAMPP ( cap. 13 ) |
| web server | Apache 2 con `mod_rewrite` | Nginx solo su unstable ( cap. 11 ) |
| PHP | 8.x; consigliato **8.2** | la versione minima dichiarata è 7.0 ma le 7.x sono deprecate |
| estensioni PHP | `curl` `fileinfo` `gd` `json` `mysqli` `redis` `tidy` `yaml` `zip` `memcached` | il framework si ferma e le elenca se ne manca una |
| Composer | 2 | il pacchetto apt fornisce Composer 1, ormai dismesso: vedi §2.2 |
| database | MySQL o MariaDB | **opzionale**: serve per CMS, login da database e moduli gestionali |
| cache | Memcached, Redis | opzionali ma consigliati in produzione |
| strumenti | `wget`, `bsdtar` ( oppure `unzip` ) | per scaricare e scompattare |

### 2.2 Preparare un server nuovo

Su un Debian o un Ubuntu appena installato non serve fare niente a mano: il framework porta con sé
lo script che installa e configura tutto quello che gli serve ( Apache con i moduli necessari,
PHP con le estensioni, Composer 2, certbot, gli strumenti di sviluppo ). Si scarica il framework
( cap. 4 ) e poi, dalla document root:

```bash
sudo _src/_sh/_lamp.setup.sh
```

Su un server già in uso conviene leggere lo script prima di lanciarlo: installa pacchetti e tocca la
configurazione di Apache e di PHP.

### 2.3 Il database

Se il progetto userà il database, crea **prima** un database vuoto e un utente dedicato che ne abbia
tutti i privilegi. Tieni a portata di mano indirizzo e porta del server, nome del database, utente e
password: servono al §5.2. Le tabelle non si creano a mano, le crea il framework ( cap. 8 ).

### 2.4 Il DNS

Il framework sceglie quale sito servire guardando il nome con cui viene chiamato ( *§2.3 di da zero a
hero* ): il dominio che userai deve quindi già puntare al server. In locale basta una riga nel file
`hosts`, per esempio `127.0.0.1 miosito.local`.

## 3. Come funziona l'installazione, in breve

Installare GlisWeb non è un'installazione nel senso dei CMS tradizionali: non c'è un wizard da
completare. Si scompatta il framework nella document root, gli si dice chi è con un file di
configurazione, e da lì in poi **è il framework stesso a dire cosa manca**, con un messaggio di una riga
per ogni problema e con la pagina di status. Il percorso è sempre questo:

```
1. scarica e scompatta nella document root      cap. 4
2. composer update                              cap. 4
3. src/config.yaml + src/shadow.yaml            cap. 5
4. permessi                                     cap. 6
5. /status                                      cap. 7
6. /task/mysql.patch   ( solo col database )    cap. 8
7. /admin                                       cap. 9
```

## 4. Scaricare il framework

Accedi via SSH al server, spostati nella document root del sito ( deve essere vuota ) e scarica lo
zip del ramo `develop` del repository che hai scelto al cap. 1.

### 4.1 Unstable ( glisdev )
<!-- @linea: unstable -->

```bash
cd /var/www/miosito
wget https://github.com/istricesrl/glisdev/archive/refs/heads/develop.zip
bsdtar --strip-components=1 -xf develop.zip
rm -f develop.zip
composer update
```

### 4.2 Stable ( glisweb )
<!-- @linea: stable -->

```bash
cd /var/www/miosito
wget https://github.com/istricesrl/glisweb/archive/refs/heads/develop.zip
bsdtar --strip-components=1 -xf develop.zip
rm -f develop.zip
composer update
```

In alternativa, se sul server è installato [Calabash](https://github.com/istricesrl/calabash), la
raccolta di script di amministrazione di Istrice, lo stesso lavoro lo fa un comando solo:

```bash
va.glisweb.install.sh /var/www/miosito develop
```

> **attenzione** — senza il secondo argomento `va.glisweb.install.sh` installa `master`, che su
> glisweb è ferma a una versione molto vecchia del framework. Indica sempre `develop`.

### 4.3 Cosa hai appena fatto

`bsdtar --strip-components=1` scompatta il contenuto dello zip direttamente nella cartella corrente,
senza la cartella `glisweb-develop/` o `glisdev-develop/` che GitHub mette in testa all'archivio. Se
non hai `bsdtar`, puoi usare `unzip` e poi spostare i file:

```bash
unzip develop.zip && mv -f ./glis*-develop/{.,}* ./ 2>/dev/null; rmdir ./glis*-develop; rm -f develop.zip
```

`composer update` scarica le librerie esterne ( Twig, PHPMailer, TCPDF, PhpSpreadsheet e le altre )
in `_src/_lib/_ext/`, **non** in `vendor/`. Lo zip non le contiene: senza questo passo il framework si
ferma con `autoload mancante, eseguire composer update`.

Le cartelle che trovi dopo lo scompattamento, e cosa contengono, sono descritte al *§2.2 di da zero a
hero*. La cosa da sapere subito è una: **le cartelle che iniziano con `_` sono il framework e vengono
sovrascritte a ogni aggiornamento**, quindi non si modificano. Tutto quello che è tuo va nelle
cartelle senza underscore ( `src/`, `mod/`, `etc/`, `usr/` ).

> **attenzione** — non rimuovere né modificare `LICENSE.md` e `README.md`: fanno parte del framework
> e la licenza ne impone la presenza in ogni copia.

## 5. La configurazione minima

### 5.1 Il sito: `src/config.yaml`

La prima cosa che il framework fa, a ogni richiesta, è capire **quale sito servire**: se non lo trova
si ferma subito. Il primo file da scrivere dichiara quindi almeno un sito. Crea `src/config.yaml`:

```yaml
sites:
  1:
    __label__: "il mio sito"
    name:
      it-IT: "Il mio sito"
    protocols:
      DEV: "http"
      PROD: "https"
    hosts:
      DEV: "miosito"
      PROD: "www"
    domains:
      DEV: "local"
      PROD: "miosito.it"
    homes:
      DEV: "home"
      PROD: "home"
```

Con questa configurazione il sito risponde su `http://miosito.local` in sviluppo e su
`https://www.miosito.it` in produzione, e **lo stesso file va bene su tutte e due le macchine**:
ognuna capisce da sola in che ambiente si trova guardando il dominio con cui viene chiamata. Il
significato di ogni chiave, e il perché di questo meccanismo, sono al *§2.3 di da zero a hero*.

`homes` indica la pagina servita alla radice `/`: la pagina `home` va dichiarata, e il modo più
rapido è un file `src/inc/pages/site.it-IT.php`, come al *§2.5 di da zero a hero*. Se invece userai
il database, le pagine le crei dal CMS e in `homes` metti l'id della pagina che fa da home.

### 5.2 Il database: ancora `src/config.yaml`

Se userai il database, aggiungi a `src/config.yaml` il server e il profilo che lo usa, **senza utente
e password**:

```yaml
mysql:
  servers:
    main:
      address: "127.0.0.1"
      port: "3306"
      db: "miosito"
  profiles:
    DEV:
      servers:
        - "main"
    PROD:
      servers:
        - "main"
```

### 5.3 Le credenziali: `src/shadow.yaml`

Utente e password del database, e la password dell'utente `root` del framework, vanno in
`src/shadow.yaml`. Questo file è escluso da git dal `.gitignore` del framework e **non va mai
committato**: `config.yaml` si copia identico su tutte le macchine, `shadow.yaml` è diverso su
ciascuna.

```yaml
mysql:
  servers:
    main:
      username: "utente del database"
      password: "password del database"
auth:
  accounts:
    root:
      password: "hash md5 della password di root"
```

L'hash della password si genera con:

```bash
_src/_sh/_password.hash.sh
```

L'utente `root` è quello con cui farai il primo login nel CMS ( cap. 9 ).

> **nota** — `yaml` e `json` sono equivalenti: puoi scrivere `src/config.json` e `src/shadow.json` al
> posto dei file `.yaml`. Se ci sono entrambi, il framework li legge tutti e il `.json` vince. L'ordine
> completo di lettura è al *§5.1 di da zero a hero*.

### 5.4 I moduli

I moduli in `_mod/` sono tutti **spenti**. Per un sito gestito dal CMS servono almeno anagrafica,
contenuti e pagine; si attivano creando la cartella corrispondente senza underscore:

```bash
mkdir -p mod/AN000.anagrafica mod/CO000.contenuti mod/PA000.pagine
```

oppure elencandoli in `src/config.yaml`:

```yaml
mods:
  active:
    array:
      - "AN000.anagrafica"
      - "CO000.contenuti"
      - "PA000.pagine"
```

Cosa fa ciascun modulo lo dice il suo `READ.md`, e il capitolo 12 di da zero a hero spiega come sono
fatti.

## 6. I permessi

Il framework deve poter scrivere in alcune cartelle ( `var/`, `tmp/` ) e **non** deve poter scrivere
nel resto: se la cartella di installazione è scrivibile dal web server, si ferma e lo dice. I permessi
giusti li imposta uno script:

```bash
sudo _src/_sh/_lamp.permissions.open.sh      # sviluppo: permessi aperti, comodi per lavorare
sudo _src/_sh/_lamp.permissions.secure.sh    # produzione: root:www-data, permessi chiusi
```

Su Nginx lo script è `_src/_sh/_nginx.permissions.secure.sh`, che si aspetta nella cartella che
**contiene** la document root un file `nginxuser.conf` con dentro il nome dell'utente a cui assegnare
il sito.

> **attenzione** — rilancia lo script dei permessi dopo ogni operazione fatta come `root` nella
> document root ( un `composer update`, un file copiato a mano ): un file di proprietà di `root` che il
> web server deve scrivere è la causa più comune degli errori dopo un intervento.

## 7. La verifica: la pagina di status

Apri il browser su:

```
http://miosito.local/status
```

Da qui in poi è il framework a dirti cosa manca, su due livelli.

**Se manca un prerequisito, qualunque indirizzo risponde con un messaggio di una riga** che dice
anche cosa fare. Alla prima installazione i casi tipici sono:

| messaggio | cosa fare |
|---|---|
| `autoload mancante, eseguire composer update` | `composer update` nella document root ( cap. 4 ) |
| `alcuni moduli di PHP necessari non sono installati ( … )` | installa le estensioni elencate, oppure `_src/_sh/_lamp.setup.sh` |
| `la cartella … non è scrivibile` / `impossibile creare la cartella …` | permessi ( cap. 6 ) |
| `la cartella di installazione è scrivibile` | permessi troppo larghi: `_lamp.permissions.secure.sh` |
| `file di configurazione … danneggiato` | errore di sintassi in `config.yaml` o `shadow.yaml`: attenzione all'indentazione |
| `sito non trovato per …` | host e dominio non combaciano con `sites` ( §5.1 ) |

**Superati i prerequisiti, la pagina di status stampa un rapporto completo**, diviso per sezioni
( versioni, sicurezza, log, sito corrente, privacy, SMTP, MySQL, cache, schedulazione, servizi
esterni ), con una riga per controllo marcata `[ OK ]`, `[INFO]`, `[WARN]` o `[FAIL]`.

L'installazione è a posto quando il rapporto arriva fino in fondo e nella sezione del sito corrente
trovi lo stato giusto ( `DEV` in locale ) e la home. Su un'installazione nuova alcune righe `[FAIL]`
sono **normali**: dicono cosa resta da configurare ( il titolare del trattamento e i cookie, il cron
mai eseguito ), non che l'installazione è rotta. Il dettaglio è al *§2.6 di da zero a hero*.

## 8. Il database

Se non usi il database salta questo capitolo: senza connessione il framework parte comunque e serve
le pagine dichiarate nei file.

Con la connessione configurata ( §5.2 e §5.3 ), lo schema **non si crea a mano**: lo applica il
framework. Prima del primo login apri:

```
http://miosito.local/task/mysql.patch
```

Il task crea tabelle, viste e dati di base, ed è **idempotente**: rilanciarlo applica solo quello che
manca, quindi è anche il comando da usare dopo ogni aggiornamento del framework. Com'è organizzato il
database è il capitolo 9 di da zero a hero.

## 9. Il primo accesso al CMS

```
http://miosito.local/admin
```

Entra con l'utente `root` e la password il cui hash hai messo in `shadow.yaml` ( §5.3 ). Da qui crei
gli account veri, le pagine e i contenuti.

> **attenzione** — in produzione l'utente `root` di configurazione va protetto con una password
> robusta e usato solo per l'amministrazione: gli operatori lavorano con account propri, creati dal CMS.

## 10. Apache

Con Apache il framework funziona senza configurazioni aggiuntive: il `.htaccess` nella document root
fa tutto l'instradamento e nega l'accesso ai file che non devono essere serviti. Serve solo che
`mod_rewrite` sia attivo e che il virtual host permetta l'override ( `AllowOverride All` ); lo script
`_lamp.setup.sh` del §2.2 prepara Apache in questo modo.

## 11. Nginx e CloudPanel
<!-- @linea: unstable -->

> **solo unstable** — il front controller `index.php` che rende possibile l'uso di Nginx esiste solo
> su glisdev. Su glisweb serve Apache.

Nginx non legge i file `.htaccess`, quindi tutto il traffico va mandato a `index.php`, che fa lo
stesso lavoro di instradamento. La configurazione che segue è quella di
[CloudPanel](https://www.cloudpanel.io/), ma la parte che conta vale per qualunque Nginx: tutte le
richieste a `index.php`, e nessun altro file `.php` eseguibile.

### 11.1 Il virtual host

Nella configurazione del sito sostituisci il blocco `server` sulla porta **8080** con questo,
mettendo il tuo dominio al posto di `miosito.it`:

```nginx
server {
  listen 8080;
  listen [::]:8080;
  server_name www.miosito.it miosito.it;
  {{root}}

  include /etc/nginx/global_settings;

  index index.php;

  location / {
    rewrite ^ /index.php?$query_string last;
  }

  # esegue solo index.php
  location = /index.php {
    include fastcgi_params;
    fastcgi_intercept_errors on;
    fastcgi_index index.php;
    fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
    fastcgi_read_timeout 3600;
    fastcgi_send_timeout 3600;
    fastcgi_param HTTPS "on";
    fastcgi_param SERVER_PORT 443;
    fastcgi_pass 127.0.0.1:{{php_fpm_port}};
    fastcgi_param PHP_VALUE "{{php_settings}}";
  }

  # blocca l'esecuzione di qualsiasi altro .php
  location ~ \.php$ {
    return 404;
  }
}
```

Se il blocco `server` sulla porta **80** contiene questo, **toglilo**:

```nginx
if (-f $request_filename) {
    break;
}
```

perché farebbe servire i file statici direttamente, senza passare dal front controller, e quindi
senza i controlli di accesso del framework.

### 11.2 La versione di PHP

Se hai problemi con PHP 8.5 e le sue estensioni, torna a PHP 8.4.

## 12. Varnish

Se davanti al web server c'è Varnish ( CloudPanel, per esempio, lo mette davanti a Nginx ), GlisWeb
sa governarne la cache, ma per farlo Varnish deve rispettare l'header con cui il framework segnala le
risposte da non mettere in cache. Aggiungi al blocco `vcl_backend_response` della configurazione di Varnish:

```
if (beresp.http.X-GlisWeb-No-Cache == "true") {
    set beresp.ttl = 0s;
    set beresp.uncacheable = true;
    unset beresp.http.Cache-Control;
    unset beresp.http.Expires;
    unset beresp.http.Pragma;
    unset beresp.http.X-Cache-Lifetime;
    unset beresp.http.X-Cache-Tags;
    return (deliver);
}
```

> **attenzione** — senza questa configurazione Varnish mette in cache anche le pagine che non devono
> esserlo ( l'area riservata, il carrello, i form ): in quel caso **va disattivato**.

## 13. XAMPP ( Windows e sviluppo locale )

Per lavorare in locale su Windows basta scaricare lo zip del repository e scompattarlo nella document
root di XAMPP, poi lanciare `composer update` in quella cartella. Se il framework chiede estensioni di
PHP che XAMPP non ha, scaricale da [PECL](https://pecl.php.net/packages.php).

Gli script di `_src/_sh/` sono per Linux e su Windows non funzionano: i permessi, su XAMPP, di norma
non sono un problema.

## 14. Hosting condiviso senza SSH

Si può fare, ma è lo scenario meno comodo, perché GlisWeb dà il meglio con gli script di `_src/_sh/`.
Se hai solo l'FTP:

1. scarica lo zip e scompattalo **sul tuo computer**;
2. lancia `composer update` **in locale**, nella cartella dove c'è `composer.json`: il provider non te
   lo farebbe fare, e senza le librerie il framework non parte;
3. scrivi `src/config.yaml` e `src/shadow.yaml` ( cap. 5 );
4. carica tutto via FTP nella document root;
5. prosegui dal cap. 7: lo schema del database lo crea `/task/mysql.patch`, che si lancia dal browser.

Verifica prima che il provider offra PHP 8 con tutte le estensioni del §2.1: `redis`, `memcached`,
`yaml` e `tidy` sono spesso quelle che mancano.

## 15. Dopo l'installazione

### 15.1 Il cron

Molte funzioni del framework ( code di invio mail, job, pulizie, sitemap ) girano in background e hanno
bisogno che qualcuno chiami `/api/cron` ogni minuto. Lo script lo installa in `/etc/cron.d/`:

```bash
sudo _src/_sh/_crontab.install.sh install https miosito.it
```

Finché il cron non gira, la pagina di status lo segnala.

### 15.2 L'aggiornamento

> **solo stable** — su glisweb il framework si aggiorna con lo script che il framework stesso
> distribuisce, che prima fa il backup del deploy e mette da parte le modifiche locali ai file `_*`:
>
> ```bash
> _src/_sh/_gw.upgrade.sh develop
> ```
>
> Il funzionamento e le sue trappole sono nel capitolo *aggiornamento e disallineamenti* del
> manuale sviluppatore.

> **solo unstable** — su glisdev lo script di aggiornamento non c'è ancora: si aggiorna scaricando di
> nuovo lo zip ( cap. 4 ) sopra le cartelle `_*`. Le cartelle senza underscore non vengono toccate.

Dopo ogni aggiornamento: `composer update`, lo script dei permessi ( cap. 6 ) e `/task/mysql.patch`
( cap. 8 ).

### 15.3 La documentazione in locale

I manuali e le guide come questa si generano dal repository con:

```bash
_src/_sh/_docs.build.sh --all
```

e si leggono via web sotto `/_manual/` e `/_quickstart/`. Dove siano e chi possa leggerli lo spiega il
`READ.md` nella radice del framework.

## 16. Per chi contribuisce al framework

Questa guida è per chi **usa** il framework in un progetto. Chi lavora **sul** framework clona il
repository con git invece di scaricare lo zip, e deve attivare una volta sola i git hook di sviluppo
nella propria copia di lavoro:

```bash
git clone https://github.com/istricesrl/glisdev.git
cd glisdev && git checkout develop
sudo _src/_sh/_githooks.install.sh
```

Gli hook sono versionati in `.githooks/`, ma git li cerca in `.git/hooks/` finché non gli si indica il
percorso: lo script imposta `core.hooksPath` ( configurazione locale del clone, non viaggia col
repository ) e rimette il bit di esecuzione, senza il quale git li salterebbe senza dire nulla. Da quel
momento ogni commit rigenera `_etc/_current.version`, e i commit sul ramo `master` aggiornano
`_etc/_changelog.json` a partire dal messaggio di commit, di cui la prima riga viene divisa sul
carattere `§` in titolo e testo:

```bash
git commit -m "titolo della modifica § descrizione estesa della modifica"
```

Lo stato dell'installazione si verifica con `sudo _src/_sh/_githooks.install.sh --check`.

> **attenzione** — nei progetti che **usano** il framework gli hook non vanno installati.

## 17. Checklist

```
[ ] scelta la linea: glisdev ( unstable ) o glisweb ( stable )              cap. 1
[ ] server Debian/Ubuntu pronto, o _lamp.setup.sh lanciato                 cap. 2
[ ] database e utente creati ( se serve )                                  §2.3
[ ] dominio che punta al server                                            §2.4
[ ] zip del ramo develop scompattato nella document root                   cap. 4
[ ] composer update                                                        cap. 4
[ ] src/config.yaml con almeno un sito ( e il database, se serve )         §5.1 §5.2
[ ] src/shadow.yaml con le credenziali, fuori da git                       §5.3
[ ] la pagina home, in un file o nel CMS                                   §5.1
[ ] moduli attivati                                                        §5.4
[ ] permessi                                                               cap. 6
[ ] /status arriva fino in fondo                                           cap. 7
[ ] /task/mysql.patch ( se c'è il database )                               cap. 8
[ ] login su /admin                                                        cap. 9
[ ] cron installato                                                        §15.1
```

Se qualcosa non torna e la pagina di status non basta a capire perché, i log sono in `var/log/`, e
`var/log/latest/run.latest.log` contiene la traccia dell'ultima richiesta. Se sei bloccato, apri una
[issue su GitHub](https://github.com/istricesrl/glisdev/issues) o chiedi sul
[server Discord](https://discord.gg/2nynQcXAWf).
