# GlisWeb — da zero a hero

> Guida introduttiva e operativa al framework GlisWeb.
> Pensata per chi non l'ha mai visto e deve arrivare a metterci le mani sul serio.
>
> **Come si legge:** i capitoli 1–4 sono il minimo sindacale per orientarsi. I capitoli 5–9 sono
> il cuore del framework (pagine, template, controller). I capitoli 10–16 sono verticali che si
> leggono quando servono. L'appendice A è la checklist da tenere aperta mentre si lavora.
>
> **Convenzione sui percorsi:** tutti i percorsi di questo documento sono relativi alla
> *document root* del progetto (la cartella che contiene `.htaccess`, `_src/`, `src/`).
> In questo deploy specifico (`glisweb.istricesrl.it`) la document root è la sottocartella
> `dev/`: quindi `_src/_config.php` sta in `dev/_src/_config.php`.
>
> **I link ai sorgenti:** quando vale la pena guardare il codice, il percorso è un link al file su
> GitHub, ramo `develop`. I commenti in testa ai file del framework sono parte della documentazione:
> spesso spiegano il *perché* meglio di quanto possa fare questa guida.

## 1. Cos'è GlisWeb e perché è fatto così

GlisWeb è un framework PHP full-stack per applicazioni web gestionali e siti dinamici, sviluppato
da Istrice srl. Non è un MVC classico e non assomiglia a Laravel o Symfony: ha una sua logica,
molto coerente, che una volta capita rende il codice prevedibile.

Le quattro idee di fondo, da tenere sempre a mente:

**1. Tutto è configurazione + convenzione.**
Una pagina non è una classe: è una voce di un array PHP. Un form non è un oggetto: è un blocco di
campi HTML nominati secondo una convenzione. Una CRUD completa non richiede codice: richiede una
tabella con la sua vista, un array di configurazione e un template.

**2. La personalizzazione è nel nome dei file.**
I file e le cartelle che iniziano con `_` sono *standard* (il framework). La loro controparte senza
underscore è *custom* (il progetto). Il framework carica automaticamente la seconda dopo la prima.
Aggiornare il framework non tocca mai il codice del progetto.

**3. L'esecuzione è una griglia deterministica.**
Ogni richiesta attraversa gli stessi *runlevel* nello stesso ordine, per ogni modulo attivo.
Non c'è un container di dependency injection, non c'è magia: c'è una sequenza di `require`
prevedibile che si può leggere dall'inizio alla fine.

**4. I dati passano per un unico imbuto.**
Qualunque scrittura sul database — form del CMS, chiamata REST, importazione CSV — finisce nella
stessa funzione: `controller()`. Un solo punto in cui applicare permessi, validazione e hook.

**Stack:** PHP 8.x, MySQL/MariaDB, Twig per il rendering, Redis/Memcached opzionali per cache e
sessioni, Composer per le dipendenze (che finiscono in `_src/_lib/_ext/`, non in `vendor/`).

## 2. Installazione e primo avvio

### 2.1 Scaricare il framework

```bash
cd /var/www/miosito
wget https://github.com/istricesrl/glisdev/archive/refs/heads/develop.zip
bsdtar --strip-components=1 -xf develop.zip
rm -f develop.zip
composer update
```

`composer update` installa le dipendenze in `_src/_lib/_ext/`.

### 2.2 Cosa hai scaricato: le cartelle

Prima di scrivere la configurazione conviene sapere dove si sta mettendo le mani. Le cartelle di
primo livello si dividono in tre famiglie:

| Famiglia | Cartelle | Chi le scrive | All'aggiornamento del framework |
|---|---|---|---|
| **standard** | `_etc/` `_mod/` `_src/` `_usr/` | il framework | vengono **sovrascritte** |
| **custom** | `etc/` `mod/` `src/` `usr/` | tu, per il progetto | restano |
| **stato del deploy** | `var/` `tmp/` | il framework, mentre gira | restano, e non vanno in git |

Appena scompattato ci sono solo le standard: le custom le crei tu, un file alla volta, quando servono.
Quelle che userai subito:

```
_src/            il codice del framework: bootstrap, API, librerie, template
_mod/            i moduli, tutti spenti finché non li attivi (§12)
src/config.json  la configurazione del progetto          ← la scrivi al §2.3
src/shadow.json  le credenziali                          ← la scrivi al §2.4
src/inc/pages/   le pagine del progetto                  ← la prima la scrivi al §2.5
var/log/         i log: il primo posto dove guardare quando qualcosa non va
```

La regola che lega standard e custom — il file senza underscore personalizza quello con
l'underscore — è il cuore del §4, dove c'è anche l'albero completo (§4.4).

### 2.3 Configurazione minima

**La prima cosa che il framework fa, a ogni richiesta, è capire quale sito deve servire.** Se non
lo trova si ferma subito, con un messaggio del tipo `sito non trovato per miosito.local`. Per questo
il primo file da scrivere è `src/config.json` (o `src/config.yaml`, è indifferente), che dichiara
**almeno un sito**:

```json
{
    "sites": {
        "1": {
            "__label__": "il mio sito",
            "name":      { "it-IT": "Il mio sito" },
            "protocols": { "DEV": "http",    "TEST": "https",        "PROD": "https" },
            "hosts":     { "DEV": "miosito", "TEST": "test",         "PROD": "www" },
            "domains":   { "DEV": "local",   "TEST": "miosito.test", "PROD": "miosito.com" },
            "homes":     { "DEV": "home",    "TEST": "home",         "PROD": "home" }
        }
    },
    "debug": { "DEV": { "log": { "lvl": 7 } } }
}
```

Cosa fa ogni chiave:

| Chiave | Significato |
|---|---|
| `1` | id del sito (una installazione può servire più siti) |
| `__label__` | etichetta interna, usata nei menu a tendina del CMS |
| `name` | **le chiavi definiscono le lingue attive del sito** — questa è la cosa che sorprende tutti la prima volta |
| `protocols` / `hosts` / `domains` | un valore per stato di deploy (`DEV`/`TEST`/`PROD`); host + dominio = URL su cui il sito risponde |
| `homes` | id della pagina servita alla radice `/` (la crei al §2.5) |
| `debug` | alza il livello di log in sviluppo: `7` è il massimo dettaglio (§16.2) |

**Come il framework usa questa configurazione.** Protocolli, host e domini hanno **un valore per
ciascuno dei tre stati di deploy**: `DEV` (sviluppo), `TEST` (collaudo), `PROD` (produzione). A ogni
richiesta il framework concatena, stato per stato, `hosts` e `domains` e confronta il risultato con
l'`HTTP_HOST` della richiesta: con `miosito` + `local` il sito risponde su `miosito.local`. Se
`hosts` vale `www`, combaciano sia `www.dominio` sia `dominio`; per host e domini aggiuntivi ci sono
le chiavi `alias.hosts` e `alias.domains`.

**Da questo confronto nasce `SITE_STATUS`**, la costante che vale `DEV`, `TEST` o `PROD` a seconda
di quale ramo ha fatto match. Non si imposta a mano, ed è proprio questo il punto: lo **stesso**
`config.json` viene copiato identico su tutte e tre le macchine, e ciascuna capisce da sola in che
ambiente si trova guardando il dominio su cui risponde. Tutto il resto del framework — database,
log, servizi esterni — sceglie i propri valori in base a `SITE_STATUS`.

Il codice che fa il confronto sta in
[`_src/_config/_015.site.php`](https://github.com/istricesrl/glisweb/blob/develop/_src/_config/_015.site.php).
Per tutto il resto sui file di configurazione — quali sono, in che ordine vengono letti, come si
scrivono i valori che cambiano da un ambiente all'altro — vedi il §5.

### 2.4 Le credenziali NON vanno lì

Le credenziali si mettono in `src/shadow.json` (o `src/shadow.yaml`), che è in `.gitignore` e
non viene mai committato:

```json
{
    "mysql": { "servers": { "main": { "username": "glisweb", "password": "********" } } },
    "auth":  { "accounts": { "root": { "password": "<hash md5 della password>" } } }
}
```

L'hash MD5 si genera con `_src/_sh/_password.hash.sh`. L'ordine completo in cui vengono letti
configurazione e credenziali è al §5.1.

### 2.5 La prima pagina

La chiave `homes` del §2.3 dice quale pagina servire alla radice `/`, ma il framework **non ha una
pagina `home` sua**: va dichiarata. Le pagine si dichiarano in file PHP sotto `src/inc/pages/`,
uno per lingua, con il nome `<qualcosa>.<lingua>.php`. Il minimo indispensabile è
`src/inc/pages/site.it-IT.php`:

```php
<?php

    // lingua di questo file
    $l = 'it-IT';

    // la pagina con id 'home', quella indicata in homes
    $p['home'] = array(
        'title'     => array( $l => 'Il mio sito' ),
        'h1'        => array( $l => 'Benvenuto!' ),
        'content'   => array( $l => '<p>La mia prima pagina con GlisWeb.</p>' ),
        'template'  => array( 'path' => '_src/_tpl/_aurora/', 'schema' => 'default.twig' ),
        'parent'    => array( 'id' => NULL )
    );
```

Ogni pagina è una voce dell'array `$p`, e la chiave (`home`) è il suo id. I testi sono indicizzati
per lingua; `template` dice con quale tema e quale schema disegnarla; `parent` la colloca nell'albero
(`NULL` = primo livello). Tutte le altre chiavi, gli URL e il pattern delle pagine del CMS sono al §6.

> Se è attivo Memcached, le definizioni delle pagine stanno in cache: dopo averle modificate serve
> `/task/memcache.clean` (§16.1), altrimenti si continua a vedere la versione vecchia senza errori.

### 2.6 Verifica: la pagina di status

Da qui in poi è il framework stesso a dirti cosa manca, su due livelli.

**Il bootstrap si ferma sui prerequisiti.** Se manca qualcosa di indispensabile, **qualunque** URL
risponde con un messaggio di una riga che dice anche cosa fare. Alla prima installazione i casi
tipici sono:

| Messaggio | Cosa fare |
|---|---|
| `autoload mancante, eseguire composer update` | mancano le dipendenze: `composer update` |
| `la cartella … non è scrivibile` / `impossibile creare la cartella …` | permessi: gli script qui sotto |
| `la cartella di installazione è scrivibile` | permessi troppo larghi: `_lamp.permissions.secure.sh` |
| `alcuni moduli di PHP necessari non sono installati (…)` | `_src/_sh/_lamp.setup.sh` |
| `file di configurazione … danneggiato` | errore di sintassi in `config.json` / `shadow.json` |
| `sito non trovato per …` | host e dominio non combaciano con la configurazione (§2.3) |

```bash
sudo _src/_sh/_lamp.permissions.open.sh      # sviluppo: permessi aperti
sudo _src/_sh/_lamp.permissions.secure.sh    # produzione: root:www-data, permessi chiusi
```

(su Nginx: `_src/_sh/_nginx.permissions.secure.sh`, che richiede un file `nginxuser.conf` nella
cartella che contiene la document root).

**La pagina di status fa il resto del controllo.** Superati i prerequisiti:

```
http://miosito.local/status
```

stampa un rapporto in testo semplice, diviso in sezioni — versioni, informazioni generali, sicurezza,
log e debug, sito corrente, privacy, SMTP, MySQL, memcache, redis, schedulazione, servizi esterni —
con una riga per controllo, marcata `[ OK ]`, `[INFO]`, `[WARN]` o `[FAIL]` (`[ -- ]` è un dato
riportato, non un giudizio).

**Cosa aspettarsi quando l'installazione è a posto:** il rapporto arriva fino in fondo, e nella
sezione *sito corrente* trovi lo stato giusto (`DEV` in locale) e `[ OK ] #id home corrente: home`.
Su un'installazione appena fatta alcune righe `[FAIL]` sono **normali** e non indicano un problema
di installazione, ma cose ancora da configurare: il titolare del trattamento e i cookie (privacy),
e il cron mai eseguito finché non lo installi (§13.3). Senza database, la sezione MySQL dice
`backend MySQL non attivato`: è corretto, vedi il paragrafo che segue.

Il sorgente della pagina,
[`_src/_api/_status/_framework.php`](https://github.com/istricesrl/glisweb/blob/develop/_src/_api/_status/_framework.php),
è anche l'elenco più rapido di cosa il framework considera "configurato".

### 2.7 Il database, se serve

**Il database è opzionale.** Senza connessione MySQL il framework parte regolarmente e serve le
pagine dichiarate nei file, come la home del §2.5: il runlevel che si occupa di MySQL si limita a
registrare un avviso nei log e prosegue. Il database serve quando vuoi contenuti gestiti dal CMS,
utenti che fanno login dal database o i moduli gestionali.

Se serve, i passi sono tre:

1. **la connessione**: la sezione `mysql` in `src/config.json` (server, nome del database, un
   profilo per ambiente — l'esempio è al §5.2) e utente e password in `src/shadow.json` (§2.4);
2. **lo schema**: non si crea a mano, lo applica il framework:
   ```
   http://miosito.local/task/mysql.patch   → crea/aggiorna tabelle, viste, dati di base
   ```
   Il task è idempotente: rilanciarlo applica solo quello che manca (§9.7);
3. **il CMS**:
   ```
   http://miosito.local/admin              → CMS
   ```
   Il login è su `/login.it-IT.html`, la dashboard su `/dashboard.it-IT.html`.

Com'è organizzato il database, e perché, è il capitolo 9.

### 2.8 Riepilogo

```
1. scompatta + composer update              §2.1
2. src/config.json      → almeno un sito     §2.3
3. src/shadow.json      → credenziali        §2.4
4. src/inc/pages/...    → almeno la home     §2.5
5. /status              → verifica           §2.6
6. /task/mysql.patch    → schema database    §2.7   (solo se serve il DB)
```

## 3. La mappa mentale: la griglia moduli × runlevel

Questa sezione è la più importante della guida. Se si capisce questo schema, il resto viene da sé.

### 3.1 Il ciclo di vita di una richiesta

```
  +-----------+      +-----------+      +-----+                  +------------------+
  | richiesta | ---> | .htaccess | ---> |     | -- (include) --> | _src/_config.php |
  +-----------+      +-----------+      |  A  |                  +------------------+
                     (index.php su      |  P  |                     (librerie,
                      Nginx)            |  I  | <-------------       runlevel)
         +--------+      +-------+      |     |
         | output | <--- | macro | <--- |     |
         +--------+      +-------+      +-----+
                            ^ |
                            | v
                   +---------------------------------+
                   | template o factory di rendering |
                   +---------------------------------+
```

1. **`.htaccess`** (Apache) o **`index.php`** (Nginx) instrada la richiesta verso una *API*.
2. L'**API** (es. [`_src/_api/_pages.php`](https://github.com/istricesrl/glisweb/blob/develop/_src/_api/_pages.php))
   include [`_src/_config.php`](https://github.com/istricesrl/glisweb/blob/develop/_src/_config.php):
   è il **bootstrap**.
3. Il bootstrap dichiara le funzioni core, legge la configurazione, include le librerie ed esegue
   i **runlevel**. Il suo prodotto sono due array globali, che da qui in poi si incontrano
   dappertutto:
   - **`$cf`** — *configurazione*: tutto quello che il framework sa di sé e della richiesta in corso
     (sito, database, utente, pagine…). Lo usa solo il PHP;
   - **`$ct`** — *contesto*: la parte di `$cf` che viene passata ai template, cioè le variabili che
     Twig può leggere.

   C'è anche un terzo array, `$cx`, che vive solo durante il bootstrap. Tutti e tre sono descritti
   al §3.4.
4. Il controllo torna all'API, che include le **macro di pagina** (la logica applicativa specifica).
5. Il **template Twig** riceve `$ct` e produce l'HTML.

Sono tre spazi distinti: *framework space* (fino alla fine di `_config.php`), *user space*
(API + macro), *output space* (Twig).

### 3.2 La griglia

Il framework è organizzato in una griglia bidimensionale:

- **verticale = i moduli** — gruppi di funzionalità attivabili a piacere
- **orizzontale = i runlevel** — i passi di esecuzione, numerati da 000 a 999

L'esecuzione procede **runlevel per runlevel**; dentro ogni runlevel, **modulo per modulo**;
e per ogni blocco, **prima lo standard poi il custom**:

```
     =========================== per ogni singola libreria ==========================
     +-------------------+   +-----------------+   +------------------+   +----------------+
     | lib standard base |-->| lib custom base |-->| lib standard mod |-->| lib custom mod |
     +-------------------+   +-----------------+   +------------------+   +----------------+
                                                                                  |
 +--------------------------------------------------------------------------------+
 |
 |   ========================== per ogni singolo runlevel ==========================
 |   +-------------------+   +----------------------+   +------------------+   +---------------------+
 +-->| runlevel std base |-->| runlevel custom base |-->| runlevel std mod |-->| runlevel custom mod |
     +-------------------+   +----------------------+   +------------------+   +---------------------+
```

I file dei runlevel stanno in `_src/_config/_NNN.<nome>.php` (standard) e `src/config/NNN.<nome>.php`
(custom). Vengono trovati con `glob()`, ordinati per nome e inclusi in sequenza: il ciclo che lo fa
è in fondo a [`_src/_config.php`](https://github.com/istricesrl/glisweb/blob/develop/_src/_config.php).

> ⚠️ **Un file custom senza il gemello standard non viene incluso mai, silenziosamente.**
> Il `glob()` gira sui **soli** file standard, e la controparte custom viene ricavata da lì con
> `path2custom()` (§4.1). Se crei `src/config/800.mio.php` senza che esista
> `_src/_config/_800.mio.php`, non verrà eseguito e non avrai nessun errore. Quando un runlevel
> serve solo al progetto, il file standard esiste lo stesso ed è quasi vuoto: è un gancio.

### 3.3 Cosa succede a ogni runlevel

| Range | Dominio | Esempi di file |
|---|---|---|
| **000** | inizializzazione framework, debug, sito, sessione, cache, privacy, localizzazione | `_000.debug.php`, `_015.site.php`, `_050.session.php`, `_090.translation.php` |
| **100** | sorgenti dati e servizi base: MySQL, Redis, Memcached, sicurezza, redirect, Google, Microsoft | `_120.mysql.php`, `_125.mysql.php`, `_130.redirect.php` |
| **200** | autenticazione, utente corrente, gruppi, permessi | `_200.auth.php`, `_210.auth.php`, `_250.auth.php` |
| **300** | routing e albero delle pagine, mail, immagini, Twig | `_300.pages.php`, `_310.pages.php`, `_350.mail.php`, `_380.twig.php` |
| **400** | riscrittura URL, risoluzione della pagina corrente | `_400.rewrite.php`, `_420.pages.php`, `_430.security.php` |
| **500** | servizi esterni: SMTP, SMS, Slack, OpenAI, FTP, MapQuest | `_510.smtp.php`, `_550.slack.php`, `_570.openai.php` |
| **600** | integrazioni piattaforme terze: PayPal, Amazon, Facebook, Hotjar | `_610.paypal.php`, `_640.facebook.php` |
| **700** | automazioni, import/export, **controller** (elaborazione dati in arrivo), job | `_750.controller.php`, `_790.job.php` |
| **900** | sitemap, privacy, debug finale | `_980.sitemap.php`, `_990.debug.php` |

**Regola pratica:** se ti serve un dato, chiediti a che runlevel viene prodotto. Se ti serve
`$cf['mysql']['connection']`, non puoi usarlo prima del runlevel 125. Se ti serve
`$_SESSION['account']`, non prima del 210.

### 3.4 I tre array globali

| Array | Cos'è | Chi lo vede |
|---|---|---|
| **`$cf`** | tutta la configurazione interna del framework | solo PHP |
| **`$ct`** | il sottoinsieme di `$cf` esposto ai template; popolato dai runlevel via reference | PHP **e Twig** |
| **`$cx`** | ciò che è stato letto dai file JSON/YAML, prima del merge in `$cf` | solo PHP, nei runlevel |

Chiavi di primo livello tipiche di `$ct` (cioè: le variabili disponibili nei template):

```
page  pages  site  sites  session  request  get  post  view  etc
localization  tr  ietf  privacy  common  cache  image  img
debug  mysql  memcache  redis  jobs  bookmarks
google  microsoft  facebook  paypal  amazon  slack  openai  mapquest  hotjar ...
```

## 4. La regola dell'underscore: come si personalizza

È il meccanismo che rende il framework aggiornabile. Va imparato bene.

### 4.1 Il principio

> Per personalizzare un file standard **non lo si modifica**: si crea la sua controparte senza
> underscore nel percorso, e il framework la carica automaticamente.

```
_src/_lib/_esempio.php     ← standard (framework)
 src/lib/esempio.php       ← custom  (progetto)
```

La funzione che fa la traduzione è `path2custom()` (per un singolo file) e `glob2custom()`
(per i pattern). Rimuovono gli underscore iniziali dai segmenti del path, avendo cura di non
toccare eventuali underscore presenti nel percorso della document root.

### 4.2 Append o replace?

| Estensione custom | Comportamento |
|---|---|
| `src/lib/esempio.php` | dipende dal tipo di file (vedi sotto) |
| `src/lib/esempio.alt.php` | **sostituisce** il file standard — questo non viene eseguito |
| `src/lib/esempio.add.php` | **si aggiunge** al file standard, eseguito dopo |

Il default cambia in base al tipo di file:

- **runlevel** (`_src/_config/`) → il custom viene eseguito **dopo** lo standard (append)
- **librerie** (`_src/_lib/`) → il custom **sostituisce** lo standard (replace), perché contenendo
  dichiarazioni di funzioni causerebbe conflitti di ridichiarazione. Per forzare l'append si usa
  `.add.php`
- **macro di pagina** → cerca prima `.alt.php` (sostituisce), poi il custom (sostituisce), poi lo standard

### 4.3 Tabella riassuntiva

| Standard | Custom (aggiunge) | Custom (sostituisce) |
|---|---|---|
| `_src/_config/_100.security.php` | `src/config/100.security.php` | — |
| `_src/_lib/_example.php` | `src/lib/example.add.php` | `src/lib/example.php` o `example.alt.php` |
| `_src/_inc/_macro/_x.php` | — | `src/inc/macro/x.php` o `x.alt.php` |
| `_src/_twig/_inc/_page.head.twig` | — | `src/twig/inc/page.head.twig` |
| `_src/_tpl/_aurora/css/main.css` | — | `src/tpl/aurora/css/main.css` |

### 4.4 Le cartelle: standard vs custom

```
progetto/
├── .htaccess          routing Apache
├── index.php          routing Nginx
├── composer.json
│
├── _etc/  _mod/  _src/  _usr/    ← STANDARD: non si toccano, li sovrascrive l'aggiornamento
│
├── etc/   mod/   src/   usr/     ← CUSTOM:  il codice del progetto
│   └── src/
│       ├── config.json           configurazione
│       ├── shadow.json           credenziali (gitignored)
│       ├── config/               runlevel custom
│       ├── lib/                  librerie custom
│       ├── inc/pages/            dichiarazione pagine
│       ├── inc/macro/            macro di pagina
│       ├── inc/contents/         contenuti statici
│       ├── twig/                 override dei template comuni
│       └── tpl/                  override dei temi
│
├── var/                          ← DATI: log, cache, spool, upload. Mai nel deploy
└── tmp/
```

> ⚠️ **Eccezione importante per i deploy upstream.** Nei progetti *cliente* la regola "non toccare
> mai i file `_*`" è assoluta. Nei due deploy *upstream* del framework —
> `glisweb.istricesrl.it` e `glisdev.istricesrl.com` — i file `_*` **sono** il sorgente e si
> modificano direttamente. Vedi §17.4.

## 5. Configurazione

### 5.1 Dove sta e in che ordine viene letta

La configurazione non è in un file solo: il bootstrap ne legge diversi in sequenza e li fonde con
`array_replace_recursive()`. **L'ultimo letto vince.**

Prima i YAML, poi i JSON; dentro ogni gruppo, prima `ext/` poi `src/`, prima `config.*` poi `shadow.*`:

| Priorità | File | Note |
|---|---|---|
| 8 — minima | `src/config/ext/config.yaml` | default di estensione |
| 7 | `src/config/ext/shadow.yaml` | gitignored |
| 6 | `src/config.yaml` | config principale |
| 5 | `src/shadow.yaml` | gitignored |
| 4 | `src/config/ext/config.json` | |
| 3 | `src/config/ext/shadow.json` | gitignored |
| 2 | `src/config.json` | |
| 1 — **massima** | `src/shadow.json` | gitignored |

JSON e YAML sono intercambiabili: il kernel legge entrambi. Un progetto sceglie un formato e
lo usa in modo coerente.

**Il risultato di questa fusione è l'array `$cx`** (§3.4), e non è ancora la configurazione del
framework: è solo quello che c'era scritto nei file. La configurazione vera, `$cf`, la costruiscono
i runlevel: ciascuno dichiara i default del proprio pezzo (`$cf['mysql']`, `$cf['google']`…), poi
prende da `$cx` la parte che lo riguarda e ci si sovrappone. È per questo che nei file basta
scrivere **solo i valori che differiscono dai default**, e che `$cx` si usa nei runlevel e mai
altrove. Il meccanismo per esteso è al §5.3; la lettura dei file sta in
[`_src/_config.php`](https://github.com/istricesrl/glisweb/blob/develop/_src/_config.php), nella
sezione che inizializza `$cx`.

Per trovare le credenziali di un progetto che non conosci, leggi in ordine decrescente di
priorità: `src/shadow.json` → `src/config.json` → `src/shadow.yaml` → `src/config.yaml`.

La stessa logica vale per i moduli: `mod/<nome>/src/config.yaml` + `mod/<nome>/src/shadow.yaml`.

### 5.2 I profili DEV / TEST / PROD

`SITE_STATUS` vale `DEV`, `TEST` o `PROD` ed è determinata **automaticamente** dal bootstrap
confrontando l'`HTTP_HOST` con i domini di `$cf['sites']`. Non si imposta a mano.

Le costanti corrispondenti sono `DEVELOPEMENT`, `TESTING`, `PRODUCTION` (definite in
`_src/_config/_000.debug.php`).

Struttura MySQL, che è l'esempio canonico:

```yaml
mysql:
  servers:
    main:
      address:  "127.0.0.1"
      port:     "3306"
      username: "..."      # → shadow
      password: "..."      # → shadow
      db:       "ilmiosito"
  profiles:
    DEV:  { servers: [ "main" ] }
    TEST: { servers: [ "main" ] }
    PROD: { servers: [ "main" ] }
```

`servers` descrive i server disponibili; ogni ramo di `profiles` dice quali usare in quell'ambiente.
In questo esempio i tre ambienti usano lo stesso server `main`, ma ciascuna macchina ha il suo
`shadow.json` con le proprie credenziali. Un progetto che in collaudo punta a un altro database
dichiara un secondo server e lo nomina nel ramo `TEST`.

### 5.3 Dai profili al codice: la coppia di runlevel `N0` / `N5`

Come fa il framework a trasformare la configurazione qui sopra in una connessione? Seguire MySQL
passo per passo mostra un meccanismo che vale per **ogni** namespace di configurazione che cambia
per ambiente: il namespace non sta mai in un runlevel solo, ma in **due runlevel accoppiati**, uno
che finisce per `0` e uno che finisce per `5`.

**[`_src/_config/_120.mysql.php`](https://github.com/istricesrl/glisweb/blob/develop/_src/_config/_120.mysql.php)
— dichiarazione.** Contiene solo i default, un ramo per profilo. Niente merge, niente logica:

```php
// server disponibili
$cf['mysql']['servers']                     = array();

// profili di funzionamento
$cf['mysql']['profiles'][ DEVELOPEMENT ]    =
$cf['mysql']['profiles'][ TESTING ]         =
$cf['mysql']['profiles'][ PRODUCTION ]      = array();
```

**[`_src/_config/_125.mysql.php`](https://github.com/istricesrl/glisweb/blob/develop/_src/_config/_125.mysql.php)
— attivazione.** Sovrappone ai default quello che è arrivato dai file (`$cx`, §5.1), lo espone ai
template, aggancia il profilo dell'ambiente corrente e poi lo *consuma*, cioè apre le connessioni:

```php
// merge della configurazione letta dai file
if( isset( $cx['mysql'] ) ) {
    $cf['mysql'] = array_replace_recursive( $cf['mysql'], $cx['mysql'] );
}

// collegamento all'array $ct
$ct['mysql']            = &$cf['mysql'];

// link al profilo corrente
$cf['mysql']['profile'] = &$cf['mysql']['profiles'][ SITE_STATUS ];

// ...e poi il consumo: connessione ai server elencati in $cf['mysql']['profile']['servers']
```

| File | Ruolo | Contenuto |
|---|---|---|
| `_NNN0.<nome>.php` | **dichiarazione** | solo i default, un ramo per profilo |
| `_NNN5.<nome>.php` | **attivazione** | merge di `$cx`, collegamento a `$ct`, link al profilo corrente, e il consumo |

Con la regola standard/custom del §4, l'ordine di inclusione è:

```
_N0 standard  →  N0 custom  →  _N5 standard  →  N5 custom
```

Così quando `_N5` fa il merge, i default dichiarati dal progetto in `N0` custom ci sono già. E vale
l'avvertenza del §3.2: un runlevel custom senza il gemello standard non viene incluso.

Altre coppie da leggere, costruite allo stesso modo: `_040`/`_045` (cache), `_110`/`_115`
(google), `_160`/`_165` (microsoft).

> **Da `N5` in poi il codice legge sempre da `$cf['<ns>']['profile']`**, mai da
> `$cf['<ns>']['<chiave>']`. Codice che legge la seconda forma su un namespace a profili sta
> ignorando l'ambiente: è un bug.

Per aggiungere un namespace nuovo con questo schema c'è la checklist A.3.

### 5.4 Due regole d'oro sulla configurazione

**Regola 1 — I file di configurazione sono artefatti di deploy.**
`src/config.json` viene copiato **identico** su DEV, TEST e PROD. Ne segue che **non può contenere
un valore che vale per un ambiente solo**. Un id, una soglia, un endpoint interno misurati su un
ambiente e messi lì nudi sono un bug latente che esplode al primo deploy, in silenzio e
sull'ambiente sbagliato. Se un valore cambia per ambiente, va sotto `profiles`.

**Regola 2 — I valori di lavoro non sono configurazione.**
Soglie ricalcolate, cursori, ultimi id lavorati, timestamp dell'ultima esecuzione: quella roba
sta in `var/spool/<qualcosa>/`, non nei file di configurazione. `var/` è escluso dal deploy,
quindi il valore resta locale all'ambiente **per costruzione**. File assente o non parsabile =
valore NULL = funzione ferma: su un ambiente nuovo la cosa parte spenta senza che nessuno debba
ricordarsene.

> **Euristica:** se per scrivere quel valore hai dovuto interrogare il database di quell'ambiente,
> non è configurazione — è spool.

## 6. Pagine

### 6.1 Come si dichiara una pagina

Le pagine sono voci dell'array `$p`, dichiarate in file PHP sotto
`src/inc/pages/<nome>.<lingua>.php`. All'avvio (runlevel [`_310.pages.php`](https://github.com/istricesrl/glisweb/blob/develop/_src/_config/_310.pages.php)) il framework raccoglie
tutti questi file — base e moduli, standard e custom — e ne unisce le definizioni nell'albero
dei contenuti.

```php
<?php
    // lingua di questo file
    $l = 'it-IT';

    $p['home'] = array(
        'sitemap'   => true,
        'cacheable' => true,
        'title'     => array( $l => 'Il mio sito' ),
        'h1'        => array( $l => 'Benvenuto!' ),
        'content'   => array( $l => '<p>La mia prima pagina con GlisWeb.</p>' ),
        'template'  => array( 'path' => '_src/_tpl/_aurora/', 'schema' => 'default.twig' ),
        'parent'    => array( 'id' => NULL ),
        'menu'      => array( 'main' => array( '' => array(
            'label'    => array( $l => 'home' ),
            'priority' => '010'
        ) ) )
    );
```

### 6.2 Le chiavi di `$p`

| Chiave | Tipo | Descrizione |
|---|---|---|
| `title` | array per lingua | titolo della pagina; da qui si deriva anche l'URL |
| `h1`, `h2` | array per lingua | intestazioni, renderizzate dal template |
| `content` | array per lingua | HTML del corpo (in alternativa: file in `src/inc/contents/`) |
| `template.path` | string | cartella del tema, es. `_src/_tpl/_aurora/` |
| `template.schema` | string | file Twig dello schema, es. `default.twig` |
| `parent.id` | string\|NULL | id della pagina genitore; `NULL` = primo livello |
| `macro` | array | percorsi dei file PHP di logica da includere (vedi §8) |
| `auth.groups` | array | gruppi autorizzati; **se assente, la pagina è pubblica** |
| `menu.<nome>` | array | inserisce la pagina nel menu `<nome>` con label e `priority` |
| `etc.tabs` | array\|string | id delle pagine da mostrare come schede (pattern del CMS) |
| `sitemap` | bool | inclusione nella sitemap XML |
| `cacheable` | bool | la pagina può essere messa in cache |
| `icon` | string | HTML dell'icona, tipicamente Font Awesome |
| `id_sito` | int | limita la pagina a un sito; **se assente, la pagina è su tutti i siti** |
| `javascript` | string | JS di pagina, renderizzato nel blocco `javascript` |

Le chiavi `title`, `h1`, `h2` e `content` sono **indicizzate per lingua**: sono le lingue
dichiarate nel `name` del sito.

### 6.3 URL e routing

| Pagina | URL |
|---|---|
| la pagina indicata in `homes` | `/` |
| una pagina di primo livello | `/<riferimento>.it-IT.html` |
| una pagina figlia | `/<genitore>/<riferimento>.it-IT.html` |

Il `<riferimento>` è derivato automaticamente dal `title`. La risoluzione avviene nel runlevel
[`_400.rewrite.php`](https://github.com/istricesrl/glisweb/blob/develop/_src/_config/_400.rewrite.php), che percorre i segmenti dell'URL cercando a ogni passo una pagina con quel
riferimento e il genitore giusto.

Le regole di `.htaccess` che portano qui:

```apache
RewriteRule ^/?$                                    _src/_api/_pages.php [L,QSA]
RewriteRule ^([A-Za-z0-9._\-/]+)\.([a-z]{2}-[A-Z]{2})\.html?$  _src/_api/_pages.php?__rw__=$1&__lg__=$2
RewriteRule ^([A-Za-z0-9._\-/]*[A-Za-z0-9_-])(?:\.[A-Za-z0-9]+)?$  _src/_api/_pages.php?__rw__=$1
```

Per il debug è utile sapere che si può forzare la pagina corrente con il parametro `__pg__`
(o la scorciatoia `p`): `?p=dashboard`.

### 6.4 Il pattern del CMS: view / form / tools / tabs

Nel CMS ogni entità gestita ha lo stesso gruppo di pagine, legate da `parent` e `etc.tabs`:

| Pagina | Cosa mostra | Schema |
|---|---|---|
| `<gruppo>.<entità>.view` | l'**elenco** delle righe | `default.view.twig` |
| `<gruppo>.<entità>.view.<variante>` | un elenco filtrato (es. `archiviate`) | `default.view.twig` |
| `<gruppo>.<entità>.tools` | le **azioni** sull'insieme (esportazioni, operazioni massive) | `default.tools.twig` |
| `<gruppo>.<entità>.form` | la **scheda** di una riga | `<gruppo>.<entità>.form.twig` |
| `<gruppo>.<entità>.form.<scheda>` | le altre schede della stessa riga | a seconda della scheda |

Le schede di navigazione (i *tab*) sono **due gruppi distinti**: quello dell'elenco e quello della
scheda di dettaglio. La pagina che apre il gruppo elenca i tab in `etc.tabs` come array; le altre
pagine del gruppo scrivono in `etc.tabs` solo l'id della pagina che li elenca, come stringa, e
ereditano il gruppo da lì (la risoluzione è in
[`_src/_config/_420.pages.php`](https://github.com/istricesrl/glisweb/blob/develop/_src/_config/_420.pages.php)). Ecco com'è fatto davvero, nel modulo notizie
([`_mod/_NO000.notizie/_src/_inc/_pages/_contenuti.it-IT.php`](https://github.com/istricesrl/glisweb/blob/develop/_mod/_NO000.notizie/_src/_inc/_pages/_contenuti.it-IT.php),
abbreviato):

```php
// lingua e modulo di questo file
$l = 'it-IT';
$m = DIR_MOD . '_NO000.notizie/';

// l'elenco: apre il primo gruppo di tab e sta nel menu del CMS
$p['contenuti.notizie.view'] = array(
    'title'     => array( $l => 'contenuti notizie' ),
    'h1'        => array( $l => 'notizie' ),
    'parent'    => array( 'id' => 'contenuti' ),
    'template'  => array( 'path' => '_src/_tpl/_athena/', 'schema' => 'default.view.twig' ),
    'macro'     => array( $m . '_src/_inc/_macro/_contenuti.notizie.view.php' ),
    'auth'      => array( 'groups' => array( 'roots', 'staff' ) ),
    'etc'       => array( 'tabs' => array( 'contenuti.notizie.view',
                                           'contenuti.notizie.view.archiviate',
                                           'contenuti.notizie.tools' ) ),
    'menu'      => array( 'admin' => array( '' => array( 'label' => array( $l => 'notizie' ), 'priority' => '200' ) ) )
);

// una pagina del primo gruppo: rimanda all'elenco per i tab
$p['contenuti.notizie.tools'] = array(
    'title'     => array( $l => 'azioni contenuti notizie' ),
    'h1'        => array( $l => 'azioni' ),
    'parent'    => array( 'id' => 'contenuti.notizie.view' ),
    'template'  => array( 'path' => '_src/_tpl/_athena/', 'schema' => 'default.tools.twig' ),
    'macro'     => array( $m . '_src/_inc/_macro/_contenuti.notizie.tools.php' ),
    'auth'      => array( 'groups' => array( 'roots', 'staff' ) ),
    'etc'       => array( 'tabs' => 'contenuti.notizie.view' )
);

// la scheda: figlia dell'elenco, apre il secondo gruppo di tab
$p['contenuti.notizie.form'] = array(
    'title'     => array( $l => 'contenuti notizie form' ),
    'h1'        => array( $l => 'gestione' ),
    'parent'    => array( 'id' => 'contenuti.notizie.view' ),
    'template'  => array( 'path' => '_src/_tpl/_athena/', 'schema' => 'contenuti.notizie.form.twig' ),
    'macro'     => array( $m . '_src/_inc/_macro/_contenuti.notizie.form.php' ),
    'auth'      => array( 'groups' => array( 'roots', 'staff' ) ),
    'etc'       => array( 'tabs' => array( 'contenuti.notizie.form',
                                           'contenuti.notizie.form.archiviazione',
                                           'contenuti.notizie.form.tools' ) )
);
```

Tre cose da notare:

- `$m` è la cartella del modulo: le macro si indicano con il percorso **standard**, e il framework
  cerca da solo l'eventuale versione custom (§8.2);
- le pagine del CMS hanno sempre `auth.groups`, perché senza sono pubbliche (§14.4);
- la scheda è figlia dell'elenco (`parent`): nell'albero delle pagine, e quindi nel breadcrumb,
  sta sotto l'elenco da cui la si apre.

Le pagine di un'entità si reggono su tre cose che la guida spiega più avanti: la vista
`<tabella>_view` con la colonna `__label__`, da cui l'elenco legge (§9.5); la `controller()` in
modalità view, che fa filtri, ordinamento e paginazione (§10.6); e le macro di default che
mettono insieme i pezzi (§11). È il pattern da copiare quando si aggiunge una nuova entità
gestita: la checklist è la A.2.

## 7. Template e Twig

### 7.1 Anatomia di un tema

Un tema (o *template*) è una cartella sotto `_src/_tpl/`. Ne arrivano diversi con il framework:

| Tema | Uso |
|---|---|
| `_aurora` | sito pubblico, punto di partenza tipico |
| `_athena` | **area di amministrazione (CMS)** |
| `_arianna`, `_cassandra`, `_demetra`, `_lydia`, `_minerva`, `_sarah` | altri temi pubblici |

```
_src/_tpl/_aurora/
├── etc/template.yaml     configurazione del tema (CSS, JS, menu, schema di default)
├── ext/main.twig         lo scheletro HTML esteso da tutti gli schemi
├── default.twig          schema di pagina generico
├── login.twig            schema usato quando i permessi non bastano
├── inc/                  header.twig, navbar.twig, footer.twig
├── lib/                  macro Twig del tema
├── css/  js/             asset del tema
└── READ.md
```

### 7.2 `etc/template.yaml`

```yaml
template:
  type: "twig"
  menu:
    main: null            # i menu che il tema vuole generare
  default: "default.twig" # schema usato se la pagina non ne specifica uno
  login: "login.twig"     # schema usato in caso di permessi insufficienti

css:
  internal:  { all: [ "_src/_css/_main.css" ] }        # dal framework
  template:
    all:    [ "css/main.css" ]                          # dal tema
    print:  [ "css/main.print.css" ]
    screen: [ "css/main.screen.css" ]
  external:  { all: [ "https://cdnjs.../all.min.css" ] } # da CDN

js:
  internal: [ "_src/_js/_main.js" ]
  template: [ "js/main.js" ]
  external: [ "https://cdnjs.../jquery.min.js" ]
```

Esiste anche il formato INI (`etc/template.conf`), storico; YAML è quello da preferire.
Un file `etc/template.add.yaml` custom si aggiunge a quello standard.

**Caching automatico delle risorse esterne.** Le URL in `css.external` e `js.external` vengono
scaricate e cachate su filesystem alla prima richiesta della pagina, in
`var/cache/css/<host>/<path>` e `var/cache/js/<host>/<path>` (per i CSS vengono cachate anche
le risorse riferite via `url(...)`: font, immagini). Poi vengono servite localmente.

> ⚠️ **Non c'è TTL né refresh automatico.** Per aggiornare una risorsa si cancella a mano il file
> in `var/cache/` oppure si usa una URL versionata (`bootstrap@5.3.2/...`).
> Le URL che contengono marker Twig (`{{`, `{%`, `{#`) non vengono cachate: restano in `external`
> e vengono pre-renderizzate a runtime (es. la site key di reCAPTCHA).

### 7.3 Come si scrive uno schema

Ogni schema estende `ext/main.twig` e riempie dei blocchi:

```twig
{# LIBRERIE #}
{% import '_lib/_default.twig' as cms %}
{% import '_lib/_form.twig'    as frm %}
{% import 'lib/default.twig'   as def %}

{# SCHEMA ESTESO #}
{% extends "ext/main.twig" %}

{# BLOCCO MAIN #}
{% block main %}
<h1>{{ include( template_from_string( page.h1[ localization.language.ietf ]|default('') ) | raw ) }}</h1>
<div>{{ include( template_from_string( page.content[ localization.language.ietf ]|default('') ) | raw ) }}</div>
{% endblock main %}
```

I blocchi disponibili in `ext/main.twig`: `header`, `nav`, `main`, `footer`, `modals`, `javascript`.

Nota il pattern `include( template_from_string( ... ) )`: serve perché i contenuti delle pagine
possono a loro volta contenere sintassi Twig, e vengono quindi renderizzati ricorsivamente.

### 7.4 Le librerie di macro Twig

Stanno in `_src/_twig/_lib/` e **si importano sempre con lo stesso prefisso**, per coerenza fra
un template e l'altro:

| Libreria | Prefisso | Contenuto |
|---|---|---|
| `_default.twig` | `cms` | `formButton()` (con reCAPTCHA), `image()`, `video()` |
| `_form.twig` | `frm` | `openForm()`, `closeForm()`, `input()`, `textarea()`, `select()`, `checkbox()`, `button()`, `uploader()` |
| `_navigation.twig` | `nav` | `menu()`, `selectMenu()`, `lineMenu()`, `tabs()`, `breadcrumbs()` |
| `_privacy.twig` | `prv` | banner cookie e informative |
| `_translation.twig` | `trn` | `tr()`, `trw()` — traduzione dei microcontenuti |

### 7.5 Le variabili disponibili nei template

Twig riceve `$ct` come contesto. Le più usate:

| Variabile | Contenuto |
|---|---|
| `page` | la pagina corrente (tutte le chiavi di `$p`, più `url`, `parents`, `backurl`) |
| `pages` | l'albero di tutte le pagine |
| `site` / `sites` | il sito corrente / tutti i siti |
| `session` | `$_SESSION`, in particolare `session.account` |
| `request` / `get` / `post` | `$_REQUEST`, `$_GET`, `$_POST` |
| `view` | configurazione e dati della vista corrente (§11) |
| `etc` | area libera per la macro di pagina: tendine, include, flag |
| `localization` | lingua corrente, `localization.language.ietf` |
| `tr` | tabella delle traduzioni |
| `privacy`, `common`, `image`, ... | namespace di configurazione esposti |

### 7.6 Il JavaScript

Il framework ha una libreria JavaScript propria: `_src/_js/_main.js` più tredici librerie in
`_src/_js/_lib/` (validazione dei form, chiamate alle API, tendine intelligenti, upload, editor).
Le librerie di terzi — jQuery, Bootstrap, Chart.js — non stanno lì: si dichiarano per URL e il
framework se le copia in locale.

I tag `<script>` li emette un punto solo, `_src/_twig/_inc/_page.close.twig`, alla chiusura del
`<body>`, in quest'ordine e tutti con `defer`:

```
1. var siteRoot          l'unica variabile che il server passa al JS
2. js.cached             copie locali delle risorse esterne (var/cache/js/)
3. js.external           URL remote non ancora copiate
4. js.internal           _src/_js/…
5. js.template           la cartella del tema: src/js/main.js
```

⚠️ **Il JavaScript non ha il meccanismo standard/custom.** Per i CSS esiste un `css.custom` che il
framework risolve da sé cercando la controparte senza underscore; **per il JS non esiste niente di
equivalente**. Un file messo in `src/js/` e non dichiarato da nessuna parte **non viene caricato
mai**, in silenzio. I tre modi per dichiararlo:

```yaml
# 1. src/tpl/<tema>/etc/template.add.yaml — additivo, è la strada consigliata
js:
  internal: [ "src/js/progetto.js" ]
```

```php
// 2. nella definizione della pagina, per un JS che serve a una pagina sola
'js' => array( 'internal' => array( '_src/_js/_lib/_codemirror.js' ) ),
// ⚠️ le pagine stanno in cache: dopo la modifica serve /task/memcache.clean
```

3. sovrascrivere l'intero `etc/template.yaml` con la controparte custom — potente e sconsigliato,
   ci si prende in carico anche le risorse che il tema aggiungerà in futuro.

Due trappole che costano tempo: i JS interni escono **senza query di versione**, quindi dopo una
modifica i browser già aperti servono la copia vecchia finché non si ricarica forzando; e la
versione di **Bootstrap la decide il tema**, non il framework.

Il dettaglio — le librerie una per una, gli attributi che il JS legge nel markup
(`also-required`, `required-alternative`, `populate-api`, `uploader-field`, `job-id`…), il dialogo
con le API e il JavaScript del CMS — sta nel manuale sviluppatore, capitolo *il javascript del
framework*.

## 8. Macro di pagina: dove vive la logica

### 8.1 Cos'è una macro di pagina

⚠️ **Attenzione al nome**: una "macro di pagina" **non** è una macro Twig. È un normale file PHP
incluso dall'API dopo il bootstrap e prima del rendering. È il posto dove va la logica applicativa
specifica di una pagina.

Si dichiara nella chiave `macro` della pagina:

```php
$p['contenuti.notizie.view'] = array(
    // ...
    'macro' => array( $m . '_src/_inc/_macro/_contenuti.notizie.view.php' ),
);
```

Il file viene incluso con `require`, quindi **condivide lo scope** con l'API: `$cf`, `$ct`,
`$_REQUEST` sono lì, e tutte le funzioni delle librerie sono disponibili.

### 8.2 Ordine di risoluzione

Per ogni macro dichiarata, il framework cerca in quest'ordine e si ferma alla prima che trova:

```
1. src/inc/macro/<nome>.alt.php    ← custom alternativa
2. src/inc/macro/<nome>.php        ← custom
3. _src/_inc/_macro/_<nome>.php    ← standard
```

Se non trova niente: `die( 'impossibile trovare la macro di pagina ...' )`.

### 8.3 Cosa fa tipicamente una macro

```php
<?php
    // 1. dichiara cosa deve fare la pagina
    $ct['form']['table'] = 'notizie';

    // 2. prepara i dati accessori (tendine, opzioni)
    $ct['etc']['select']['tipologie_notizie'] = tendinaTipologieNotizie();
    $ct['etc']['select']['ruoli_anagrafica']  = mysqlCachedIndexedQuery(
        $cf['memcache']['index'],
        $cf['memcache']['connection'],
        $cf['mysql']['connection'],
        'SELECT id, __label__ FROM ruoli_anagrafica_view WHERE se_notizie = 1'
    );

    // 3. delega il lavoro pesante alla macro di default
    require DIR_SRC_INC_MACRO . '_default/_default.form.php';

    // 4. eventualmente post-elabora i risultati
```

Questo è il pattern dominante nel CMS: **configura, delega, post-elabora**. Le macro di default
disponibili sono in `_src/_inc/_macro/_default/`:

| File | Uso |
|---|---|
| `_default.view.php` | elenchi tabellari con filtri, ordinamento, paginazione |
| `_default.form.php` | schede di dettaglio con CRUD |
| `_default.form.multilingua.php` | schede con campi tradotti |
| `_default.tools.php` | pagine di azioni |

## 9. Il database

### 9.1 Panoramica

Il database, lo si è visto al §2.7, è **opzionale**: serve quando entrano in gioco il CMS, gli
account o i moduli gestionali. Quando c'è, è MySQL o MariaDB, e non è necessariamente uno solo:
in `mysql.servers` si possono dichiarare più server, ciascuno con il proprio database, e il profilo
di ogni ambiente elenca quali usare (§5.2). Il framework si connette a tutti quelli elencati, le
connessioni stanno in `$cf['mysql']['connections']`, e la prima riuscita diventa quella di default,
`$cf['mysql']['connection']`, che è quella che usano le funzioni del framework.

Lo schema di un database GlisWeb non si scrive a mano: arriva con il framework, sotto forma di
**patch** SQL da applicare in ordine (§9.7). I file di base delle patch sono anche la mappa più
rapida di cosa c'è dentro un database GlisWeb, e di come sono organizzati questo capitolo e i
successivi:

| Patch | Cosa crea | Dove se ne parla |
|---|---|---|
| `tables` | le tabelle, costruite secondo cinque forme | §9.3, §9.4 |
| `indexes` | gli indici, su cui si progettano anche le viste | §9.5 |
| `acl` | le tabelle dei permessi riga per riga | §14.4 |
| `data` | i dati di base: lingue, geografia, valute, IVA… | §9.2, §9.3 |
| `constraints` | le chiavi esterne, il cui vincolo discende dalla forma della tabella | §9.4 |
| `procedures` | funzioni e procedure | — |
| `static` | le viste statiche, tabelle materializzate dai job | §9.5 |
| `views` | le viste `<tabella>_view`, con la colonna `__label__` | §9.5 |
| `reports` | i report, che incrociano più entità | §9.5 |

Sopra questo schema lavorano le funzioni di accesso (§9.6) e soprattutto la `controller()`
(capitolo 10), che è la strada con cui passano tutte le scritture.

### 9.2 Database di supporto e database di lavoro

Fra i database a cui il framework è connesso, quello che contiene i dati di funzionamento del
framework si chiama **database di supporto**; gli altri sono **database di lavoro**.

Il database di supporto contiene i dati strutturali — lingue, geografia, fusi orari, unità di
misura, valute — e integra array già presenti nel framework aggiungendoci dati.

### 9.3 Le tre categorie di tabelle

| Categoria | Modificabile dall'interfaccia? | Esempi |
|---|---|---|
| **standard** | **No** — sono parte del framework; modificarle è un aggiornamento | `lingue`, `comuni`, `provincie`, `stati`, `valute`, `iva`, `udm` |
| **assistite** | Sì — contengono dati standard per comodità, ma sono gestibili | `categorie_anagrafica`, `listini`, `reparti`, `certificazioni` |
| **gestite** | Sì — sono i dati dell'applicazione | `anagrafica`, `notizie`, `documenti`, ... |

### 9.4 Le cinque forme di tabella

| Forma | Cosa descrive | Vincolo verso di essa | Esempio |
|---|---|---|---|
| **principale** | oggetti indipendenti, che hanno senso di per sé | `SET NULL` | `anagrafica` |
| **secondaria** | oggetti dipendenti da un principale | `CASCADE` | `telefoni` |
| **di relazione** | relazioni molti-a-molti | `CASCADE` | `anagrafica_progetti` |
| **di multirelazione** | relazioni fra più entità | `CASCADE` | `documenti_articoli` |
| **di specifica** | qualifica un principale o una relazione | `NO ACTION` | `tipologie_anagrafica`, `ruoli_anagrafica` |

La scelta del vincolo non è arbitraria: discende dalla forma. Un telefono senza la sua anagrafica
non ha senso → `CASCADE`. Un'anagrafica senza tipologia sarebbe decontestualizzata ma esiste
comunque → `NO ACTION`, il framework impedisce di cancellare la tipologia.

Le tabelle **ricorsive** hanno una relazione con sé stesse (tipicamente `id_genitore`) e su quel
campo si applica sempre `NO ACTION`, per evitare inconsistenze nell'albero.

Prefissi convenzionali: `categorie_*`, `tipologie_*`, `relazioni_*`, `ruoli_*`.
Le `ruoli_*` stanno alle tabelle di relazione come le `tipologie_*` stanno alle principali.

### 9.5 Tabelle e viste: la convenzione `_view` e `__label__`

> Ogni tabella ha una vista corrispondente, con lo stesso nome più il suffisso **`_view`**.
> Ogni vista **deve** avere la colonna **`__label__`**.

```
anagrafica          → anagrafica_view          (con __label__)
notizie             → notizie_view             (con __label__)
tipologie_notizie   → tipologie_notizie_view   (con __label__)
```

`__label__` è la rappresentazione testuale della riga: è quella che il framework usa per i menu
a tendina (`id` + `__label__`) e come colonna leggibile negli elenchi. Le viste vanno costruite
in base agli indici delle tabelle, per massimizzare le performance.

Esistono anche le **viste statiche** (`*_view_static`): tabelle materializzate popolate da job,
per le entità le cui viste sono troppo pesanti da calcolare a ogni richiesta. E i **report**
(`__report_*`): a differenza delle viste statiche, che si riferiscono a una sola entità, i report
mettono insieme più entità per produrre un dato di sintesi.

### 9.6 Le funzioni di accesso

Le librerie sono `_src/_lib/_mysql.tools.php` (generiche) e `_src/_lib/_mysql.utils.php`
(specifiche del dominio, dipendono da `$cf`).

Le più usate:

```php
// query generica — restituisce array di righe (SELECT) o id (INSERT)
mysqlQuery( $cf['mysql']['connection'], $q, $params, $errori );

// query preparata
mysqlPreparedQuery( $c, $q, array( 'i' => 1, 's' => 'testo' ), $e );

// scorciatoie di lettura
mysqlSelectValue( $c, 'SELECT count(*) FROM anagrafica' );   // un valore
mysqlSelectRow(   $c, 'SELECT * FROM anagrafica WHERE id=?' ); // una riga
mysqlSelectColumn( 'nome', $c, $q );                          // una colonna

// versioni cachate (memcache)
mysqlCachedQuery( $mc, $c, $q );
mysqlCachedIndexedQuery( $idx, $mc, $c, $q );   // tipico per le tendine

# ATTENZIONE al nome: l'"indexed" di mysqlCachedIndexedQuery e' l'indice di
# invalidazione della CACHE, non la chiave del risultato. La funzione ritorna una
# LISTA NUMERICA di righe ( 0, 1, 2, ... ), quindi array_keys() su quel risultato
# da' 0,1,2 e non gli id. Il 15/09/2026 questo ha fatto negare per giorni le stampe
# ai familiari in un'area riservata: il controllo autorizzava le anagrafiche 0, 1 e 2,
# che non esistono. Si legge sempre per valore: $riga['id'].
mysqlSelectCachedValue( $mc, $c, $q );

// operazioni di alto livello
mysqlInsertRow( $c, $riga, $tabella );
mysqlDuplicateRow( $c, $tabella, $idOrigine );
mysqlDuplicateRowRecursive( $c, $tabella, $idOrigine );  // con i figli
mysqlDeleteRowRecursive( $mc, $c, $tabella, $id );
```

In `_mysql.utils.php` ci sono anche le funzioni `tendina*()` (`tendinaStati()`, `tendinaProvincie()`,
`tendinaAnni()`, `tendinaSiNo()`, ...) che restituiscono array pronti per `frm.select()`, e le
`aggiungi*()` (`aggiungiImmagini()`, `aggiungiFile()`, `aggiungiMetadati()`, ...) che arricchiscono
un array di dati con le entità collegate.

L'esito della connessione e tutte le query dell'ultima richiesta stanno in
`var/log/latest/mysql.latest.log`.

### 9.7 Lo schema: il sistema di patch

Lo schema non si crea a mano: si applica con le patch.

```
_usr/_database/_patch/
├── _010000999999.tables.sql
├── _030000999999.indexes.sql
├── _040000999999.acl.sql
├── _050000999999.data.sql
├── _060000999999.constraints.sql
├── _070000999999.procedures.sql
├── _080000999999.static.sql
├── _090000999999.views.sql
├── _100000999999.reports.sql
└── _202609151510.sedi.inline.backfill.sql   ← patch incrementale, datata
```

Si applicano chiamando:

```
http://miosito.local/task/mysql.patch
```

Il task crea la tabella `__patch__`, legge l'ultimo livello applicato e applica in ordine tutte
le patch successive, registrandole. È idempotente: si può rilanciare. Il commento in testa a
[`_src/_api/_task/_mysql.patch.php`](https://github.com/istricesrl/glisweb/blob/develop/_src/_api/_task/_mysql.patch.php) spiega la numerazione per esteso.

Le patch incrementali si chiamano con un timestamp `AAAAMMGGHHMM` come prefisso, così l'ordine
è garantito.

## 10. La `controller()`: il cuore del framework

Questo è il capitolo che separa chi "usa" GlisWeb da chi lo capisce.

### 10.1 L'idea

> Ogni array presente in `$_REQUEST` il cui nome **non** inizia con `__` viene interpretato come
> un **blocco dati** riferito a una tabella, e passato alla funzione `controller()`, che esegue
> l'operazione CRUD corrispondente al metodo HTTP.

Questo succede al runlevel [`_750.controller.php`](https://github.com/istricesrl/glisweb/blob/develop/_src/_config/_750.controller.php), quindi **prima** che la macro di pagina venga
eseguita. Quando la tua macro parte, la scrittura è già avvenuta.

```php
// _src/_config/_750.controller.php, semplificato
foreach( $_REQUEST as $k => &$v ) {
    if( is_array( $v ) && checkNomeBloccoDati( $k ) ) {
        $cf['controller']['status'][ $k ] = controller(
            $cf['mysql']['connection'],
            $cf['memcache']['connection'],
            $v,                            // il blocco dati
            $k,                            // il nome dell'entità/tabella
            $_SERVER['REQUEST_METHOD'],    // il metodo
            NULL,
            $_REQUEST['__err__'][ $k ],    // errori
            $_REQUEST['__info__'][ $k ],   // direttive e stato
            $pi, $ci, $cf['speed']
        );
    }
}
```

La conseguenza pratica: **un form HTML che nomina i suoi campi correttamente salva sul database
senza una riga di PHP.**

```html
<form method="post">
    <input type="hidden" name="notizie[id]"        value="12">
    <input type="hidden" name="notizie[__method__]" value="put">
    <input type="text"   name="notizie[nome]"      value="La mia notizia">
    <textarea            name="notizie[note]"></textarea>
    <button type="submit">salva</button>
</form>
```

### 10.2 I metodi

Il metodo si prende da `$_SERVER['REQUEST_METHOD']`, ma si può forzare con il campo speciale
`__method__` (che è quello che fa sempre il CMS, dato che i browser mandano solo GET e POST).

| Metodo | SQL generato |
|---|---|
| `GET` senza `id` | `SELECT` in **modalità view** (elenco, con filtri e paginazione) |
| `GET` con `id` | `SELECT * FROM t WHERE id = ?` — lettura di una riga |
| `POST` | `INSERT INTO t (...) VALUES (...)` |
| `PUT` | `UPDATE t SET ... WHERE id = ?` |
| `REPLACE` | `REPLACE INTO t (...) VALUES (...)` |
| `UPDATE` | `INSERT ... ON DUPLICATE KEY UPDATE ...` (upsert) |
| `DELETE` | `DELETE FROM t WHERE id = ?` |

`UPDATE` è la forma più usata per le importazioni: inserisce se non c'è, aggiorna se c'è.

### 10.3 I campi speciali del blocco dati

Le chiavi che iniziano e finiscono con `__` non sono colonne: sono direttive.

| Chiave | Effetto |
|---|---|
| `__method__` | forza il metodo (`get`, `post`, `put`, `delete`, `replace`, `update`) |
| `__table__` | forza la tabella di destinazione |
| `__firma__` | firma di importazione, bypassa il controllo permessi (uso batch) |
| `__reset__` | svuota `$_REQUEST[<tabella>]` dopo l'elaborazione |
| `__view_mode__` | forza la modalità di visualizzazione |
| `__forced_view__` | forza la visualizzazione anche con `id` presente |
| `__report_mode__` / `__filesystem_mode__` | modalità report / filesystem |

### 10.4 I valori speciali

Certi **valori** vengono sostituiti al volo:

| Valore | Diventa |
|---|---|
| `__null__` | `NULL` |
| `__parent_id__` | l'id del record padre (nelle sottoform) |
| `__self_id__` | l'id del record corrente |
| `__timestamp__` | `time()` |
| `__date__` | `date('Y-m-d')` |

Questo è quello che permette a una sottoform di collegarsi al padre **prima che il padre esista**:
si scrive `__parent_id__` e il framework lo risolve dopo l'INSERT del padre.

### 10.5 Sottoform e ricorsione

Se dentro un blocco dati c'è un array, quello è una **sottoform**: `controller()` la elabora
ricorsivamente dopo aver salvato il record principale.

```html
<!-- il padre -->
<input name="notizie[nome]" value="...">
<!-- la sottoform: una relazione -->
<input name="notizie[notizie_categorie][0][id_categoria]" value="3">
<input name="notizie[notizie_categorie][0][id_notizia]"   value="__parent_id__">
```

C'è anche una **modalità multipla**: se il blocco non ha campi al primo livello ma solo array,
`controller()` interpreta ognuno come un record autonomo della stessa tabella.

```php
// modalità singola
array( 'test' => array( 'id' => 1, 'nome' => 'Test' ) )

// modalità multipla
array( 'test' => array(
    0 => array( 'id' => 1, 'nome' => 'Test'   ),
    1 => array( 'id' => 2, 'nome' => 'Test 2' ),
) )
```

### 10.6 La modalità view: filtri, ordinamento, paginazione

Una `GET` senza `id` produce un elenco. Le direttive si passano tramite `$_REQUEST['__info__']`:

| Direttiva | Effetto |
|---|---|
| `__fields__` | campi da selezionare (se assente: tutti) |
| `__search__` | stringa di ricerca full-text sui `__fields__` |
| `__filters__` | filtri impostabili dall'utente |
| `__restrict__` | restrizioni imposte dal codice, non modificabili dall'utente |
| `__group__` | `GROUP BY` |
| `__sort__` | `ORDER BY` |
| `__pager__` | `LIMIT`; in uscita valorizza `total` e `pages` |

Gli operatori disponibili per `__filters__` e `__restrict__`:

| Op | Significato |
|---|---|
| `NN` | not null |
| `NL` | null |
| `EQ` | uguale |
| `GT` / `GE` | maggiore / maggiore o uguale |
| `LT` / `LE` | minore / minore o uguale |
| `LK` | like (contiene) |
| `IN` | in un elenco di valori separati da `\|` |
| `BT` | between (due valori separati da `\|`) |

```php
// solo le notizie non archiviate
$ct['view']['__restrict__']['data_archiviazione']['NL'] = true;

// solo i documenti di questo cliente
$ct['view']['__restrict__']['id_cliente']['EQ'] = $_REQUEST[ $ct['form']['table'] ]['id'];

// su campi multipli in OR: si separano con pipe
$ct['view']['__restrict__']['id_cliente|id_fornitore']['EQ'] = $id;
```

> **`__filters__` vs `__restrict__`:** i filtri sono quelli che l'utente può cambiare
> dall'interfaccia; le restrizioni sono imposte dal codice e non si possono aggirare.
> Un filtro di sicurezza va **sempre** in `__restrict__`.

### 10.7 Gli hook: `before`, `append`, `after`, `finally`

`controller()` cerca e include automaticamente dei file di hook, sia dal core sia dai moduli,
sia standard sia custom. I nomi seguono la convenzione:

```
_src/_inc/_controllers/_{default,<tabella con . al posto di _>}.<hook>.php
```

| Hook | Quando |
|---|---|
| `before.php` | prima della query di scrittura |
| `append.php` | durante la costruzione della query |
| `after.php` | subito dopo la query |
| `finally.php` | dopo l'elaborazione delle sottoform: è la fine di tutto |

`_default.*.php` vale per **tutte** le tabelle; `_anagrafica.indirizzi.before.php` vale solo per
la tabella `anagrafica_indirizzi`.

È il punto giusto per normalizzazioni, ricalcoli, notifiche e propagazioni. Esempi già presenti
nel framework: `_anagrafica.indirizzi.before.php` (normalizzazione indirizzi),
`_mail.finally.php`, `_url.before.php`.

### 10.8 L'esito

`controller()` restituisce uno status HTTP-like e lo scrive in `$_REQUEST['__info__'][<tabella>]['__status__']`:

| Status | Significato |
|---|---|
| `200` | ok |
| `400` | colonna inesistente (errore MySQL 1054) |
| `401` | permessi insufficienti |
| `409` | violazione di chiave univoca (errore MySQL 1062) |

Gli errori dettagliati stanno in `$_REQUEST['__err__'][<tabella>]`.

## 11. View e form del CMS

Con la `controller()` capita, le pagine del CMS diventano semplici: sono configurazione.

### 11.1 Una view (elenco)

La macro di pagina configura `$ct['view']` e delega a `_default.view.php`:

```php
<?php
    $ct['view'] = array(

        // la tabella (in realtà la sua _view) da cui leggere
        'table' => 'notizie',

        // dove porta il click su una riga
        'open' => array( 'page' => 'contenuti.notizie.form', 'table' => 'notizie' ),

        // le colonne: chiave = campo della vista, valore = intestazione
        'cols' => array(
            'id'        => '#',
            '__label__' => 'notizia',
            NULL        => 'azioni',       // colonna calcolata
        ),

        // classi CSS per colonna
        'class' => array(
            'id'        => 'd-none',
            '__label__' => 'no-wrap text-start',
            NULL        => 'no-wrap',
        ),

        'onclick' => array( NULL => 'event.stopPropagation();' ),

        // restrizioni non aggirabili
        '__restrict__' => array( 'data_archiviazione' => array( 'NL' => true ) ),

        // ordinamento di default
        '__sort__' => array( '__label__' => 'ASC' ),
    );

    // tendine eventualmente necessarie ai filtri
    $ct['etc']['select']['siti'] = $cf['sites'];

    // il lavoro vero
    require DIR_SRC_INC_MACRO . '_default/_default.view.php';

    // post-elaborazione delle righe
    foreach( $ct['view']['data'] as &$row ) {
        if( is_array( $row ) ) {
            $row['id_sito'] = ( ! empty( $row['id_sito'] ) && isset( $cf['sites'][ $row['id_sito'] ] ) )
                ? $cf['sites'][ $row['id_sito'] ]['__label__']
                : 'nessun sito';

            $buttons = array();
            $row[NULL] = implode( $buttons );   // riempie la colonna calcolata
        }
    }
```

La pagina usa lo schema `default.view.twig` del tema `_athena`, che disegna la tabella leggendo
`view.cols`, `view.class` e `view.data`.

Cosa fa `_default.view.php` sotto il cofano: costruisce l'id univoco della vista (usato per
memorizzare filtri e paginazione in sessione), fonde i filtri preimpostati con quelli in arrivo
dall'utente, traduce tutto in direttive `__info__` e innesca la `controller()` in modalità view.

### 11.2 Un form (scheda)

```php
<?php
    // la tabella gestita
    $ct['form']['table'] = 'notizie';

    // le tendine di cui il template ha bisogno
    $ct['etc']['select']['tipologie_notizie'] = tendinaTipologieNotizie();
    $ct['etc']['select']['categorie_notizie'] = tendinaCategorieNotizie();

    // il lavoro vero
    require DIR_SRC_INC_MACRO . '_default/_default.form.php';
```

Il template corrispondente:

```twig
{% import '_lib/_form.twig' as frm %}
{% extends 'ext/main.twig' %}

{% block main %}
{{ frm.openForm({ 'form': form, 'page': page, 'session': session, 'request': request }) }}

    <fieldset>
        <legend>dati generali</legend>

        <div class="form-group row">
            <div class="col-12 col-md-auto form-col">
                <span class="label-top">tipologia</span>
                {{ frm.select({
                    'field':   { 'name': 'id_tipologia' },
                    'source':  { 'values': etc.select.tipologie_notizie },
                    'request': request, 'form': form, 'page': page, 'pages': pages
                }) }}
            </div>
            <div class="col form-col">
                <span class="label-top">nome</span>
                {{ frm.input({
                    'field':   { 'name': 'nome', 'type': 'text' },
                    'request': request, 'form': form, 'page': page
                }) }}
            </div>
        </div>

        <div class="form-group row">
            <div class="col-12 form-col">
                <span class="label-top">note</span>
                {{ frm.textarea({
                    'field':   { 'name': 'note', 'rows': 2 },
                    'request': request, 'form': form, 'page': page
                }) }}
            </div>
        </div>

    </fieldset>

    {# sottoform: relazioni molti-a-molti #}
    {{ sub.categorie( form.table, 'notizie_categorie', 'categorie', site, page, pages, ietf, etc, request, session, 'id_notizia' ) }}

    <fieldset class="form-controls mt-auto">
        {{ def.controls( page, pages, ietf, session, form.table, request ) }}
    </fieldset>

</form>
{% endblock main %}
```

**Perché funziona.** `frm.openForm()` emette automaticamente i campi nascosti che la
`controller()` si aspetta:

```html
<input type="hidden" name="notizie[id]"                         value="...">
<input type="hidden" name="notizie[__method__]"                 value="post">
<input type="hidden" name="notizie[__reset__]"                  value="">
<input type="hidden" name="notizie[timestamp_inserimento]"      value="...">
<input type="hidden" name="notizie[id_account_inserimento]"     value="...">
<input type="hidden" name="__backurl__"                         value="...">
```

E ogni `frm.input({ 'field': { 'name': 'nome' } })` emette
`<input name="notizie[nome]" value="...">` con il valore già ripescato da `request`.

Il giro completo si chiude così: form → POST → runlevel 750 → `controller()` → INSERT/UPDATE →
macro di pagina → template ricarica i dati aggiornati.

## 12. Moduli

### 12.1 Come si attiva un modulo

I moduli stanno in `_mod/_<CODICE.nome>/` e sono **disattivi** di default. Si attivano in uno
di due modi:

```bash
# 1. creando la cartella corrispondente SENZA underscore
mkdir mod/PA000.pagine
```

```json
// 2. oppure dichiarandoli esplicitamente nella configurazione
{ "mods": { "active": { "array": [ "AN000.anagrafica", "PA000.pagine", "CO000.contenuti" ] } } }
```

Nel primo caso il framework fa auto-discovery delle sottocartelle di `mod/`.

### 12.2 Struttura di un modulo

Un modulo replica la struttura del framework:

```
_mod/_NO000.notizie/
└── _src/
    ├── _config/        _030.common.php, _310.pages.php, _420.pages.php
    ├── _inc/
```

## 13. Le API: REST, task, job, cron, print, download

### 13.1 La tabella di routing

Il `.htaccess` (o `index.php` su Nginx) instrada così:

| URL | Va a | Scopo |
|---|---|---|
| `/` | `_src/_api/_pages.php` | home |
| `/<path>.<lang>.html` | `_src/_api/_pages.php` | pagina |
| `/status` | `_src/_api/_status/_framework.php` | diagnostica del framework |
| `/status/<nome>` | `_src/_api/_status/_<nome>.php` | diagnostiche specifiche |
| `/cf` | `_src/_api/_status/_cf.php` | dump della configurazione |
| `/api/<entità>` | `_src/_api/_rest.php` | **API REST** |
| `/api/<entità>/<id>` | `_src/_api/_rest.php` | API REST su una riga |
| `/api/login`, `/api/logout` | `_src/_api/_user.php` | autenticazione JSON |
| `/api/cron` | `_src/_api/_cron.php` | esecuzione schedulata |
| `/task/<nome>` | `_src/_api/_task/_<nome>.php` | **task** |
| `/task/<modulo>/<nome>` | `_mod/_<modulo>/_src/_api/_task/_<nome>.php` | task di modulo |
| `/job/<id>` | `_src/_api/_job.php` | **job** in background |
| `/report/<nome>` | `_src/_api/_report/_<nome>.php` | report |
| `/print/<nome>` | `_src/_api/_print/_<nome>.php` | stampe PDF |
| `/var/<path>` | `_src/_api/_download.php` | download controllato |
| `/tiles/z/x/y.png` | `_src/_api/_osm.php` | tile di mappa |

Le API dirette (`_src/_api/_<nome>.php`) sono raggiungibili anche come `/api/<nome>` quando il
file esiste.

### 13.2 API REST

La REST API è un wrapper sottile attorno alla `controller()`: riceve JSON o form-urlencoded,
lo fa convergere in `$_REQUEST[<entità>]` e lascia lavorare il controller.

```bash
# lettura di un elenco
curl -H 'Accept: application/json' https://miosito/api/notizie

# lettura di una riga
curl -H 'Accept: application/json' https://miosito/api/notizie/12

# creazione
curl -X POST -H 'Content-Type: application/json' -H 'Accept: application/json' \
     -d '{"nome":"nuova notizia","id_tipologia":1}' \
     https://miosito/api/notizie

# modifica
curl -X PUT -H 'Content-Type: application/json' -H 'Accept: application/json' \
     -d '{"nome":"titolo corretto"}' \
     https://miosito/api/notizie/12
```

> L'header **`Accept` è obbligatorio**: senza, l'API non elabora la richiesta.
> Il metodo HTTP diventa il metodo della `controller()`, e valgono gli stessi permessi ACL.

### 13.3 Cron, task e job

**Il cron** si installa con:

```bash
sudo _src/_sh/_crontab.install.sh install https miosito.com
# scrive in /etc/cron.d/: * * * * * root curl -s 'https://miosito.com/api/cron' > /dev/null
```

Gira **ogni minuto**. All'avvio prende un lock MySQL (`GET_LOCK`): se il run precedente è ancora
in corso, esce senza fare nulla e riproverà il minuto dopo. Ha una durata massima configurabile
(`$cf['cron']['durata_massima']`, default 45 secondi).

**Task vs job:**

| | Task | Job |
|---|---|---|
| Cosa fa | un'operazione breve, che finisce entro il run | un'operazione lunga, a stati |
| Dove sta | `_src/_api/_task/_<nome>.php` | `_src/_api/_job/_<nome>.php` |
| Come si chiama | `/task/<nome>` o dal cron | `/job/<id>`, avviato da un task `*.start` |
| Esempi | `_mail.queue.send.php`, `_log.clean.php`, `_memcache.clean.php` | `_anagrafica.importazione.php`, `_comuni.importazione.php` |

Il pattern per un'importazione lunga è: un task `*.start` che crea il job → il cron avanza il job
un pezzo per volta → il job si segna lo stato e riprende dal punto giusto.

Task utili da conoscere:

```
/task/mysql.patch                     applica le patch di schema
/task/framework.setup                 setup iniziale
/task/mail.queue.send                 invio della coda mail
/task/pages.cache.clean               svuota la cache delle pagine
/task/memcache.clean                  svuota memcache
/task/log.clean                       ruota/pulisce i log
/task/images.resize                   genera i formati delle immagini
/task/indirizzi.geocode               geocodifica gli indirizzi
```

### 13.4 Mail

Le mail non si mandano in linea: si accodano.

```php
// accoda una mail da template
queueMailFromTemplate( $c, 'DEFAULT_CONTATTI', $dati, $timestamp_invio, $destinatario, 'it-IT' );

// accoda una mail costruita a mano
queueMail( $c, $timestamp_invio, $mittente, $destinatari, $oggetto, $corpo );
```

I template si dichiarano sotto `mail.tpl.<NOME>` nella configurazione. La coda viene svuotata dal
task `/task/mail.queue.send`, richiamato dal cron. `sendMail()` esiste ma è l'invio diretto SMTP:
si usa solo dove l'accodamento non ha senso.

## 14. Autenticazione, gruppi, permessi, ACL

### 14.1 Il login

- Il form di login **non usa CSRF token**: bastano i campi POST `__login__[user]` e
  `__login__[pasw]` (la password viene hashata in MD5 lato backend).
- URL di default: `/login.it-IT.html`.
- Il backend confronta contro `$cf['auth']['accounts']` (configurazione) o, in fallback, la vista
  MySQL `account_view`.
- A login riuscito viene popolato `$_SESSION['account']`.
- Il cookie è il `PHPSESSID` standard, con `cookie_secure=1` (**richiede HTTPS**),
  `cookie_httponly=1`, `cookie_samesite=Lax`.
- Storage delle sessioni: Redis → Memcached → filesystem, in quest'ordine di preferenza.

File rilevanti: `_src/_config/_210.auth.php` (logica), `_src/_config/_050.session.php`
(configurazione sessione), `_src/_api/_user.php` (endpoint REST).

### 14.2 La rigenerazione dell'id di sessione

**Ai login interattivi l'id di sessione viene rigenerato** (`session_regenerate_id(true)`,
anti session fixation). I dati di `$_SESSION` vengono mantenuti e `$_SESSION['id']` riallineato.
I login *stateless* (JWT, API `_user.php`, HTTP Basic) **non** rigenerano l'id.

> ⚠️ **Conseguenza da tenere a mente:** non salvare mai `session_id()` in una tabella come chiave
> di collegamento — dopo la rigenerazione la riga resterebbe orfana. La convenzione del framework
> è l'opposto: **tenere in `$_SESSION` l'id dell'entità** (es. `$_SESSION['id_carrello']`), perché
> i dati di `$_SESSION` sopravvivono alla rigenerazione.

Se un progetto deve comunque mantenere su DB un riferimento al session id, può agganciarsi alla
rigenerazione creando `src/inc/macro/session.regenerate.php` (o la variante di modulo): viene
inclusa subito dopo la rigenerazione e dispone di
`$cf['session']['regenerate']['old_id']` e `['new_id']`.

### 14.3 Gruppi e privilegi

I gruppi predefiniti (dichiarati in `_src/_config/_200.auth.php`) sono:

| Gruppo | Ruolo |
|---|---|
| `roots` | amministratori |
| `staff` | operatori |
| `users` | utenti registrati |

I gruppi trovati nella vista `gruppi_view` del database si integrano a questi.

I **privilegi** sono capability nominali indipendenti dai gruppi:

```
EDIT_CONFIGURAZIONE          editare la configurazione del framework
GESTIONE_ACCOUNT             gestire gli account
INVIO_DIRETTO_MAIL           inviare mail da API REST senza passare dalla coda
CANCELLAZIONE_RICORSIVA      cancellare ricorsivamente oggetti dal database
INVIO_ANAGRAFICA_ARCHIVIUM   inviare un'anagrafica ad Archivium
```

### 14.4 I due livelli di controllo

**Livello pagina** — `getPagePermission()`:

```php
'auth' => array( 'groups' => array( 'roots', 'staff' ) )
```

Se la pagina non ha `auth.groups`, è pubblica. Altrimenti serve un'intersezione fra i gruppi della
pagina e `$_SESSION['account']['gruppi']`. Senza permessi, il template mostra lo schema `login`
del tema invece del contenuto.

**Livello dato** — `getAclPermission()`:

I permessi dell'utente stanno in `$_SESSION['account']['permissions'][<tabella>]`, come array
di azioni consentite. Oltre alle azioni esplicite (`GET`, `POST`, `PUT`, `DELETE`) esistono due
permessi speciali:

| Permesso | Effetto |
|---|---|
| `CONTROL_FULL` (`'FULL'`) | tutte le azioni sulla tabella |
| `CONTROL_FILTERED` (`'FILTERED'`) | tutte le azioni, ma filtrate riga per riga dalla tabella ACL |

**Livello riga** — `getAclRights()`:

Quando esiste una tabella di ACL per l'entità, la `controller()` la aggiunge in JOIN alla query,
così l'elenco mostra solo le righe su cui l'utente ha diritti. È la modalità `FILTERED`.

### 17.4 Governance: progetto cliente vs upstream

Questa distinzione conta, e sbagliarla fa danni.

| Ruolo | Cos'è | Dove |
|---|---|---|
| **Progetto cliente** | usa il framework. I `_*` sono standard e **non si modificano**. Il custom va in `src/`, `mod/`, `var/` | tutto tranne i due path sotto |
| **Progetto upstream** | sviluppa il framework. I `_*` **sono** il sorgente e si modificano direttamente | `glisweb.istricesrl.it` e `glisdev.istricesrl.com` |

Come capire dove sei:

```bash
grep -q '"name": "istricesrl/glisweb"' composer.json && echo "UPSTREAM" || echo "CLIENTE"
```

**Il flusso corretto per far entrare una fix nel framework standard:**

1. **Modificare localmente nel progetto cliente.** Nella quasi totalità dei casi: creare un
   override custom senza underscore. Per fix urgenti che toccano davvero un `_*`, modificarlo
   *nel progetto cliente stesso*.
2. **Sincronizzazione**: un job raccoglie le divergenze del progetto rispetto al framework
   standard e genera un *disallineamento* che confluisce in `glisweb.istricesrl.it`.
3. **Valutazione**: su glisweb un manutentore valuta. Se la modifica è generalizzabile entra nel
   codice standard; altrimenti resta customizzazione del solo progetto cliente e va consolidata
   in `src/`/`mod/`.
4. **Redistribuzione**: le modifiche accettate vengono committate e ridistribuite ai progetti
   cliente al loro prossimo aggiornamento.

**Anti-pattern, da un progetto cliente:**

- ❌ SSH/edit/git sui deploy upstream per "anticipare" una fix — bypassa la valutazione e rischia
  di propagare modifiche non validate a tutti gli altri progetti
- ❌ PR o push diretti verso i repo upstream "perché ho una fix urgente" — il canale è comunque
  il disallineamento; i manutentori hanno strumenti per il fast-track
- ❌ toccare gli hard link fra glisweb e glisdev — è competenza esclusiva dei manutentori upstream

## Appendice A — Checklist operative

### A.1 Aggiungere una pagina statica

1. Crea o apri `src/inc/pages/site.it-IT.php`
2. Aggiungi la voce a `$p` con `title`, `h1`, `content`, `template`, `parent`
3. Se deve stare in un menu, aggiungi `menu.<nome>` con `label` e `priority`
4. Svuota la cache dei contenuti (`/task/memcache.clean`) o attendi l'invalidazione
5. Verifica: `_src/_sh/_smoke.curl.sh status /<riferimento>.it-IT.html`

### A.2 Aggiungere un'entità gestita completa (CRUD nel CMS)

1. **Database**: crea la tabella e la vista `<tabella>_view`, con la colonna `__label__`.
   Metti la DDL in una patch datata in `_usr/_database/_patch/`
2. **Pagine**: dichiara le quattro pagine `<gruppo>.<entità>.view`, `.form`, `.tools`,
   più eventuali varianti, tutte con lo stesso `etc.tabs`
3. **Macro view**: configura `$ct['view']` (`table`, `open`, `cols`, `class`, `__restrict__`,
   `__sort__`) e `require` `_default/_default.view.php`
4. **Macro form**: imposta `$ct['form']['table']`, prepara le tendine in `$ct['etc']['select']`,
   `require` `_default/_default.form.php`
5. **Template form**: `frm.openForm()`, i campi con `frm.*`, `def.controls()`, `</form>`
6. **Permessi**: `auth.groups` sulle pagine; permessi di tabella per gli account
7. **Applica**: `/task/mysql.patch`, poi verifica

### A.3 Aggiungere un namespace di configurazione a profili

1. Crea la **coppia** di runlevel standard `_src/_config/_NNN0.<nome>.php` e `_NNN5.<nome>.php`
2. In `N0`: solo i default, un ramo per `DEVELOPEMENT`/`TESTING`/`PRODUCTION`
3. In `N5`: merge di `$cx`, `$ct['<ns>'] = &$cf['<ns>']`, link a `profile`, poi il consumo
4. Nel progetto, se serve: `src/config/NNN0.<nome>.php` per i default di progetto
5. Nella configurazione: i valori sotto `<ns>.profiles.<AMBIENTE>`
6. Il codice legge **sempre** `$cf['<ns>']['profile']`

### A.4 Debuggare "la pagina non si vede"

```
1. /status                                  → il framework parte?
2. tail var/log/latest/run.latest.log       → dove si ferma?
3. ?p=<id pagina>                           → è un problema di rewrite o di pagina?
4. la pagina ha auth.groups?                → è un problema di permessi
5. la pagina ha id_sito?                    → è limitata a un altro sito
6. la cache dei contenuti è vecchia?        → /task/memcache.clean
```

### A.5 Debuggare "il form non salva"

```
1. i campi si chiamano <tabella>[<colonna>]?    → altrimenti il controller non li vede
2. c'è <tabella>[__method__]?                   → senza, arriva POST anche per una modifica
3. tail var/log/latest/mysql.latest.log         → la query è stata generata? cos'ha risposto?
4. $_REQUEST['__info__'][<tabella>]['__status__'] → 401 permessi, 409 duplicato, 400 colonna
5. la tabella esiste? le colonne si chiamano così?
6. il nome del blocco inizia per __?            → viene scartato
```

## Appendice B — Glossario e riferimenti rapidi

### B.1 Glossario

| Termine | Significato |
|---|---|
| **runlevel** | uno dei passi numerati dell'esecuzione del framework (`_NNN.<nome>.php`) |
| **factory** | il ruolo di un file di runlevel nel suo gruppo |
| **macro di pagina** | file PHP di logica applicativa incluso dall'API (non è una macro Twig) |
| **macro Twig** | funzione riutilizzabile di template, in `_src/_twig/_lib/` |
| **template / tema** | cartella sotto `_src/_tpl/` con schemi, CSS, JS |
| **schema** | il file Twig di una pagina (es. `default.view.twig`) |
| **blocco dati** | array in `$_REQUEST` il cui nome è una tabella; input della `controller()` |
| **sottoform** | array annidato in un blocco dati, elaborato ricorsivamente |
| **view** | pagina di elenco tabellare del CMS |
| **form** | pagina di scheda/dettaglio del CMS |
| **task** | operazione breve richiamabile via URL o dal cron |
| **job** | operazione lunga a stati, avanzata a pezzi dal cron |

## Appendice C — Errori comuni

**«Ho creato `src/config/800.mio.php` ma non viene eseguito.»**
Manca il gemello standard. Il loop dei runlevel fa `glob()` sui soli file `_src/_config/_*.php`
e ricava il custom da lì. Crea `_src/_config/_800.mio.php`, anche vuoto: è un gancio.

**«Ho modificato un file `_*` e all'aggiornamento è sparito tutto.»**
È il comportamento previsto. I `_*` sono standard e vengono sovrascritti. Usa un override custom.
(Eccezione: i due deploy upstream, §17.4.)

**«Ho messo la libreria custom in `src/lib/` e le funzioni standard non ci sono più.»**
Per le librerie il default è **replace**, non append. Se volevi aggiungere funzioni senza perdere
le altre, il file va chiamato `.add.php`.

**«Il form non salva e non dà errori.»**
Nove volte su dieci è il nome dei campi: devono essere `<tabella>[<colonna>]`. Un blocco che
inizia per `__` viene scartato da `checkNomeBloccoDati()`. E senza `<tabella>[__method__]` una
modifica arriva come POST, quindi come inserimento.

**«L'elenco è vuoto ma i dati ci sono.»**
Controlla che esista la vista `<tabella>_view` con la colonna `__label__`, e che le
`__restrict__` della macro non stiano filtrando tutto.

**«Ho messo un valore in `config.json` e in produzione fa la cosa sbagliata.»**
`config.json` viene deployato identico su tutti gli ambienti. Se il valore cambia per ambiente,
va sotto `profiles`. Se è un valore misurato sul database di un ambiente, non è configurazione:
va in `var/spool/`.

**«La pagina esiste ma il sito mostra un'altra cosa.»**
Se una pagina non ha `id_sito` compare su **tutti** i siti dell'installazione. E se due pagine
hanno lo stesso riferimento con lo stesso genitore, vince quella che il parser trova prima.

**«Il CSS aggiornato sul CDN non si vede.»**
Le risorse esterne vengono cachate su filesystem **senza TTL**. Cancella il file in
`var/cache/css/<host>/...` o usa una URL versionata.

**«Il login funziona in locale ma non in staging.»**
Il cookie di sessione è `cookie_secure=1`: richiede HTTPS. Su HTTP la sessione non si mantiene.

**«Ho salvato il session id in tabella e dopo il login la riga è orfana.»**
Al login interattivo l'id viene rigenerato. Tieni l'id dell'entità in `$_SESSION`, non il
contrario (§14.2).

**«Il cron non fa niente.»**
Verifica il lock: se un run precedente non è terminato, i successivi escono subito. Guarda
`var/log/latest/cron.latest.log`.
