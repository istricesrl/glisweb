# controllo di uptime dei siti

> **nota** — capitolo scritto il 2026-11-04 insieme al controllo di uptime, che ha preso il posto di Site24x7,
> non rinnovato. Le decisioni di partenza sono di Fabio, il coordinamento del capitano di web03.

Descrizione di come i server del cluster si accorgono che un sito glisweb è giù, e di chi avvisano.

introduzione
============
Ogni server del cluster ha un timer systemd che una volta al minuto lancia `_src/_sh/_uptime.check.sh` da un deploy
glisweb scelto da chi amministra il server. Il giro:

1. legge `/etc/glisweb/uptime.yaml`, la configurazione del cluster;
2. chiede agli altri server la loro **vista**: i siti che ospitano e lo stato che vedono;
3. raccoglie i siti glisweb di questo server e ci aggiunge quelli pubblicati dagli altri;
4. li controlla, quattro alla volta, e applica l'**isteresi**: un sito è giù per questo server al terzo fallimento
   consecutivo, e torna su al primo controllo riuscito;
5. decide col **consenso**: il sito è giù solo se lo vede giù anche un altro server. Se un altro server lo vede su,
   il problema è di questo server; se nessun altro risponde, il sito è giù ma **non confermato**;
6. scrive il registro e il `DOWNTIME.md`, e manda gli avvisi.

Non è un demone: un giro che si pianta non ne blocca altri, e systemd non lancia il successivo finché il precedente
non è finito. Il giro non fa il bootstrap del framework, quindi gira anche se il database del deploy da cui parte
è giù; quel deploy conviene comunque che sia aggiornato e stabile, non quello in cui si sviluppa il framework.

quali siti si controllano
=========================
Un deploy glisweb è una cartella `/var/www/<deploy>/dev` con `_src/_config.php`. I suoi siti sono gli host dei
virtual host HTTPS di Apache ( o nginx ) che hanno quella cartella come document root, col `ServerName`: gli alias
restano fuori. I domini dei profili di `src/config.json` non bastano, perché non sempre sono quelli serviti dal
server.

Su un deploy che ha `/status/uptime` si controlla quello, che deve rispondere 200 con `OK`; su uno non ancora
aggiornato si controlla la home, e vale come su qualunque risposta sotto il 500, perché la home di un gestionale
può essere un redirect al login o un 404.

`/status/uptime` fa il bootstrap e risponde `KO` con 503 se il deploy ha un database configurato e la connessione
non c'è. È pubblica e dice solo questo: niente versioni, percorsi o nomi di database.

configurazione di un sito
=========================
Un sito si personalizza con `etc/uptime/<host>.yaml` nel suo deploy, versionato. Il file sovrascrive i default
( `UPTIME_DEFAULT` in `_src/_lib/_uptime.tools.php` ) o aggiunge un sito che i virtual host non mostrano:

```yaml
url: https://www.esempio.it/status/uptime  # di default https://<host>/status/uptime
testo: OK                                   # il testo che la risposta deve contenere; null per nessuno
codice: 200                                 # il codice atteso; null per qualunque risposta sotto il 500
timeout: 10                                 # secondi oltre i quali il controllo fallisce
lento: 3                                    # secondi oltre i quali si avvisa noi, una volta al giorno
certificato: 14                             # giorni di validità sotto i quali si avvisa noi, una volta al giorno
soglia: 3                                   # fallimenti consecutivi per dire giù
attivo: false                               # toglie il sito dal controllo
avvisa:
  referente: [ "referente@esempio.it" ]
  abilitato: true                           # senza, il referente non riceve niente
  ritardo: 10                               # minuti di down confermato prima di avvisare il referente
```

Un file vuoto basta a dichiarare il sito con i default. Con `url:` e `testo:` si può dichiarare anche un sito che
non è glisweb.

configurazione del cluster
==========================
`/etc/glisweb/uptime.yaml` non è versionato, sta su ogni server e lo mantiene chi amministra il cluster. Lo legge
anche Apache, per `/status/uptime`, quindi va `root:www-data` con permessi `640`:

```yaml
server: web03                               # il nome di questo server
deploy: /var/www/<deploy>/dev               # il deploy da cui gira il timer: /status/uptime legge la vista da qui
token: "..."                                # condiviso fra i server: chi lo presenta vede i siti del server
cluster:                                    # dove chiedere la vista agli altri server
  web02: https://<un sito di web02>/status/uptime
  web03: https://<un sito di web03>/status/uptime
paralleli: 4                                # controlli contemporanei
smtp:
  host: localhost
  port: 25
  from: uptime@<dominio>
avvisa:
  noi: [ "noi@<dominio>" ]
```

L'elenco dei siti di un server contiene i nomi dei clienti: per questo la vista si dà solo a chi presenta il
token, nell'header `X-Glisweb-Uptime`.

avvisi
======
Gli avvisi partono via SMTP diretto con `sendMail()`, non dalla coda delle mail, che vive nel database di un sito:
proprio quello che potrebbe essere giù. Avvisa solo uno dei server che vedono giù il sito, il primo in ordine
alfabetico, così la mail non arriva doppia.

quando                                      | a chi
--------------------------------------------|---------------------------------------------
il sito è giù, confermato o non confermato  | noi
un down non confermato viene confermato     | noi
il down confermato dura da `ritardo` minuti | il referente, solo se `abilitato`
il sito torna su                            | chi era stato avvisato
risposta lenta o certificato in scadenza    | noi, una volta al giorno

registro e DOWNTIME.md
======================
Ogni server tiene nel deploy da cui gira:

- `var/uptime/stato.json`, la sua vista: i siti che ospita e, per ogni sito controllato, fallimenti, stato locale,
  stato deciso e ultimo esito. È quello che `/status/uptime` dà agli altri server;
- `var/uptime/registro.jsonl`, in sola aggiunta: un evento `inizio` e uno `fine` per ogni periodo di down, con
  durata, server che l'hanno visto e conferma.

Da quel registro il giro riscrive il `DOWNTIME.md` nella cartella del deploy del sito, se il deploy sta su questo
server: una riga per periodo, dal più recente. Il file è generato e non si modifica a mano; è uno dei file
canonici della cartella di progetto, e lo legge il capitano nel suo giro.

installazione e prove
=====================
Prima si scrive `/etc/glisweb/uptime.yaml`, poi si prova senza scrivere niente e senza avvisare, e si verifica che
le mail escano davvero dal server:

```
dev/_src/_sh/_uptime.check.sh --secco
dev/_src/_sh/_uptime.check.sh --prova-avviso
```

Infine si installa il timer, dal deploy scelto, e lo si controlla:

```
dev/_src/_sh/_uptime.install.sh install
systemctl list-timers glisweb-uptime.timer
journalctl -u glisweb-uptime.service --since today
```

Il giro scrive nel journal solo gli eventi e gli errori. Per togliere il timer: `_uptime.install.sh remove`.
