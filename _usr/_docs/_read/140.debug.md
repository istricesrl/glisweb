il sistema di log
=================
I log si scrivono con logger() ( _src/_config.php ), o con logWrite() che le inoltra il messaggio, in
`var/log/<canale>.<livello>.<anno e mese>.log`: il livello è nel nome del file, quindi un evento finisce nel
file della sua gravità. Si scrivono solo i messaggi di livello minore o uguale a LOG_CURRENT_LEVEL, che viene
da `debug.<stage>.log.lvl` ( _src/_config/_020.debug.php ); i default sono in _src/_config/_000.debug.php:

stage | livello | cosa si scrive
------|---------|---------------
DEV   | LOG_DEBUG   | tutto
TEST  | LOG_NOTICE  | fino agli eventi significativi
PROD  | LOG_WARNING | guasti e anomalie gestite ( fino al 21/10/2026 era LOG_ERR )

Il livello si sceglie per la gravità vera dell'evento, non per farlo comparire in produzione: i file `*.err`
e `*.crit` sono quelli che guardano i controlli dei deploy, e un evento normale scritto lì nasconde i guasti.

livello     | quando
------------|-------
LOG_EMERG, LOG_ALERT | il deploy intero è inservibile
LOG_CRIT    | un componente essenziale è giù ( sessione, database, un'estensione PHP necessaria ) o i dati sono a rischio ( una mail inviata e non copiata in mail_sent )
LOG_ERR     | un'operazione che doveva riuscire è fallita: un guasto, una configurazione mancante che blocca una funzione, un dato perso
LOG_WARNING | un'anomalia gestita: un errore dell'utente ( password errata ), una richiesta respinta da una regola ( controller before, antispam, coupon ), un dato in ingresso sbagliato, una funzione opzionale non configurata
LOG_NOTICE  | un evento normale ma significativo ( un consenso, che il suo registro lo ha nel database, un logout, una patch applicata )
LOG_INFO    | il flusso normale ( una cache mancante e ricostruita, un file importato, un pagamento riuscito )
LOG_DEBUG   | tracce e dump

Un registro con valore legale non si tiene nei log: i consensi stanno in anagrafica_consensi,
carrelli_consensi e consensi_contatti, e il log privacy ne è solo la traccia.


i log remoti
------------
I software che girano fuori dal deploy ( un agent sul PC di un cliente, un altro server, uno script ) possono
scrivere i loro log accanto a quelli del framework chiamando `/api/log` ( _src/_api/_log.php ), così li guardano
gli stessi controlli. Le righe finiscono in `var/log/remoti/<host>/<sorgente>[.<canale>].<livello>.<anno e mese>.log`,
dove `host` è il nome della macchina dichiarato dal mittente ( l'IP se manca o non è un nome valido ). Ogni sorgente
si dichiara nello shadow, col suo segreto:

```json
"debug": { "log": { "remoti": { "sorgenti": { "glisweb-agent": { "segreto": "<64 caratteri casuali>" } } } } }
```

e si chiama così, col segreto nell'header `gliswebLogKey`:

```json
{ "sorgente": "glisweb-agent", "host": "PC-MAGAZZINO",
  "righe": [ { "livello": "info", "data": "2026-10-26 18:00:00", "canale": "socket", "codifica": "base64", "messaggio": "..." } ] }
```

chiave | significato | default
-------|-------------|--------
`debug.log.remoti.sorgenti.<nome>.segreto` | segreto della sorgente; senza, la sorgente non esiste | —
`debug.log.remoti.sorgenti.<nome>.livello` | livello minimo scritto per la sorgente | `LOG_DEBUG`
`debug.log.remoti.limite.richieste` e `.finestra` | tetto per IP di rateLimitCheck() | 120 in 60 secondi
`debug.log.remoti.righe` | righe al massimo per richiesta | 100
`debug.log.remoti.dimensione` | byte oltre i quali un file del mese non cresce più | 52428800

Le righe remote **non passano dal filtro di LOG_CURRENT_LEVEL**, che è la verbosità del deploy e non del mittente:
per questo l'endpoint scrive con il formato di logger() ma non la chiama. Ogni messaggio è troncato a 4096 caratteri
e portato su una riga sola; i rifiuti ( segreto sbagliato, limite superato ) finiscono nel log `log.remoti` del
deploy.

**Chi manda testo libero lo codifica**, con `"codifica": "base64"`: il `messaggio` è allora la base64 del testo UTF-8,
e l'endpoint lo decodifica prima di portarlo su una riga e troncarlo. Dove c'è ModSecurity col Core Rule Set, un a
capo seguito da una parola, un percorso con `../`, frammenti di shell o di SQL — cioè proprio quello che c'è in una
traccia d'errore — vengono letti come un attacco e respinti con 403 **prima** di arrivare all'endpoint, e ogni 403 dà
punti all'IP del mittente nel firewall applicativo ( _src/_api/_security.403.php ). Senza `codifica` il messaggio si
scrive com'è; una codifica sconosciuta o una base64 non valida mandano la riga fra le scartate.

Le stesse sorgenti, con lo stesso segreto, valgono per `/api/aggiornamenti` ( _src/_api/_aggiornamenti.php ), da
cui un software esterno scarica le sue versioni nuove firmate: una sorgente è l'identità di un software.
