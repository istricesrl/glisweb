# la sicurezza del framework

Questo capitolo raccoglie le **schede delle vulnerabilita'** ( CVE ) che sono state valutate per il
framework o per il suo stack — PHP, Apache, MySQL, le librerie installate con Composer. Le schede
sono i capitoli di questa sezione, elencati in fondo alla pagina.

la regola
=========
Ogni CVE che si valuta ha la sua scheda, **aperta il giorno stesso della valutazione**, anche quando
l'esito e' che il framework non e' esposto: sapere che una vulnerabilita' e' gia' stata guardata, e
perche' non ci riguarda, vale quanto sapere come ci si e' protetti.

La scheda e' un file per CVE, col nome ufficiale della vulnerabilita':

percorso                                | contenuto
----------------------------------------|---------------------------------------------------
`_usr/_docs/_cve/CVE-AAAA-NNNNN.md`     | scheda dello standard: vale per ogni deploy
`usr/docs/cve/CVE-AAAA-NNNNN.md`        | scheda di progetto: un'esposizione o una protezione propria di un deploy

Un advisory che non ha un numero CVE si scheda col suo identificativo GitHub, `GHSA-xxxx-xxxx-xxxx.md`;
quando il CVE c'e' vince il CVE, e il GHSA si cita fra i riferimenti. Una scheda per advisory, anche
quando piu' advisory toccano la stessa libreria: ognuno ha il suo esito.

Le librerie Composer le sorveglia **Dependabot** sui repository del framework ( la scheda *Security*
di GitHub, o `gh api repos/istricesrl/<repo>/dependabot/alerts` ): ogni alert aperto e' un advisory
da valutare, e la valutazione finisce in una scheda come per ogni altra vulnerabilita'.

Vale la legge degli underscore come per il resto della documentazione: la scheda di progetto si
scrive solo se il deploy ha qualcosa di suo da dire, e finisce nel manuale di progetto, dietro
password.

⚠ **Le schede dello standard sono pubbliche**, come tutto il manuale sviluppatore dello standard.
Due conseguenze:

- la sezione *come si sfrutta* descrive il **meccanismo** della vulnerabilita' come lo descrivono gli
  advisory ufficiali, mai un exploit o i passi per riprodurlo;
- i dettagli dell'infrastruttura — quale server ha quale versione, cosa e' ancora scoperto e dove —
  non stanno nella scheda: stanno negli appunti di progetto del deploy che se ne occupa.

com'e' fatta una scheda
=======================
Le sezioni sono fisse e in quest'ordine, cosi' che le schede si leggano tutte allo stesso modo:

```markdown
# CVE-AAAA-NNNNN — <componente>: <cosa permette, in poche parole>

| | |
|---|---|
| componente | <PHP, Apache, una libreria con la sua versione…> |
| gravita' | <CVSS con la versione del punteggio e il vettore> |
| versioni affette | <…> |
| versioni corrette | <…> |
| pubblicata | <data> |
| valutata | <data> |
| esito | <esposto / non esposto / protetto da …> |

riferimenti ufficiali
=====================
NVD, advisory del produttore, changelog della versione corretta, elenchi come il KEV della CISA.

effetti
=======
Cosa ottiene chi la sfrutta, con quali privilegi, con quali precondizioni.

come si sfrutta
===============
Il meccanismo, come lo descrivono gli advisory: niente exploit, niente passi per riprodurlo.

esposizione del framework
=========================
Se il framework usa il componente o il percorso coinvolto, e in quale configurazione.

come ci siamo protetti
======================
Cosa e' cambiato nel framework, con l'hash del commit; oppure perche' non serviva cambiare niente,
e da quale versione dello stack dipende la protezione.

storia
======
- AAAA-MM-GG: prima valutazione
```

La scheda si aggiorna quando cambia lo stato — patch rilasciata, mitigazione tolta, migrazione fatta
— con una riga datata in fondo alla storia.
