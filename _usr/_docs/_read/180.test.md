# i test del framework

I test del framework girano con **Codeception** e sono divisi in tre suite:

suite      | cosa verifica                                                  | come
-----------|----------------------------------------------------------------|-------------------------------------
`unit`     | le librerie di `_src/_lib/`, attraverso gli esempi di `_usr/_examples/` | PhpBrowser, senza JavaScript
`backend`  | il gestionale: login, maschere, viste                          | Chromium headless via chromedriver
`frontend` | il sito come lo vede il visitatore: form, carrello, checkout   | Chromium headless via chromedriver

I test `backend` e `frontend` sono **funzionali**: aprono le pagine in un browser vero, compilano i form,
cliccano e poi controllano il risultato anche nel database. Per questo **scrivono nel database del deploy**, e
il bootstrap dei test si rifiuta di partire su un sito in produzione.

**Applicazione e test vanno sempre tenuti allineati**, nel framework come nei progetti: una funzionalità nuova
si consegna col suo test, una modifica aggiorna nello stesso lavoro i test che la riguardano, e una correzione
porta con sé il test che avrebbe intercettato il difetto. Codice e test si committano insieme.

dove stanno le cose
===================

percorso                                          | contenuto
--------------------------------------------------|-----------------------------------------------
`_usr/_test/codeception.yml`                      | configurazione di Codeception
`_usr/_test/_bootstrap.php`                       | avvia il framework da riga di comando per i test
`_usr/_test/_tests/<suite>.suite.yml`             | configurazione delle tre suite
`_usr/_test/_tests/<suite>/`                      | i test del framework, un `<nome>Cest.php` per file
`_usr/_test/_tests/_support/Helper/Glisweb.php`   | l'helper che collega i test al deploy
`_mod/_<modulo>/_usr/_test/_tests/<suite>/`       | i test di un modulo, eseguiti solo se il modulo e' attivo
`usr/test/tests/<suite>/`                         | i test del progetto ( custom )
`mod/<modulo>/usr/test/tests/<suite>/`            | i test custom di un modulo
`usr/test/tests/_support/Helper/`                 | gli helper del progetto
`var/test/`                                       | area di lavoro: test raccolti, output, log di chromedriver
`_usr/_examples/_lib/<nome.libreria>/`            | gli esempi che i test `unit` eseguono

come si lanciano
================
```sh
_src/_sh/_codeception.run.sh                       # suite unit
_src/_sh/_codeception.run.sh backend               # una suite
_src/_sh/_codeception.run.sh tutte                 # unit, backend e frontend una dopo l'altra
_src/_sh/_codeception.run.sh backend AN000.anagrafica/anagraficaFormCest.php              # un file
_src/_sh/_codeception.run.sh backend AN000.anagrafica/anagraficaFormCest.php:<metodo>     # un metodo
```

Le opzioni dopo la suite vanno a `codecept run`. Il percorso di un test singolo e' relativo alla cartella in
cui lo script lo raccoglie ( vedi sotto ): `framework/` per i test del framework, il nome del modulo senza
underscore per quelli di un modulo, `progetto/` per quelli solo del progetto.

Lanciato da root, lo script esegue i test come `www-data`, perche' i file che creano ( cache, log, spool ) devono
restare scrivibili dal sito. Per le suite col browser avvia `chromedriver` sulla porta 9515 e lo ferma alla
fine; il codice di uscita e' quello di Codeception, quindi si puo' mettere in catena con altro.

Servono sulla macchina `chromium` e `chromedriver`; nel deploy servono la connessione al database e
`auth.jwt.secret` nello shadow, perche' il login dei test passa dal token JWT.

come i test vengono raccolti
============================
I test non stanno in un posto solo, quindi prima di eseguirli lo script li raccoglie in `var/test/tests/` con
dei collegamenti simbolici, una cartella per origine:

- `var/test/tests/<suite>/framework/` da `_usr/_test/_tests/<suite>/`;
- `var/test/tests/<suite>/<modulo>/` da `_mod/_<modulo>/_usr/_test/_tests/<suite>/`, solo per i moduli attivi;
- `var/test/tests/<suite>/progetto/` da `usr/test/tests/<suite>/`.

Vale la legge degli underscore: un test custom con lo **stesso nome** di uno standard lo **sostituisce**
( `usr/test/tests/<suite>/` al posto di quelli del framework, `mod/<modulo>/usr/test/tests/<suite>/` al posto
di quelli del modulo ), uno senza corrispettivo si **aggiunge**. La stessa regola vale per i `<suite>.suite.yml`
e per il supporto: un progetto puo' mettere i propri helper in `usr/test/tests/_support/Helper/` e abilitarli
nella propria copia del `.suite.yml`.

l'helper `\Helper\Glisweb`
==========================
L'helper usa il framework avviato da `_usr/_test/_bootstrap.php` ( quindi `$cf`, il database e le librerie )
per preparare i dati, fare il login e ripulire. Si abilita nei `.suite.yml` **prima** di WebDriver.

metodo                                            | cosa fa
--------------------------------------------------|-----------------------------------------------
`$I->amLoggedInAs( '<gruppo>' )`                  | entra nel back-end con l'account `test-<gruppo>`
`$I->amOnPageId( '<id>' )`                        | apre una pagina per id, p.es. `anagrafica.form`
`$I->rifiutaCookie()`                             | chiude il banner dei cookie, che intercetta i click
`$I->clearGliswebCache()`                         | svuota la cache del sito
`$I->grabTestName( '<nome>' )`                    | un nome univoco col prefisso `TEST-E2E-`
`$I->deleteTestRecords( '<tabella>', '<campo>' )` | toglie i record col prefisso `TEST-E2E-`
`$I->haveInDatabase( '<tabella>', $riga )`        | scrive una riga e ne restituisce l'id
`$I->updateInDatabase( '<tabella>', $riga )`      | modifica la riga con l'id indicato in `$riga`
`$I->grabTestAnagrafica( '<gruppo>' )`            | l'id dell'anagrafica dell'operatore `test-<gruppo>`
`$I->grabFromDatabase( $query, $parametri )`      | il primo valore di una query
`$I->seeInDatabase()` / `dontSeeInDatabase()`     | verifica la presenza di una riga

Le regole che l'helper fa rispettare:

- **account**: all'inizio della suite crea un account `test-<gruppo>` per ogni gruppo della configurazione
  `gruppi` ( default `roots`; `[]` per non crearne ), con una password casuale diversa a ogni giro, e lo
  cancella alla fine; gli avanzi di un giro interrotto si tolgono anche all'inizio;
- **operatore**: con `anagrafica: true` ogni account di test ha un'anagrafica `test-<gruppo>` collegata, per le
  maschere che lavorano sull'operatore ( presenze, attivita', magazzino ); non porta il prefisso `TEST-E2E-`, quindi
  la pulizia dei record non la tocca, e se ne va con l'account;
- **dati di partenza**: quelli che servono al test ( articoli, documenti... ) si preparano con `haveInDatabase()` e
  vanno marcati `TEST-E2E-` come tutto il resto;
- **record**: quello che un test crea va marcato col prefisso `TEST-E2E-` in un campo di testo, e si toglie con
  `deleteTestRecords()` in `_before()` e in `_after()` del Cest, cosi' un giro interrotto non sporca il successivo;
- **pagine**: i percorsi si ricavano dai titoli e cambiano da un deploy all'altro, quindi nel back-end le pagine
  si aprono per id e non per URL.

il reCAPTCHA durante i test
===========================
Il reCAPTCHA v3 da' punteggio zero al browser headless, e i form protetti scarterebbero come spam quello che il
test invia. Per la durata della suite l'helper crea il file `var/test/recaptcha.off`, e
`_src/_config/_115.google.php` quando lo trova toglie la chiave privata: le verifiche lato server rispondono
"reCAPTCHA non configurato" e lasciano passare, mentre la pagina continua a generare il token con la chiave
pubblica ( e il test puo' verificare che arrivi ).

Il file vale **solo fuori produzione** e **per un'ora al massimo**, e si toglie alla fine della suite e comunque
all'uscita di `_codeception.run.sh`: un giro interrotto non lascia il sito senza protezione. Con
`recaptcha: true` nella configurazione dell'helper il reCAPTCHA resta attivo.

come si scrive un test
======================
Un test e' una classe `<nome>Cest` in un file con lo stesso nome; ogni metodo pubblico e' un test, e riceve
l'actor della suite ( `UnitTester`, `BackendTester`, `FrontendTester` ). I modelli da copiare sono:

- `_usr/_test/_tests/backend/loginCest.php` — il login e la dashboard;
- `_mod/_AN000.anagrafica/_usr/_test/_tests/backend/anagraficaFormCest.php` — una maschera di gestione: si apre,
  si compila, si salva, si verifica la riga nel database;
- `_mod/_CT000.contatti/_usr/_test/_tests/frontend/contattiCest.php` — un form del front-end col reCAPTCHA,
  verificato fino alla riga in `contatti`.

Il test di un modulo sta nel modulo, non nel framework: cosi' gira solo dove il modulo e' attivo.

i test delle librerie ( suite `unit` )
--------------------------------------
Il principio e' che un esempio e' insieme la documentazione di una funzione e il suo banco di prova: se
l'esempio smette di dare l'output che dava, il test lo dice. Per una libreria `_nome.libreria.php`:

- creare `_usr/_test/_tests/unit/nomeLibreriaCest.php`, con dentro una classe che si chiama come il file;
- per ogni test creare `_usr/_examples/_lib/_nome.libreria/_nomeFunzione.<n>.php`, scritto in modo che produca
  un **output controllato** — cioe' prevedibile e stabile;
- aggiungere alla classe un metodo per test che apre l'esempio e ne verifica l'output.

Il nome del file di esempio non e' libero: e' il contratto fra il test e l'esempio, ed e' anche il modo in cui
si trova l'esempio di una funzione partendo dal suo nome.

problemi frequenti
==================
- **il WAF banna la macchina stessa**: dietro un NAT ( p.es. Google Cloud ) i test chiamano il sito dall'IP
  pubblico del server, che non e' ne' `127.0.0.1` ne' `SERVER_ADDR`, e un giro di test fitto puo' farlo bannare. Si
  corregge una volta per macchina, non per deploy: una regola `iptables -t nat -A OUTPUT -d <IP pubblico>/32 -p tcp
  -m multiport --dports 80,443 -j DNAT --to-destination <IP interno>` fa arrivare le chiamate dall'IP interno, che e'
  `SERVER_ADDR` e non viene bandito; va salvata in `/etc/iptables/rules.v4`. Un bando gia' preso si toglie da
  `var/spool/security/ban/`;
- **il login dei test fallisce**: manca `auth.jwt.secret` nello shadow del deploy;
- **il login riesce ma la pagina e' negata**: l'helper fa il login da `/admin.it-IT.html`, la dashboard, che e'
  riservata allo staff; per i gruppi operativi la configurazione `login` del `.suite.yml` va puntata su una pagina
  che il gruppo puo' aprire ( p.es. `login: '/app.it-IT.html'` );
- **i risultati dei test falliti** ( screenshot e HTML della pagina ) stanno in `var/test/output/`, insieme al
  log di chromedriver.
