# come fare a pubblicare e distribuire il framework

> **nota** — capitolo nato il 2026-09-16 dallo smistamento della FAQ: erano domande che
> descrivevano una procedura, e una procedura si cerca per compito, non per domanda.

## quali sono le operazioni da svolgere per pubblicare una nuova release?
Le release seguono gitflow: `develop` è l'integrazione, `master` riceve solo le release, e ogni merge su
`master` porta un tag `X.Y.z`. La versione ( `_etc/_current.version` ) non si tocca mai a mano: la scrive
il git hook a ogni commit. Come si fa dipende dal livello della release.

**Release di livello patch** ( `X.Y.z` → `X.Y.z+1` ), dal repository del framework, con la copia di
lavoro su `develop`, pulita e allineata a `origin/develop`:

```bash
_src/_sh/_gw.release.sh          # dice quale release farebbe e da quale commit
_src/_sh/_gw.release.sh --si     # test, release branch, merge su master col tag, ritorno in develop, push
```

Lo script si ferma senza pubblicare niente se un test fallisce o se nel frattempo qualcuno ha spinto su
`develop` o su `master`. Lavora in un clone separato, perché checkout e merge nella copia di lavoro
romperebbero gli hard link con l'altro deploy del framework.

**Release minore o maggiore** ( `X.Y+1.0`, `X+1.0.0` ), a mano, sempre in un clone separato:

1. si parte da una release di livello patch appena fatta: la coda delle patch del database non deve
   contenere patch non testate;
2. si apre `release/X.Y.0` da `develop`;
3. si assorbono le patch datate di `_usr/_database/_patch/` nei file base `_0N0000999999.*.sql` e si
   tolgono dalla cartella;
4. si verifica con `_src/_sh/_database.rebuild.check.sh` che i file base da soli ricostruiscano lo
   schema di un database che aveva tutte le patch;
5. si scrive `_etc/_current.schema` con **due righe**: l'id dell'ultima patch assorbita, e il tag della
   release da cui si è partiti, che è il gradino da cui passeranno i database rimasti indietro;
6. si aggiorna `_etc/_current.release`, si fa il merge `--no-ff` su `master` col tag `X.Y.0` e su
   `develop`, e si pubblica.

Il perché di ogni passo è nel capitolo [il database del framework](300-database.html), sezione *il
canone e la coda delle patch*, e nel capitolo
[aggiornamento del framework](020-aggiornamento-disallineamenti.html), sezione *il database lungo gli
aggiornamenti*.

## come funziona la distribuzione del framework GlisWeb tramite container Docker?
Il framework è pubblicato su Docker Hub in due immagini, una per linea: `istricesrl/glisdev` (https://hub.docker.com/r/istricesrl/glisdev)
è la linea latest, `istricesrl/glisweb` (https://hub.docker.com/r/istricesrl/glisweb) la oldstable. Le costruisce `.github/workflows/container.yml`
in ciascuno dei due repository, a partire da `_usr/_deploy/_docker/_Dockerfile`: Debian bookworm, Apache e PHP 8.2 con le estensioni del
framework. A ogni push su `develop` l'immagine prende come tag la versione (il timestamp di `_etc/_current.version`) e `latest`. A ogni
release prende anche il tag `X.Y.Z`; le release precedenti al 05/11/2026 non hanno il Dockerfile e quindi nemmeno l'immagine. Chi vuole l'ultima versione del framework usa `istricesrl/glisdev:latest`, chi vuole una versione
fissa usa la release o il timestamp ( p.es. `istricesrl/glisdev:20261105221803` ).

L'immagine contiene il framework e nient'altro: non ci sono `src/`, `mod/` ed `etc/`, quindi nessun modulo è attivo e non c'è nessuna
configurazione. La configurazione si monta in `src/config/ext/`, che il bootstrap legge per prima. Per effettuare un test minimale è possibile
predisporre un piccolo file di configurazione e lanciare il container mappando la cartella in cui lo si è salvato. Si supponga ad esempio di
creare il seguente file YAML in una cartella chiamata ./conf/:

```
sites:
  1:
    __label__: "test Docker"
    name:
      it-IT: "test Docker"
    protocols:
      DEV: "http"
    hosts: 
      DEV: ""
    domains:
      DEV: "localhost"
```

A questo punto è possibile lanciare il container con:

```
docker run -dit -p 8080:80 -v ./conf/:/var/www/html/src/config/ext/ istricesrl/glisdev:latest
```

Aprendo un browser su http://localhost:8080/_src/_api/_status/_uptime.php si dovrebbe leggere `OK`, segno che il bootstrap del framework è
andato a buon fine. La home invece risponde con la pagina 404 del framework, ed è giusto così: le pagine le definisce il progetto, e
l'immagine del solo framework non ne ha.

Il report completo sullo stato del framework è su http://localhost:8080/status e vuole un utente con il privilegio `GESTIONE_SISTEMA`.
Senza database l'unico disponibile è `root`, che nasce disattivato: lo si attiva mettendo l'hash della sua password, generato con
`_src/_sh/_password.hash.sh` o con `docker run --rm istricesrl/glisdev:latest php -r 'echo password_hash( "<password>", PASSWORD_DEFAULT );'`,
in un `shadow.yaml` nella stessa cartella `./conf/`:

```
auth:
  accounts:
    root:
      password: "<hash>"
```

A quel punto `curl -u root:<password> http://localhost:8080/status` restituisce il report. Senza database e senza cron qualche
`[FAIL]` è normale, ma il report deve arrivare fino a `FINE REPORT`. Una password debole lo ferma, di proposito. Le password e gli altri segreti non vanno in `config.yaml`: si mettono in un `shadow.yaml` nella stessa cartella. I log di Apache
escono dal container (`docker logs <containerID>`), quelli del framework restano in `var/log/`. Per fermare il container in esecuzione
è necessario conoscerne l'ID:

```
docker container list
```

e successivamente fermarlo con:

```
docker container stop <containerID>
```

Per entrare in un container ed esplorare i file (utile per vedere i file di log) utilizzare:

```
docker exec -it <containerId> bash
```

## come si costruisce l'immagine Docker di un progetto?
L'immagine di un progetto parte da quella del framework e ci aggiunge le cartelle custom. Il suo Dockerfile, secondo la legge degli underscore,
sta in `usr/deploy/docker/Dockerfile`:

```
FROM istricesrl/glisweb:20261105220900
COPY ./src/ /var/www/html/src/
COPY ./mod/ /var/www/html/mod/
COPY ./etc/ /var/www/html/etc/
RUN /var/www/html/_src/_sh/_lamp.permissions.secure.sh
```

e si costruisce dalla document root con `docker build -t <progetto> -f usr/deploy/docker/Dockerfile .`. Conviene fissare la versione del
framework ( una release `X.Y.Z` o un timestamp ) invece di usare `latest`, così l'aggiornamento diventa una scelta e non succede a ogni build. Le password restano comunque fuori
dall'immagine: lo `shadow.yaml` si monta in `src/config/ext/` al momento del lancio, come nella FAQ precedente.

## come si fa girare il framework su Kubernetes?
Si usa l'immagine del framework, o quella del progetto, e si tiene presente che un pod può essere distrutto e ricreato in qualsiasi
momento, e che le repliche possono essere più di una:

- la **configurazione** va in una ConfigMap (`config.yaml`) e in un Secret (`shadow.yaml`), montati tutti e due in `src/config/ext/`;
- **`var/`** va su un PersistentVolumeClaim, perché contiene log, cache, spool, contenuti e immagini caricate. Con più repliche il
  volume dev'essere `ReadWriteMany`. Il pod deve girare con `fsGroup: 33` (il gruppo `www-data`), altrimenti Apache non scrive sul volume;
- le **sessioni** vanno su Redis appena le repliche sono più di una: il framework usa Redis da solo se trova `redis` configurato
  (`_src/_config/_050.session.php`);
- il **cron** non gira dentro il container: si usa un CronJob che ogni minuto chiama `/api/cron` del Service;
- per le **probe** di liveness e readiness si usa `/_src/_api/_status/_uptime.php`, che risponde `OK` senza login, e 503 se il
  database è configurato ma non risponde;
- il **dominio** con cui si raggiunge l'Ingress va dichiarato fra i `domains` del sito, perché il profilo (`DEV`, `TEST`, `PROD`) il
  framework lo ricava dall'host della richiesta. L'HTTPS lo termina l'Ingress, quindi nel container non va creato `etc/https`.
