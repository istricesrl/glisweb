# i file di /_src/_lib

> **nota** — capitolo travasato il 2026-09-16 dalla reference file per file che stava in
> `READ.md`, nella radice del framework. I percorsi sono stati verificati uno per uno contro
> l'albero: al travaso ne esistevano 639 su 640, e l'unico assente era un segnaposto.

Le librerie di funzioni, caricate per intero a ogni richiesta. Il nome dice il tipo: `tools` sono
utility che stanno in piedi da sole, `utils` dipendono da `$cf` e `$ct`.

Il caricamento lo fa `/_src/_config.php`, prima dei runlevel: raccoglie con `glob()` i file standard
`_src/_lib/_*.*.php` e quelli delle `_src/_lib/` dei moduli attivi, e per ciascuno cerca la controparte
custom con `path2custom()`. Se `src/lib/<nome>.php` esiste viene incluso **al posto** dello standard ( una
libreria dichiara funzioni, e le due versioni insieme andrebbero in conflitto ), mentre `src/lib/<nome>.add.php`
viene incluso **dopo** quello dei due che è stato caricato. **Solo ciò che ha una controparte standard si può
customizzare, ed è voluto**: un file in `src/lib/` ( o in `mod/<modulo>/src/lib/` ) senza il suo gemello
underscore non viene incluso mai, in silenzio. Per questo esistono file standard vuoti come
`/_src/_lib/_soap.tools.php`, che servono solo da gancio per una libreria di progetto.

Questa libreria contiene le funzioni di utilità per la gestione dei permessi degli utenti.

### /_src/_lib/_analytics.tools.php
Invio di eventi a Google Analytics lato server, tramite il Measurement Protocol di GA4
( `https://www.google-analytics.com/mp/collect` ) e `restCall()`. Le funzioni vive sono `ga4event()`, che spedisce un
evento qualsiasi, e `ga4purchase()`, che compone l'evento `purchase` da un carrello concluso e che il modulo e-commerce
chiama in `_checkout.finally.success.php` con `$cf['google']['profile']['analytics']['ua']` e
`['mp']['secret']`. Le funzioni `analytics*Hit()` e `analyticsPurchase()` parlavano a Universal Analytics, che Google ha
dismesso, e nessuno le chiama più.

### /_src/_lib/_ehiweb.tools.php
Invio di un SMS tramite il gateway HTTP di Ehiweb ( `https://secure.apisms.it/http/send_sms` ) con la sola
`ehiwebSend()`, che accetta anche un array di destinatari e li spedisce uno per uno. Credenziali, mittente e
`id_api` arrivano come parametri: li passa `_src/_api/_task/_sms.queue.send.php` ( e la sua copia in `_mod/_SM000.sms` )
prendendoli dal server SMS in `$cf['sms']['servers']` quando il suo `type` è `ehiweb`; come mittente il task passa il
nome, cioè la chiave dell'array `nome => numero` salvato in coda. Con un array di destinatari vuoto restituisce
`false`: fino al 2026-09-29 restituiva `NULL`, che il task leggeva come un invio riuscito. Ogni destinatario passa per
`string2smsNumber()` di `_src/_lib/_sms.tools.php` e va a Ehiweb in formato internazionale senza il `+`; un
destinatario senza cifre non parte e restituisce `false`. Fino al 2026-09-30 al numero si toglievano gli zeri iniziali
e si aggiungeva `39` solo se mancava, quindi i cellulari `39x` restavano senza prefisso e i fissi perdevano lo `0`.

### /_src/_lib/_emailable.utils.php
Verifica della recapitabilità degli indirizzi mail tramite le API di Emailable, sia uno per volta
( `emailableVerifyOne()`, chiamata da `_src/_api/_emailable.verifica.php` sul blur dei campi mail dei form ) sia in
blocco ( `emailableVerifyStart()` ed `emailableVerifyResult()`, per ora senza chiamanti nell'albero ). I verdetti
stanno in cache nella tabella `mail_status` ( `mailStatusRead()`, `mailStatusWrite()` ), e `mailStatusState()`
ricava lo stato di un verdetto letto dalla cache anche quando manca quello grezzo di Emailable: la usano
`_src/_api/_emailable.verifica.php` e `_src/_api/_emailable.scarti.php`. Legge `$cf['emailable']['profile']`
( `apikey`, `apikey_server`, `ttl`, runlevel 600/605 ) e lavora in *fail-open*: se il servizio non risponde
l'indirizzo passa, e si boccia solo uno stato `undeliverable`.

### /_src/_lib/_monetaweb.tools.php
Avvio di un pagamento MonetaWeb ( Nexi, protocollo XML ): `monetawebGetPaymentDetails()` chiede al gateway un
`paymentid` e l'URL della pagina di pagamento ospitata e restituisce `redirecturl`, a cui il riepilogo del carrello
manda l'utente; l'esito lo salva poi il listener. La chiamano `_carrello.riepilogo.php` e `_cassa.monetaweb.init.php`

riepilogo del carrello mostra l'errore `pagamento_non_disponibile` del dizionario invece del form. Il docblock riporta le carte di prova dell'ambiente di test.

### /_src/_lib/_mysql.tools.php
Questa libreria contiene le funzioni necessarie alla gestione del database MySQL. mysqlQuery() sceglie come eseguire
una query dalla sua prima parola, e un comando che non conosce lo scrive nel log e non lo esegue, senza errore
( `PREPARE`, `EXECUTE` e `DEALLOCATE` li riconosce dal 29/09/2026 ).

Contiene anche le funzioni delle patch del database, l'unica implementazione delle loro regole: le usano il task
`/_src/_api/_task/_mysql.patch.php`, `/_src/_sh/_mysql.upgrade.sh` e, tramite `/_src/_cli/_mysql.patch.php`,
`/_src/_sh/_database.rebuild.check.sh`. Non dipendono da nient'altro del framework, quindi gli script da riga di comando
le includono senza bootstrap.

Per le viste materializzate ( le tabelle `<tabella>_view_static` ) ci sono `refreshStaticView()`, che riscrive con
`REPLACE` le righe restituite dalla vista ( tutte, un id o un elenco di id ), e `cleanStaticView()`, che toglie dalla
statica le righe che non esistono più nella tabella: chi cancella in blocco chiama la seconda prima della prima. Tutte e
due non fanno niente se la statica non esiste sul deploy. La vecchia coda `refresh_view_statiche` e le procedure
`<tabella>_view_static()` non ci sono più ( patch `_202609302300` ).

- mysqlPatchFiles( $b ) restituisce i file `_*.*.sql` di `_usr/_database/_patch/` e di `usr/database/patch/` sotto la
  document root, con la sostituzione di glob2custom(), ordinati: prima lo standard, poi il progetto;
- mysqlPatchLevel( $c ) restituisce l'id più alto di `__patch__`, `000000000000` se la tabella manca o è vuota,
  false per ogni altro errore ( chi la chiama deve fermarsi: una connessione caduta non è un database vuoto );
- mysqlPatchRead( $f, $l, &$w ) restituisce le patch sopra il livello: un blocco per marcatore `-- |`, righe di
  commento scartate, id crescenti, `------------` uguale a `date( 'YmdHi' )`; l'SQL dopo l'ultimo marcatore, prima del
  primo o dopo un marcatore senza id numerico ( `-- | FINE` ) non si applica e va in `$w` con le patch non crescenti;
- mysqlPatchApply( $c, $p, &$e ) crea `__patch__` se manca ed esegue le patch una per volta con mysqli_query(),
  ciascuna come una query, registrandole; al primo errore si ferma e lo scrive in `$e`.

Le patch passano da mysqli e non da mysqlQuery() apposta: così un'istruzione che il server non conosce è un errore di
sintassi che ferma l'applicazione, e non un blocco saltato e registrato come fatto, che è quello che succedeva al task
fino al 29/09/2026.

### /_src/_lib/_skebby.tools.php
Invio di un SMS tramite le API REST di Skebby ( `https://api.skebby.it/API/v1.0/REST/` ) con la sola `skebbySend()`,
che si autentica, poi spedisce il messaggio del tipo indicato ( `TI` di default ). Credenziali e mittente arrivano
come parametri dal server SMS di `$cf['sms']['servers']` con `type` pari a `skebby`: la chiamano
`_src/_api/_task/_sms.queue.send.php` e la sua copia in `_mod/_SM000.sms`, passando il mittente nella forma
`nome => numero`, di cui la funzione usa il numero ( o il nome, se il numero è vuoto ). I destinatari possono essere
un array o un numero singolo; ciascuno passa per `string2smsNumber()` di `_src/_lib/_sms.tools.php`, che lo porta in
formato internazionale ( `+` e sole cifre ), e quelli senza cifre vengono scartati con un errore nel log `skebby`; se
non ne resta nessuno la funzione restituisce `false`. Fino al 2026-09-30 il numero veniva ridotto alle sole cifre e
riceveva `+39` se non cominciava già così, quindi `+39 333 ...` diventava `+39393...`.

### /_src/_lib/_sms.tools.php
Accodamento degli SMS: `queueSms()` scrive un messaggio nella tabella `sms_out`, compreso il server con cui inviarlo
( fino al 2026-09-29 il parametro `$server` veniva ignorato ), `queueSmsFromTemplate()` ci arriva
passando da un template Twig di `$cf['sms']['tpl']` ( la usa la registrazione di `_mod/_0350.registrazione` ) e con un
tipo di template non supportato non accoda niente e restituisce `NULL`,
`string2smsNumber()` porta un numero di telefono scritto come capita in formato internazionale per i provider ( un
numero che comincia con `+` o `00` è già internazionale, uno che è `39` seguito da 10 cifre ha già il prefisso
italiano, tutti gli altri sono italiani e ricevono `+39`; `false` se non ci sono cifre ),
`array2smsString()` scrive mittente e destinatari come testo ( "nome <numero>, numero" ) e `smsString2array()` fa
il contrario: le usano le viste di `_mod/_SM000.sms` e i suoi controller ( `_sms.out.before.php`, `_sms.out.after.php`
e gli stessi per `sms_sent` ), così nelle schede mittente e destinatari si leggono e si modificano come testo e nel
database restano serializzati. L'invio vero lo fa il task
`_sms.queue.send.php` con la funzione del provider ( `_src/_lib/_skebby.tools.php`, `_src/_lib/_ehiweb.tools.php` ):
una `smsSend()` generica non esiste di proposito. Dipende da `twig/twig` ( Composer ).

### /_src/_lib/_twig.tools.php
Contiene la sola `twigRenderText()`, che rende con Twig ( `twig/twig`, Composer ) un array di template, anche annidato,
sostituendo ogni template con il testo prodotto. La usano le stampe PDF di `_mod/_0400.documenti` e
`_mod/_2000.commerciale`.

### /_src/_lib/_txt.tools.php
Impaginazione di report in testo semplice a larghezza fissa: `txtHeader()`, `txtDateTimeLine()`, `txtTable()` e
`txtText()` compongono intestazione, righe, tabelle e paragrafi giustificati. La usano le API che rispondono in testo,
come `_src/_api/_status/_images.resize.status.php`, i report delle fatture passive e delle note attive di
`_mod/_0400.documenti` e `_progetti.todo.php` di `_mod/_1200.todo`. Non legge `$cf`.

### /_src/_lib/_variables.tools.php
Contiene la sola `swap()`, che scambia il contenuto di due variabili passate per riferimento. Nessun file del
framework o dei moduli la chiama.

### /_src/_lib/_xls.tools.php
Lettura e scrittura dei fogli Excel con PhpSpreadsheet ( `phpoffice/phpspreadsheet`, Composer ): `xls2csv()` converte il
foglio attivo in un CSV accanto al file, `array2xlsFile()` scrive un array in un `.xlsx`, `xlsDate2timestamp()` e
`xlsNumber2mysql()` normalizzano date e numeri letti dalle celle, `xlsIncrementCol()` sposta una lettera di colonna.
Oggi nessun file del framework o dei moduli la chiama.

### /_src/_lib/_xml.tools.php
Conversione fra XML e array ( `xml2array()`, `array2xml()` ), validazione e trasformazione ( `xmlValidate()`,
`xmlTransform()` ) e preparazione dei valori da scrivere ( `xmlEntities()`, `xmlFloat()` ). Le due funzioni del
2026-09-29 fanno cose diverse, e conviene non confonderle: `xmlValidate()` verifica un documento contro uno **schema
XSD**, cioè ne controlla la struttura ( elementi, ordine, valori ammessi ), restituisce true o false e raccoglie gli
errori di libxml; `xmlTransform()` applica un **foglio di stile XSL**, cioè trasforma il documento in un altro, di solito
una pagina HTML leggibile, e richiede l'estensione xsl di PHP. Un XSL non serve a validare. Gli schemi importati da un
URL assoluto `xmlValidate()` li cerca per nome nella cartella dello schema e poi in `DIR_SRC_XML_XSD`, per non andare in
rete. Le usa la stampa della fattura elettronica, `/_mod/_0400.documenti/_src/_api/_print/_fattura.xml.php`, che valida
ogni file prima di restituirlo e lo mostra in HTML trasformato sul server.

#### le librerie Python di /_src/_py/_lib

Le librerie di `_src/_py/_lib/` servono a un solo strumento, `_src/_py/_mysql.populate.py`, che popola il database
di un deploy con dati casuali verosimili per le demo e i collaudi ( anagrafiche, catalogo, documenti, progetti,
notizie, mailing ). Si lanciano quindi sempre attraverso di lui, dalla document root, per esempio
`_src/_py/_mysql.populate.py --elenco` o `_src/_py/_mysql.populate.py anagrafica --quantita 200 --secco`. Il nome segue
la convenzione del framework ( `tools` stanno in piedi da sole, `utils` dipendono dal contesto ) e non è un nome di
modulo Python valido: lo script le carica a mano e le registra come `_casuali_tools`, `_mysql_tools` e così via,
senza scrivere `__pycache__`. Non richiedono pacchetti esterni: niente driver MySQL e niente PyYAML.

### /_src/_py/_lib/_casuali.tools.py
Generatori di valori casuali ma coerenti: la classe `Casuali` produce nomi, denominazioni, date di nascita,
recapiti, indirizzi e testi, e le funzioni `calcola_codice_fiscale()`, `calcola_cin()` e `calcola_controllo_iban()`
fanno sì che codice fiscale, IBAN e partita IVA superino le validazioni delle interfacce. Non legge configurazione né
database.

### /_src/_py/_lib/_catalogo.tools.py
La classificazione delle tabelle in standard, assistite e gestite, allineata a `_usr/_docs/_read/300.database.md`:
`classifica()`, `scrivibile()` e `verifica_scrivibili()` decidono dove lo strumento può scrivere ( solo nelle
gestite ), `leggibile_per_lookup()` da dove può pescare valori, `vista_statica()` dà il nome della vista materializzata
di una tabella. Una tabella che non compare in nessuna lista è trattata come non scrivibile.

### /_src/_py/_lib/_config.tools.py
Legge la configurazione del deploy replicando l'ordine del bootstrap di `_src/_config.php` ( YAML poi JSON, `ext/` poi
`src/`, `config.*` poi `shadow.*` ) con `carica()`, e con `parametri_mysql()` ne estrae il server MySQL del profilo
richiesto ( `mysql/profiles/<DEV|TEST|PROD>/servers` e `mysql/servers` ). Per i file YAML chiede a PHP
( `yaml_parse()` ) invece di dipendere da PyYAML, e se non ci riesce lo dice.

### /_src/_py/_lib/_mysql.tools.py
Client MySQL minimale sopra il comando `mysql`, perché sulle macchine del framework non c'è un driver Python: la classe
`Mysql` offre `seleziona()`, `valore()` ed `esegui_script()`, e le funzioni `virgoletta()` e `inserimento()`
compongono l'SQL. La password non passa mai dalla riga di comando: va in un file temporaneo con permessi 600 letto con
`--defaults-extra-file`.

### /_src/_py/_lib/_ricette.utils.py
Le ricette di popolamento, una per entità: `genera_anagrafica()`, `genera_catalogo()`, `genera_documenti()`,
`genera_progetti()`, `genera_notizie()` e `genera_mailing()` costruiscono in memoria la riga principale con il suo
corredo, classificato come obbligatorio, consigliato o opzionale ( le opzioni `--con`, `--senza` e `--forza` dello
script ). È `utils` perché la classe `Contesto` legge dal database del deploy le tipologie, le categorie e i ruoli
esistenti.

### /_src/_py/_lib/_schema.tools.py
Introspezione di `information_schema` con la classe `Schema`: sapere quali colonne esistono davvero ( `filtra()` ),
assegnare gli id in memoria ( `prossimo_id()` ) per scrivere tutto in una transazione, ordinare gli inserimenti lungo
le chiavi esterne e pianificare lo svuotamento ( `piano_svuotamento()` ) e il rifacimento delle viste statiche
( `piano_viste_statiche()` ). Lo svuotamento è un `DELETE` mirato, non un `TRUNCATE`, e risparmia le righe a cui sono
agganciate tabelle protette come `account`.
