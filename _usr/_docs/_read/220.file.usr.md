# i file di /_usr/_config e /_usr/_deploy

I file di appoggio per mettere in piedi e distribuire un deploy: la configurazione di esempio di
Apache, i `.gitignore` di partenza, i file JSON da cui nasce `src/config.json` e la build di Phing.
Nessuno di questi file viene letto dal framework a runtime: li usano gli script di shell di
`_src/_sh/` al momento dell'installazione o dell'aggiornamento, oppure servono da modello da
copiare a mano.

### /_usr/_config/_apache2/default.http.conf
Un VirtualHost minimo sulla porta 80 con document root `/var/www/html/`, `AllowOverride All` ( senza
il quale il `.htaccess` del framework, che fa tutto il routing, non viene letto ) e i log nelle
posizioni di default di Debian. È un modello da copiare nella configurazione di Apache: nessuno
script lo usa.

> **nota** — usa ancora la sintassi `Order allow,deny` / `allow from all` di Apache 2.2, che su
> Apache 2.4 funziona solo con mod_access_compat; l'equivalente moderno è `Require all granted`.

#### i .gitignore di partenza

### /_usr/_config/_git/.gitignore.dev
Il `.gitignore` che `/_src/_sh/_git.init.sh` copia nella radice quando crea il repository di un
progetto: esclude le cartelle standard ( `_*/` ), `tmp/`, `var/`, i file di stato di `etc/` e gli
shadow di configurazione. Su un deploy aggiornato con `_gw.upgrade.sh` viene poi sostituito da
/_usr/_deploy/_git/.gitignore.

> **attenzione** — è rimasto indietro rispetto a /_usr/_deploy/_git/.gitignore e contiene pattern
> non ancorati molto larghi: `config.*` esclude anche `src/config.json` e `*.md` qualunque markdown
> a qualunque profondità, compresa la documentazione custom di `usr/docs/`.

### /_usr/_config/_git/.gitignore.gw
Una copia vecchia del `.gitignore` del repository del framework ( esclude `/etc`, `/mod`, `/src`,
`/usr`, cioè tutto il custom, e tiene solo le cartelle standard ). Nessuno script la usa, e il
`.gitignore` nella radice del framework nel frattempo è andato avanti per conto suo.

#### i file JSON di configurazione

Sotto `_usr/_config/_json/` ci sono tre famiglie di file, con tre usi diversi:

- gli **examples** ( `_examples/example.*.json` ) sono documenti JSON completi, uno per argomento,
  con valori finti o vuoti: mostrano la forma di un ramo di `$cx` e si copiano a mano dentro
  `src/config.json`. Nessuno script li legge;
- i **templates** ( `_templates/template.*.json` ) sono lo scheletro di un `src/config.json` intero,
  con dei segnaposto `%descrizione del valore%` al posto dei valori; li usa `/_src/_sh/_gw.config.sh`,
  che copia il template scelto in `src/config.json` e poi chiede a riga di comando un valore per ogni
  segnaposto, finché non ne restano;
- le **options** ( `_templates/_options/option.*.json` ) sono frammenti, cioè una sola chiave senza
  le graffe esterne, che `_gw.config.sh` propone uno per uno ( «vuoi attivare l'opzione ...» ) e
  inserisce al posto del segnaposto `%opzioni%` del template; i loro segnaposto vengono chiesti nello
  stesso giro.

In `_gw.config.sh` due segnaposto hanno un trattamento speciale: `%moduli%` diventa l'elenco dei
moduli di `_mod/` a cui si risponde di sì, e `%password di root%` viene salvato come md5; con
protocollo, host e dominio del sito lo script installa anche il crontab.

> **attenzione** — `_gw.config.sh` sostituisce i valori con `perl -pi -e "s/.../.../g"`: un valore
> che contiene `/` rompe la sostituzione, e uno che contiene `@` ( un utente SMTP, una password )
> viene interpolato da perl come array ed esce troncato. Il `src/config.json` prodotto va riletto.

### /_usr/_config/_json/_examples/example.analytics.json
Esempio del ramo `google.profiles.PROD.analytics`: l'ID di misurazione in `ua` ( per GA4 è il `G-...`
dello stream, che /_src/_lib/_analytics.tools.php legge da questa chiave ) e il flag `anonymous`.

### /_usr/_config/_json/_examples/example.casse.json
Esempio del ramo `casse.printer` ( `address` e `port` della stampante fiscale ), letto dal modulo
_6500.casse, ad esempio dal task di chiusura fiscale giornaliera.

### /_usr/_config/_json/_examples/example.mail.json
Esempio del ramo `mail`: un template `tpl.TEMPLATE_DI_PROVA` di tipo twig con mittente, oggetto, testo e
allegati per lingua, che si aggiunge ai template dichiarati in /_src/_config/_350.mail.php.

> **nota** — la chiave `postmaster` dell'esempio non è letta da nessuna parte del codice.

### /_usr/_config/_json/_examples/example.mapquest.json
Esempio del ramo `mapquest`: un server `default` con la sola `key` e i tre profili DEV, TEST e PROD che
lo usano; la chiave è quella che il task di geocodifica degli indirizzi legge da
`$cf['mapquest']['server']['key']`.

### /_usr/_config/_json/_examples/example.memcache.json
Esempio del ramo `memcache`: un server `default` su `127.0.0.1:11211` usato dai profili TEST e PROD.

### /_usr/_config/_json/_examples/example.mods.json
Esempio del ramo `mods.active.array`, l'elenco dei moduli attivi ( nome della cartella senza
underscore ). Se la chiave c'è, `_src/_config.php` usa questo elenco invece di ricavarlo dalle
cartelle presenti in `mod/`.

### /_usr/_config/_json/_examples/example.mysql.json
Esempio del ramo `mysql`: un server `default` con indirizzo, porta, utente, password e database, tutti
vuoti, collegato al profilo TEST.

### /_usr/_config/_json/_examples/example.pages.json
Esempio di una pagina dichiarata da configurazione sotto `contents.pages`, con titolo, h1, genitore,
template e voce nel menu principale; /_src/_config/_310.pages.php la unisce alle pagine lette dai file PHP.

### /_usr/_config/_json/_examples/example.privacy.json
Esempio del ramo `privacy` con i dati del titolare del trattamento e i rami vuoti `moduli` e `cookie`.

> **attenzione** — l'esempio mette il titolare in `privacy.titolare`, mentre il framework lo legge da
> `privacy.persone.titolare` ( /_src/_config/_060.privacy.php, e il controllo di stato in
> /_src/_api/_status/_framework.php ): copiato così com'è non ha effetto.

### /_usr/_config/_json/_examples/example.redis.json
Esempio del ramo `redis`: un server `localhost` su `127.0.0.1:6379` usato dai profili TEST e PROD.

### /_usr/_config/_json/_examples/example.root.json
Esempio del ramo `auth.accounts.root`, l'utente root definito da file di configurazione, che resta
utilizzabile anche quando il database non risponde. La password non si scrive in chiaro ma come hash:
passwordVerify() in /_src/_lib/_cryptography.tools.php accetta sia gli hash di password_hash() sia il
vecchio md5 di 32 caratteri, che è quello che produce `_gw.config.sh`.

### /_usr/_config/_json/_examples/example.site.json
Esempio del ramo `sites.1`: etichetta, nome per lingua, e per ogni status ( qui TEST e PROD ) la home,
il protocollo, l'host e il dominio con cui /_src/_config/_015.site.php riconosce il sito corrente.

### /_usr/_config/_json/_examples/example.slack.json
Esempio della configurazione Slack, sia generale ( `slack.profiles.DEV.webhooks.default` ) sia per sito
( `sites.1.slack` ): i tre pezzi `sa`, `sb` e `sc` sono i segmenti dell'URL del webhook con cui
slackTxtMsg() compone `https://hooks.slack.com/services/sa/sb/sc`.

> **nota** — il ramo per sito dell'esempio ha una forma ( `default-sito`, poi una chiave vuota ) che
> nel codice non trova riscontro; quello che i job dei moduli leggono è
> `$cf['slack']['profile']['webhooks']['default']`.

### /_usr/_config/_json/_examples/example.smtp.json
Esempio del ramo `smtp`: un server con indirizzo, porta, utente e password e i profili TEST e PROD che lo
usano ( vedi /_src/_config/_510.smtp.php ).

### /_usr/_config/_json/_examples/example.twig.json
Esempio del ramo `twig.profiles`: debug acceso e nessuna cache in DEV, debug spento e cache in
`var/cache/twig/` in TEST e PROD.

### /_usr/_config/_json/_templates/_options/option.cassa.json
Frammento opzionale con il ramo `casse.printer` ( indirizzo e porta della stampante fiscale ), da
attivare sui deploy che usano il modulo _6500.casse.

### /_usr/_config/_json/_templates/_options/option.memcache.json
Frammento opzionale con il ramo `memcache`: un server `default` e il profilo dello stage del sito che lo usa.

### /_usr/_config/_json/_templates/_options/option.redis.json
Frammento opzionale con il ramo `redis`: un server `default` e il profilo dello stage del sito che lo usa.

### /_usr/_config/_json/_templates/_options/option.smtp.json
Frammento opzionale con il ramo `smtp`: un server `default` con indirizzo, porta, utente e password e il
profilo dello stage del sito che lo usa.

### /_usr/_config/_json/_templates/template.base.json
Il template generico, per un solo stage scelto al momento ( `%stage del sito%` ): sito 1 con
protocollo, host e dominio, password di root, livelli di log e di report del debug, server e profilo
MySQL, profilo Twig con cache, le opzioni scelte e i moduli attivi. Si usa con
`_src/_sh/_gw.config.sh base`.

### /_usr/_config/_json/_templates/template.sviluppo.json
Come template.base.json ma con lo stage fisso a DEV, log al livello 7, report a 32767 e Twig in debug
senza cache: è la configurazione di una macchina di sviluppo.

### /_usr/_config/_json/_templates/template.test.json
Template per un deploy che vive in due stage, DEV e TEST: per ciascuno protocollo, host e dominio del
sito, un server MySQL proprio ( `develop` e `testing` ), livelli di debug e profilo Twig.

> **nota** — i segnaposto di host e dominio di questo template hanno nomi propri ( «in DEV», «in
> TEST» ), che `_gw.config.sh` non riconosce: al termine lo script non installa il crontab e dice di
> farlo a mano. Le options, poi, portano il segnaposto `%stage del sito%`, che qui viene chiesto a parte.

#### i file del deploy

### /_usr/_deploy/_git/.gitignore
Il `.gitignore` dei deploy di progetto, che `/_src/_sh/_gw.upgrade.sh` ricopia nella radice a ogni
aggiornamento se esiste un repository git. Esclude le cartelle standard, `tmp/`, `var/`, i file di stato
e i segreti di `etc/`, gli shadow di configurazione, i manuali generati sotto `usr/pages/`, gli hook e la
skill che lo zip del framework sovrascrive; i commenti nel file spiegano ogni scelta, in particolare quali
pattern sono ancorati alla radice e perché.

> **attenzione** — il file viene sovrascritto a ogni aggiornamento: una regola aggiunta a mano nel
> `.gitignore` di un deploy si perde al giro successivo.

### /_usr/_deploy/_phing/_build.xml
La build di Phing lanciata da `/_src/_sh/_phing.deploy.sh <destinazione>` con le proprietà di
`usr/deploy/phing/<destinazione>.properties` ( il modello è `_usr/_examples/_phing/build.properties` ).
Lo schema è `dist.<tipo>` → `dist.exec` → `dist.<strategia>` → `notify.<canale>`: il tipo ( Major, Minor,
Bugfix, o chiesto in modo interattivo ) incrementa `etc/version.conf`, `dist.exec` fa anche commit e push
del repository di progetto se c'è, la strategia è rsync locale o
remoto, FTP, scp o gcscp a seconda delle proprietà, e alla fine arrivano le notifiche su Slack e per mail.

> **attenzione** — Phing è deprecato ( vedi il capitolo sul deploy ): su un deploy nuovo si usa
> `_deploy.run.sh`. Il file richiama inoltre script esterni al framework ( `va.lamp.permission.fix.sh`,
> `va.mysql.db.export.schema.sh` ) e il target `mysql.diff` è commentato.
