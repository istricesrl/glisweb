# i file di /_src/_api

> **nota** — capitolo travasato il 2026-09-16 dalla reference file per file che stava in
> `READ.md`, nella radice del framework. I percorsi sono stati verificati uno per uno contro
> l'albero: al travaso ne esistevano 639 su 640, e l'unico assente era un segnaposto.

Gli entry point da HTTP: ogni richiesta che arriva al framework finisce in uno di questi file,
che fa il bootstrap e poi decide cosa produrre. Si leggono in coppia con `_src/_cli/`, che sono
gli entry point da riga di comando.

### /_src/_api/_bookmarks.php
Questa API si occupa di gestire la memorizzazione di elementi nello spazio di lavoro della sessione. Il meccanismo del "pin" di elementi in sessione
è molto comodo per portarsi dietro delle informazioni da una maschera all'altra, dove previsto dalla maschera stessa. Per ulteriori informazioni su
questo meccanismo si veda anche la documentazione dei file /_src/_config/_710.session.php e /_src/_config/_715.session.php, e dei file
/_src/_config/_770.bookmarks.php e /_src/_config/_775.bookmarks.php. Le viste e le maschere aggiungono e tolgono i
bookmark con i task `/task/bookmark.add` e `/task/bookmark.del`; questa API serve a leggere lo stato dello spazio di
lavoro.

### /_src/_api/_cron.php
Questa API si occupa di eseguire i task periodici; solitamente viene richiamata dal cron di sistema tramite un file appositamente creato nella cartella
/etc/cron.d/. La creazione di questo file può essere eseguita in maniera semi automatica tramite lo script /_src/_sh/_crontab.install.sh. La gestione
dei task periodici è piuttosto complessa, per ulteriori dettagli si veda la documentazione del file /_src/_api/_cron.php.

### /_src/_api/_download.php
Questo file si occupa di erogare i download, verificando che l'utente sia autorizzato a scaricare il file che sta richiedendo; riceve le richieste
dalle regole del file .htaccess e fatti i dovuti controlli restituisce il file richiesto. Agisce in pratica come un guardiano della cartella
/var che contiene ordinati in sottocartelle i file caricati tramite il CMS. Si noti che alcune sotto cartelle di /var (come /var/log) sono protette
e l'accesso è impedito da regole apposite all'inizio di /.htaccess.

### /_src/_api/_emailable.scarti.php
Endpoint pubblico ( `/api/emailable.scarti` ) che registra gli indirizzi scartati dalla validazione Emailable: lo
chiama in POST JSON lo snippet `_src/_twig/_inc/_emailable.close.twig` ( e il gemello legacy in `_src/_html/_inc/` )
quando una mail risulta `undeliverable`. Aggiunge IP e user agent e accoda una riga JSON nel file mensile
`var/spool/emailable/scarti/AAAAMM.jsonl`. Registra solo gli indirizzi che la cache `mail_status` dà come
`undeliverable` ( `mailStatusState()` ), prendendo stato, motivo e punteggio dalla cache e non dal browser; passa da
`rateLimitCheck()` sul canale `emailable.scarti` con lo stesso tetto della verifica ( `emailable.profiles.<PROFILO>.limite` )
e smette di scrivere quando il file del mese raggiunge `emailable.profiles.<PROFILO>.scarti.dimensione` byte
( default 10 MB ). Risponde `OK` se ha registrato lo scarto, altrimenti `KO` con 400, 429 o 507; lo snippet non legge
la risposta.

> **nota** — sui deploy senza la tabella `mail_status` gli scarti non si registrano. I file mensili non li pota
> nessuno, ma ciascuno ha la sua dimensione massima.

### /_src/_api/_emailable.verifica.php
Endpoint pubblico ( `/api/emailable.verifica` ) che verifica un indirizzo mail per conto dei form, chiamato in POST
JSON dallo stesso snippet sul blur del campo. Prima guarda la cache dei verdetti in `mail_status`
( `mailStatusRead()` ), altrimenti interroga Emailable con `emailableVerifyOne()` e scrive il verdetto con
`mailStatusWrite()`; le funzioni stanno in `_src/_lib/_emailable.utils.php`. È limitato per IP con `rateLimitCheck()`
( default 30 richieste all'ora, `emailable.profiles.<PROFILO>.limite` ) e risponde 400, 429 o 502 nei casi di errore,
che lo snippet legge come "non verificato" lasciando partire il form.

### /_src/_api/_ics.php
Genera al volo un file `.ics` con un solo evento a partire dai parametri GET `titolo`, `descrizione`, `luogo`, `inizio`
e `fine` ( obbligatori gli ultimi due, in un formato che `strtotime()` capisca ), e lo restituisce come download
`evento.ics` in UTC. Non include il framework e non tocca il database; nel repository non ho trovato chiamanti.

> **attenzione** — `UID` e `PRODID` contengono ancora dei segnaposto ( `@tuodominio.it`, `TuoProgetto` ), e il
> fuso è fissato a `Europe/Rome` nel file stesso.

### /_src/_api/_job.php
Questa API consente l'esecuzione dei job in foreground; per ulteriori informazioni si veda la documentazione del file stesso oltre a quella del
file /_src/_api/_cron.php.

### /_src/_api/_osm.php
Questa API funge da proxy per le tele OSM, in modo da non sovraccaricare i server OSM.

### /_src/_api/_pages.php
Questo file ha lo scopo di renderizzare e erogare le pagine. Svolge numerose funzioni ed è ampiamente documentato, quindi si rimanda al sorgente
per i dettagli. In sintesi, riceve le richieste di pagina in base alle regole del file /.htaccess e le soddisfa tramite le informazioni in suo
possesso.

### /_src/_api/_rest.php
Questa API fondamentale per il funzionamento del framework gestisce tutte le chiamate REST in entrata. Per maggiori dettagli si rimanda alla
lettura del codice dell'API stessa.

### /_src/_api/_upload.php
Questa API è la controparte dell'uploader Javascript creato da /_src/_js/_lib/_uploader.js e si occupa di ricevere i dati e salvarli su disco.
Per maggiori dettagli si rimanda al codice dell'API stessa e al codice di /_src/_js/_lib/_uploader.js.

### /_src/_api/_user.php
Questa API consente il login dell'utente, è utilizzata per le integrazioni e per il dialogo con app e altri sistemi esterni. Tramite il meccanismo di
login è possibile ottenere un'API key temporanea per fare più rapidamente le chiamate successive. Per ulteriori dettagli sul meccanismo di login
tramite API key si vedano i commenti a questo file e ai file dev/_src/_config/_210.auth.php e dev/_src/_config/_220.auth.php.

#### i job

I file di `_job/` sono lavori a step che avanzano una riga per iterazione: non si chiamano da soli, ma vengono
accodati come righe della tabella `job` ( di solito da un task, come `_anagrafica.importazione.start.php` ) e fatti
avanzare da `/_src/_api/_cron.php` in background o da `/_src/_api/_job.php` in foreground. Struttura, workspace e
modalità di chiamata sono descritti nel capitolo sull'esecuzione dei job, a cui si rimanda.

### /_src/_api/_job/_anagrafica.importazione.php
Job che importa le anagrafiche da un CSV, una riga per iterazione; lo accoda il task
`_src/_api/_task/_anagrafica.importazione.start.php` con il percorso del file nel workspace. Al primo giro legge il
file con `csvFile2array()` e parcheggia il dataset con `jobDatasetScrivi()` ( memcache, o un file di spool se la cache
lo rifiuta: `_src/_lib/_job.utils.php` ); poi per ogni riga scrive `anagrafica`, `indirizzi` e `anagrafica_indirizzi`,
categorie, mail, PEC, telefoni. Il tracciato di esempio è `_usr/_examples/_csv/anagrafica.import.csv`. Non gira in
standalone, e se il file manca o non è leggibile chiude subito il job invece di lasciarlo in coda.

### /_src/_api/_job/_comuni.importazione.php
Job che popola `regioni`, `provincie` e `comuni` dall'elenco ISTAT, una riga per iterazione; il dataset non lo legge
lui ma lo trova in memcache sotto la chiave scritta nel workspace da `_src/_api/_task/_comuni.importazione.start.php`.
Le righe vanno in `mysqlInsertRow()`, quindi aggiornano quelle esistenti; lo stato è inchiodato a `id_stato = 1`. Non
gira in standalone.

> **attenzione** — se la chiave memcache scade prima della fine del job, i giri successivi lavorano su un dataset
> vuoto senza segnalarlo.

### /_src/_api/_job/_test.job.php
Questo è un job di test.

### /_src/_api/_print/_anagrafica.csv.php
Esporta in CSV, nel formato di importazione di Mailchimp ( `Email Address`, `First Name`, `Last Name` ), le anagrafiche
di una categoria ( `__categoria__` ) o tutte; per ognuna prende la mail con `se_notifiche`, altrimenti la più recente.
È il `/print/anagrafica.csv` chiamato dalla modale `anagrafica.tools.modal.mailchimp.html` del template Athena legacy.
Ha una query sua e non passa da `controller()`, quindi è protetto da `checkTaskPrivilege( 'GESTIONE_ANAGRAFICA' )`.

### /_src/_api/_print/_default.csv.php
Questa stampa consente di stampare in CSV tutte le view del framework; è collegata al tasto "esporta in CSV" che si trova nelle view standard.

### /_src/_api/_print/_etichette.cartelle.sospese.pdf.php
Stampa in PDF ( TCPDF, A4 orizzontale ) una striscia di etichetta per ogni anagrafica, con il `__label__` di
`anagrafica_view`: quella indicata da `id`, oppure tutti i clienti ( `se_cliente = 1` ). I parametri `d`, `f` e `fi`
scelgono fra download, salvataggio su file e le due cose insieme. Richiede `GESTIONE_ANAGRAFICA`; nel repository non
ho trovato chiamanti.

### /_src/_api/_print/_indirizzario.csv.php
Esporta in CSV la rubrica degli indirizzi ( contatto, tipologia, indirizzo, civico, CAP, comune, provincia,
coordinate ) delle anagrafiche, filtrabile per categoria con `__categoria__`. È il `/print/indirizzario.csv` della
modale `anagrafica.tools.modal.indirizzi.html` del template Athena legacy; come `_anagrafica.csv.php` richiede
`GESTIONE_ANAGRAFICA`. Il file scaricato si chiama `esportazione contatti mail.csv`, per un copia e incolla dal gemello.

### /_src/_api/_report/_cookie.php
Questo report restituisce l'elenco di tutti i cookie presenti nel browser per il dominio corrente indicando se sono gestiti o meno dal
framework, il loro scopo e altre informazioni utili. Per accedere al report utilizzare il percorso /report/cookie.

### /_src/_api/_report/_import.php
Questo report innesca l'importazione dei file presenti in /var/spool/import/todo/*/ e /var/spool/import, e restituisce un report dettagliato delle
operazioni svolte. Normalmente l'importazione dei file è svolta dall'API cron, ma questo report può essere fondamentale per lo sviluppo, il test
e il debug dei nuovi tracciati di importazione. Per accedere al report utilizzare il percorso /report/import.

### /_src/_api/_report/_memcache.php
Questo report mostra il contenuto dell'indice di memcache.

### /_src/_api/_soap/_current.version.php
Server SOAP minimo con un'unica operazione, `getCurrentVersion`, che restituisce version e release del deploy lette
da `_etc/_current.version` e `_etc/_current.release`. Non include il framework e carica il WSDL
`_current.version.wsdl` dalla stessa cartella, con la cache WSDL spenta.

### /_src/_api/_soap/_current.version.wsdl
Descrizione WSDL del servizio `CurrentVersionService`: operazione `getCurrentVersion`, tipo `CurrentVersion` con i
due campi stringa `version` e `release`. L'indirizzo del servizio contiene il segnaposto `{{HTTP_HOST}}`, che
sostituisce `_current.version.wsdl.php`.

> **attenzione** — l'indirizzo dichiarato è `/api/current.version.soap`, ma nel `.htaccess` non c'è una regola che
> porti lì il server: `/api/<nome>` cerca `_src/_api/_<nome>.php`, che non esiste. Il server risponde solo al suo
> percorso diretto.

### /_src/_api/_soap/_current.version.wsdl.php
Serve il WSDL di `_current.version.wsdl` come `application/xml`, dopo aver sostituito `{{HTTP_HOST}}` con l'host
della richiesta. Non include il framework.

### /_src/_api/_status/_cf.php
Questa API di stato restituisce il contenuto, navigabile, dell'array $cf. Tutti i dati sensibili sono censurati tramite la funzione core array2censored()
per evitare problemi di sicurezza. Tramite una regola di /.htaccess l'accesso a questa API è possibile tramite l'URL speciale /cf.

### /_src/_api/_status/_framework.php
Questa API restituisce un report di auto diagnostica del framework, indicando lo stato corrente della piattaforma ed eventuali errori o warning. Si
tratta di un file piuttosto complesso, al cui sorgente si rimanda per approfondimenti. Una regola di /.htaccess rende disponibile questa API all'URL
speciale /status.

### /_src/_api/_status/_geo.php
Pagina HTML di consultazione della geografia caricata nel database, raggiungibile all'URL speciale `/geo`: quattro
colonne ( stati, regioni, province, comuni ) navigabili con i parametri `s`, `r`, `p` e `c`. Legge soltanto, ed è
utile per controllare l'esito di `_geografia.importazione.php` o del job dei comuni. Non verifica sessione né
privilegi.

### /_src/_api/_status/_images.resize.status.php
Report testuale della coda di ridimensionamento delle immagini: legge `__report_immagini_da_scalare__`, cioè le
stesse righe su cui lavora il task `_src/_api/_task/_images.resize.php`, e le stampa in tabella con gli strumenti di
`_src/_lib/_txt.tools.php`. Se la coda non scende, di solito il cron è fermo.

### /_src/_api/_status/_session.php
Questa API restituisce informazioni minimali sulla sessione corrente e viene interrogata in background dal template Athena (vedi il codice di
/_src/_tpl/_athena/src/js/main.js dove viene chiamata come /status/session).

### /_src/_api/_status/_session.status.php
Alias di `_session.php`, che include e basta: stessa risposta JSON su uso, durata e scadenza della sessione, stessi
header no-cache, e con `renew` la rinnova. Lo interroga come `/status/session.status` il template Athena legacy
( `_src/_templates/_athena/`, sia il controllo di `main.js` ogni minuto sia il pulsante di rinnovo di
`inc/header.html` ), mentre il template in `_src/_tpl/_athena/` usa `/status/session`; resta per le copie di Athena
legacy nei custom, che la chiamano ancora.

Nessuna delle due API è autenticata ( i runlevel si fermano a `055` ): per questo la risposta non contiene più
l'elenco dei file inclusi, che mostrava agli anonimi i moduli attivi e i file custom del server.

#### i task

Un task è un file di `_task/` che fa un lavoro breve e autonomo, spesso una sola riga di una coda per chiamata.
Si chiama in due modi: da web come `/task/<nome>` ( regola del `.htaccess` verso `_src/_api/_task/_<nome>.php` ), e in
quel caso `checkTaskPrivilege()` in cima al file controlla il privilegio e risponde 403 se manca; oppure da
`/_src/_api/_cron.php`, che lo include con `CRON_RUNNING` definita e senza controllare privilegi. Per il cron un task
va **registrato** come riga della tabella `task`: percorso del file, campi di pianificazione alla crontab ( `minuto`,
`ora`, `giorno_del_mese`, `mese`, `giorno_della_settimana`, `settimana`, NULL vale "ogni" ) e `iterazioni`, cioè quante
volte il file viene incluso a ogni giro. Lo schema standard non ha righe di default: quali task girino e con che
frequenza lo decide ogni deploy, e le indicazioni che seguono vengono dal codice di ciascun task. I task a coda
( mail, SMS, immagini, geocode ) quando non trovano niente assegnano `$iter` e interrompono le iterazioni residue; il
run si ferma comunque dopo `$cf['cron']['durata_massima']` secondi ( default 45 ). Struttura del file, lock di riga e
task che avviano un job sono descritti nel capitolo sull'esecuzione dei task; i log per task stanno in
`var/log/task/<id>.log` e `var/log/task/<id>/`.

`giorno_della_settimana` va da 1 ( lunedì ) a 7 ( domenica ), perché `_cron.php` lo confronta con `date( 'N' )`: la
domenica è 7 e non 0 come in crontab, e un task con 0 non parte mai. Ogni campo contiene un solo valore, senza
intervalli, liste né passi.

### /_src/_api/_task/_account.reset.password.php
Resetta la password dell'account indicato da `account`: ne genera una casuale, la salva con `passwordHash()` e mette
in coda con `queueMailFromTemplate()` la mail `NOTIFICA_RESET_PASSWORD` all'indirizzo dell'anagrafica collegata. La
chiama il pulsante del form account di Athena legacy ( `account.form.tools.resetta.password.html` ). Richiede
`GESTIONE_ACCOUNT`; non è pensato per il cron.

> **nota** — il commento parla di sedici caratteri "alfanumerici e speciali", ma `bin2hex()` produce sedici cifre
> esadecimali.

### /_src/_api/_task/_anagrafica.attivazione.archivium.php
Invia un'anagrafica ( `id` ) ad Archivium chiamando `archiviumPostInsertAzienda()` di `_src/_lib/_archivium.utils.php`,
solo se l'account in sessione ha il privilegio `INVIO_ANAGRAFICA_ARCHIVIUM`. Lo lancia il pulsante nei tools del form
anagrafica dei moduli anagrafica. Legge la sessione, quindi da cron non fa niente di utile.

### /_src/_api/_task/_anagrafica.creazione.account.php
Crea un account per un'anagrafica: riceve `anagrafica`, l'id della mail ( `__e__` ), il profilo ( `__p__` ) e la
password ( `__psw__` ), scrive `account` con la mail come username, lo associa ai gruppi del profilo
( `$cf['auth']['profili'][...]['gruppi']` ) e mette in coda la mail di benvenuto con il template della chiave `mail`
del profilo, o `NOTIFICA_NUOVO_ACCOUNT` se manca. La chiama in POST `anagrafica.form.tools.crea.account.html` di
Athena legacy. La password si legge solo da `$_POST`: se arriva in querystring il task risponde con un errore e non
crea l'account; se non c'è se ne genera una come in `_account.reset.password.php`, e la mail di benvenuto la
comunica. Risponde con `__status__` e, sulla password in querystring, sui parametri mancanti o sul profilo
inesistente, con i messaggi in `err`. Richiede `GESTIONE_ACCOUNT`; non è per il
cron.

### /_src/_api/_task/_anagrafica.deduplica.php
Unisce anagrafiche duplicate con `unisciAnagrafiche()` ( `_src/_lib/_mysql.utils.php` ). Chiamato con `src` e `dst`
fonde le due indicate ( è il caso della modale `anagrafica.tools.modal.deduplica.html` ); senza parametri, com'è da
cron, prende l'anagrafica aggiornata meno di recente che ha un doppione per codice fiscale o partita IVA, ci fonde
dentro tutti i doppioni e le aggiorna `timestamp_aggiornamento`, così il giro successivo passa a un'altra. Richiede
`GESTIONE_ANAGRAFICA`.

> **attenzione** — da cron la fusione è automatica e irreversibile: va pianificato solo dove i doppioni per CF o
> P.IVA sono davvero la stessa entità.

### /_src/_api/_task/_anagrafica.importazione.start.php
Accoda in `job` l'importazione di un CSV di anagrafiche, con il job `_src/_api/_job/_anagrafica.importazione.php`,
30 iterazioni per giro e in background ( `se_foreground` NULL ), sul file `var/contenuti/upload/<file>` ( default
`anagrafica.csv` ). Lo chiama la modale di importazione di Athena legacy ( `/task/anagrafica.importazione.start` );
richiede `GESTIONE_IMPORT`. È il caso tipico del task che avvia un job ( vedi il capitolo sull'esecuzione dei task ).

### /_src/_api/_task/_anagrafica.indirizzi.normalizzazione.php
Normalizza un indirizzo per giro fra quelli scritti a mano in `anagrafica_indirizzi.indirizzo`, nel formato
`indirizzo | civico | località | cap | comune | [provincia |] stato`: cerca stato, provincia e comune, scarta la riga
se l'anagrafica ha già lo stesso indirizzo, altrimenti crea la riga in `indirizzi` e la associa ( come sede, se
l'anagrafica non ne ha ). Aggiorna poi `anagrafica_view_static` con `updateAnagraficaViewStaticIndirizzi()`, che sta
nei moduli anagrafica. Pensato per il cron; richiede `GESTIONE_ANAGRAFICA` da web.

> **attenzione** — quando la provincia è indicata, il parametro viene aggiunto con `array_merge()` invece che come
> elemento, e la query dei comuni riceve un parametro malformato.

### /_src/_api/_task/_anagrafica.view.static.popolazione.php
Aggiorna una riga di `anagrafica_view_static` per giro: quella dell'anagrafica ( o di una sua categoria ) modificata
dopo l'ultima scrittura della statica, oppure quella forzata con `idAnagrafica`. Il lavoro lo fa
`updateAnagraficaViewStatic()`, che è definita nei moduli anagrafica ( `_0010.anagrafica`, `_AN000.anagrafica` ):
senza uno dei due il task non funziona. È pensato per girare dal cron con molte iterazioni. Richiede `GESTIONE_MYSQL`.

### /_src/_api/_task/_anagrafica.view.static.pulizia.php
Toglie da `anagrafica_view_static` le righe di anagrafiche che non esistono più, con `cleanAnagraficaViewStatic()`
dei moduli anagrafica. Complemento di `_anagrafica.view.static.popolazione.php`, adatto a un giro poco frequente.
Richiede `GESTIONE_MYSQL`.

### /_src/_api/_task/_anagrafica.view.static.svuotamento.php
Svuota del tutto `anagrafica_view_static` con `emptyAnagraficaViewStatic()`, così che il task di popolazione la
ricostruisca da capo. È un'operazione manuale, non da cron. Richiede `GESTIONE_MYSQL`.

### /_src/_api/_task/_bookmark.add.php
Endpoint dei segnalibri di sessione, chiamato come `/task/bookmark.add?__work__[...]` dai pulsanti "metti fra i
segnalibri" dei form e delle viste. Il file in sé si limita a restituire `$_SESSION['__work__']`: l'aggiunta la fa il
bootstrap, cioè `_src/_config/_775.bookmarks.php`, che fonde in sessione il `__work__` della richiesta. Basta una
sessione autenticata.

### /_src/_api/_task/_bookmark.del.php
Toglie dai segnalibri di sessione l'elemento `__item__` del gruppo `__key__` e restituisce `$_SESSION['__work__']`
aggiornato. Lo usano per esempio le viste dei corsi. Basta una sessione autenticata.

### /_src/_api/_task/_comuni.importazione.start.php
Scarica da ISTAT l'elenco dei comuni in XLS ( `tmp/comuni.xls` ), lo legge con PhpSpreadsheet, tiene le colonne che
servono ( codici ISTAT, nomi, sigla, codice catastale ), mette il dataset in memcache e accoda in `job` il job
`_src/_api/_job/_comuni.importazione.php` in foreground. Senza memcache si ferma con una riga di log. Richiede
`GESTIONE_IMPORT`; il tracciato è citato anche da `_src/_cli/_geografia.build.php`.

### /_src/_api/_task/_creazione.pianificazione.php
Calcola le date di una ripetizione con `creazionePianificazione()` di `_src/_lib/_cron.utils.php` a partire da
`__data__`, periodicità ( `__p__` ), cadenza, data di fine, numero di ripetizioni e giorni della settimana, e le
restituisce in JSON. Non scrive niente nel database: serve all'interfaccia per mostrare le date prima di crearle.
Richiede `GESTIONE_SISTEMA`.

### /_src/_api/_task/_cron.queue.check.php
Sblocca le code del cron: dà una `timestamp_esecuzione` ai job che non l'hanno, toglie il token ai job fermi da più
di dieci minuti e riporta in background i job in foreground abbandonati. Le stesse tre operazioni oggi le fa già
`_src/_api/_cron.php` a ogni giro, quindi il task serve soprattutto a lanciarle a mano. Richiede `GESTIONE_SISTEMA`.

> **attenzione** — sblocca anche una tabella `cron` che nello schema standard non esiste: quella query fallisce in
> silenzio.

### /_src/_api/_task/_database.frammentazione.check.php
Controllo periodico dello spazio sprecato dalle tabelle InnoDB: interroga `information_schema` e scrive nel log
`mysql` le tabelle oltre entrambe le soglie ( default 50 MB e 25% del file, regolabili in
`$cf['database']['frammentazione']` ). Non recupera niente di proposito: il recupero si fa a mano con
`_src/_sh/_database.optimize.sh`. Adatto al cron con frequenza bassa, per esempio giornaliera; il docblock del file
spiega il perché delle due soglie. Richiede `GESTIONE_SISTEMA`.

### /_src/_api/_task/_mail.queue.send.php
Spedisce una mail per giro dalla coda `mail_out`, con `sendMail()` di `_src/_lib/_mail.tools.php`, il server SMTP
della riga o quello di default e la firma DKIM se configurata per il dominio del mittente. Se va a buon fine sposta la
riga in `mail_sent` ( e aggiorna `mailing_mail` se il modulo mailing è attivo ), altrimenti la rimanda di tante ore
quanti sono i tentativi, fino a `$cf['mail']['tentativi_massimi']` tentativi falliti ( default 10, runlevel
`_350.mail.php`; 0 toglie il limite ): lì la riga resta in `mail_out` ferma con il token dedicato `TROPPI_TENTATIVI`, e
l'errore va nel log `mail` a livello LOG_ERR. Parametri: `id` per una mail precisa ( solo se la riga non è già
marcata da un altro processo; una mail ferma per troppi tentativi riparte, con i tentativi azzerati: è l'invio forzato
dalla scheda della mail in uscita ), `hard` per ignorare l'orario di invio, `full` per rimettere in circolo tutta la
coda: azzera la data prevista di tutte le righe tranne quelle ferme per troppi tentativi e **non invia nulla**, la coda
la riprende il cron dal giro successivo, e la risposta dice quante date ha azzerato ( `rimesse` ), quante righe ha
sbloccato ( `sbloccate` ) e quante restano ferme per troppi tentativi ( `ferme` ). Un server
nominato nella riga ma assente dalla configurazione, o un profilo senza server SMTP, sono un errore di invio: la mail
resta in coda e l'errore va nel log `mail`. Se la mail parte ma la copia in `mail_sent` fallisce, la riga non viene
cancellata né rimessa in coda: resta in `mail_out` marcata dal token dedicato `COPIA_FALLITA`, fuori da tutte le
modalità di evasione e dallo sblocco, e l'errore va nel log a livello critico; va sistemata a mano. Dopo la copia i
file della mail passano da `file.id_mail_out` a `file.id_mail_sent`, prima che la cancellazione da `mail_out` li
stacchi. È il task di riferimento del capitolo sull'esecuzione dei task, pensato per il cron ogni minuto con più
iterazioni. Richiede `GESTIONE_COMUNICAZIONI`. Il modulo `MA000.mail` ne ha una copia identica, come `SM000.sms` per
gli SMS: le due vanno tenute uguali.

Il task marca la riga scrivendo insieme il token e l'ora in `mail_out.timestamp_elaborazione`, e all'inizio di ogni
giro, in tutte le modalità, toglie il token alle righe marcate da più di `$cf['mail']['minuti_sblocco']` minuti
( default 60, runlevel `_350.mail.php`, sovrascrivibile da `src/config.json` ): sono le righe di un giro morto a metà,
che altrimenti nessuna modalità prenderebbe più. È lo stesso recupero che `_cron.php` fa su task, job e
pianificazioni; una mail sbloccata così può partire due volte, se il processo era morto dopo averla consegnata al
server SMTP. Lo sblocco non tocca le righe con il token `COPIA_FALLITA` né quelle con `TROPPI_TENTATIVI`.

Il limite di tentativi c'era già nel primo disegno del task, del 2020 ( "se i tentativi sono più di 5, notificare il
mittente e spostarla in `mail_unsent`" ), ma non era mai stato scritto: fino al 2026-09-30 una mail che falliva sempre
veniva riprovata all'infinito. `full` non rimette in circolo le mail ferme perché una mail che ha fallito tante volte
di fila ha di solito un problema che il tempo non risolve; nella scheda il titolo ( la `__label__` di `mail_out_view` )
dice che la mail è ferma e dopo quanti tentativi.

Fino al 2026-09-30 una riga di un giro morto a metà restava bloccata per sempre, `full` rispondeva "nessuna mail da
evadere" come se non avesse fatto niente, e i file della mail inviata andavano persi: la cancellazione da `mail_out`
azzerava `file.id_mail_out` e nessuno aveva scritto `file.id_mail_sent`.

Fino al 2026-09-29 il task cancellava la riga da `mail_out` senza controllare l'esito della copia in `mail_sent`, e
una copia fallita faceva sparire la mail; la modalità `id` marcava anche una riga già presa da un altro processo, e un
server nominato ma non configurato arrivava a `sendMail()` senza indirizzo.

### /_src/_api/_task/_mysql.patch.php
Questo task si occupa di installare e aggiornare il database MySQL del deploy corrente. La logica di aggiornamento del database è piuttosto complessa ma
funzionale allo scopo di tenere aggiornati tutti i database di tutti i deploy senza dover eseguire le query a mano. Le componenti del sistema sono:

- l'API /_src/_api/_task/_mysql.patch.php
- le funzioni `mysqlPatch…()` di /_src/_lib/_mysql.tools.php, che leggono e applicano le patch
- i file di patch presenti in /_usr/_database/_patch ( e in usr/database/patch per le patch del progetto )

Il task non contiene le regole delle patch: legge il livello con mysqlPatchLevel(), ricava le patch da applicare con
mysqlPatchFiles() e mysqlPatchRead() e le esegue con mysqlPatchApply(), le stesse funzioni che usano
`_src/_sh/_mysql.upgrade.sh` e `_src/_sh/_database.rebuild.check.sh`. Ogni blocco fra due marcatori `-- |` va al server
come una query, con mysqli e non con mysqlQuery(); la patch si registra in `__patch__` e al primo errore il task si
ferma, stampa la query e l'errore e non applica le patch successive. Stampa anche le segnalazioni della lettura ( SQL
dopo l'ultimo marcatore o fuori da una patch, id non crescenti ), che finiscono pure nel log `mysql`. Se non riesce a
leggere il livello di patch per un errore diverso da "tabella `__patch__` inesistente" non applica niente.
Negli errori ( livello illeggibile, patch fallita, connessione assente ) risponde HTTP 500, così un cron o un monitor che
guardano solo il codice se ne accorgono; per poterlo fare dopo aver già scritto le patch applicate trattiene l'uscita
con ob_start(). Fino al 01/10/2026 rispondeva sempre 200, con l'errore solo nel testo. Le regole
sono descritte nel capitolo 300, sezione «aggiornamento del database e patch», e nei docblock delle funzioni;
l'introduzione del task spiega la numerazione.

Fino al 29/09/2026 il task leggeva ed eseguiva da sé passando da mysqlQuery(): un blocco che cominciava con un comando
che mysqlQuery() non conosceva ( fino a quel giorno `PREPARE`, `EXECUTE` e `DEALLOCATE` ) non veniva eseguito, senza
errore, e il task lo registrava come applicato; l'id `------------` diventava `date( 'YmdHis' )`, quattordici
caratteri in una colonna `char(12)`, e l'SQL dopo l'ultimo marcatore si perdeva in silenzio.
