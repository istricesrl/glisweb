# i template del framework

> **nota** — capitolo travasato il 2026-09-16 da `_usr/_docs/_dox/_templates.dox`, fermo al 2024.
> Il testo e' stato riverificato contro il codice di oggi: dove il `.dox` descriveva la linea
> vecchia ( `_src/_templates/`, file `.html`, `etc/template.conf` ) la descrizione e' stata
> riportata alla linea nuova ( `_src/_tpl/`, file `.twig`, `etc/template.yaml` ), e le differenze
> sono segnalate dove contano.

Come e' fatto un template, quali file deve avere e come si configura. Le **macro** che i template
usano per rendere i contenuti hanno un capitolo loro, [le librerie dei template](154-librerie-template.html);
la **collocazione** dei template nell'albero del framework sta in [le cartelle del framework](030-cartelle.html);
il singolo template standard ha la sua documentazione nel template stesso, ed e' elencata in fondo
a questo capitolo.

struttura e funzione dei template
=================================
I template sono lo strumento con cui il framework rende i contenuti delle pagine. Il template
manager e' **Twig** ( https://twig.symfony.com/doc/3.x/ ): `template.type` non ammette altri valori.

Ogni template e' composto da una o piu' **basi** nella sottocartella `ext/`, estese dagli **schemi**
che stanno nella radice del template. Per convenzione la base principale si chiama `ext/main.twig`,
mentre gli schemi prendono il nome dalla pagina per cui sono pensati, tranne due che il framework
da' per scontati:

schema                    | ruolo
--------------------------|---------------------------------------------------------------------
`default.twig`            | lo schema usato quando la pagina non ne specifica uno
`login.twig`              | lo schema usato quando l'utente non ha i permessi per accedere

I due nomi non sono cablati: `template.default` e `template.login` in `etc/template.yaml` dicono
quali file usare, e i valori di cui sopra sono i default di fatto di tutti i template standard.

struttura minima
----------------
I file indispensabili sono pochi:

file                        | descrizione
----------------------------|-------------------------------------------------------------------
`etc/template.yaml`         | configurazione del template — **l'unico obbligatorio**
`ext/main.twig`             | base del template
`default.twig`              | schema di default
`login.twig`                | schema della pagina di login
`css/main.css`              | foglio di stile principale

> **attenzione** — senza un file di configurazione il framework **non degrada**: logga a `LOG_CRIT`
> e interrompe la richiesta con `file di configurazione del template ... danneggiato o mancante`
> ( `_src/_api/_pages.php` ). E' il solo file la cui assenza ferma la pagina.

Il template `_src/_tpl/_aurora/` e' il riferimento da leggere per primo: e' pensato come template
scuola e come base per svilupparne di piu' complessi. Gli esempi di questo capitolo vengono da li'.

le cartelle di un template
--------------------------
Come il resto del framework, anche il template ha una struttura di cartelle fissa, che consente di
capire al volo il ruolo di un file:

cartella                  | descrizione
--------------------------|---------------------------------------------------------------------
`css/`                    | fogli di stile del template
`css/themes/`             | fogli di stile dei temi
`etc/`                    | configurazione del template
`ext/`                    | basi Twig, che gli schemi estendono
`img/`                    | elementi grafici
`img/favicons/`           | le favicon ( vedi sotto )
`inc/`                    | schemi aggiuntivi, quelli che vengono **inclusi**
`js/`                     | JavaScript del template
`lib/`                    | macro Twig del template, quelle che vengono **importate**

A parte `etc/`, tutte le altre sono opzionali e si creano alla bisogna. La differenza fra `lib/` e
`inc/` e' quella fra importare e includere: nella prima stanno le librerie di macro, nella seconda
i pezzi di schema.

> **nota** — `lib/` si chiamava `bin/` nella linea vecchia, e `js/` stava in `src/js/`. Fra i
> template standard `_minerva` usa ancora `bin/` e `src/`: e' l'unico rimasto, e non e' un errore
> ma una migrazione non finita.

il file etc/template.yaml
=========================
Contiene le informazioni essenziali del template. Il formato e' YAML; la linea vecchia usava un
file INI chiamato `etc/template.conf` con le stesse chiavi.

> **attenzione** — se in `etc/` esistono **tutti e due** i file, vince `template.conf`: il
> framework prova prima l'INI e passa allo YAML solo se l'INI non c'e' ( `_src/_api/_pages.php` ).
> Un `template.yaml` che sembra ignorato quasi sempre e' questo.

chiave                    | descrizione
--------------------------|---------------------------------------------------------------------
`template.type`           | il template manager: solo `twig`
`template.default`        | schema da usare quando la pagina non ne specifica uno
`template.login`          | schema da usare quando i permessi non bastano
`template.menu.<m>`       | presenza del menu `<m>`; si dichiara a `null` e lo popola `buildMenu()`
`css.external`            | CSS caricati da un URL esterno
`css.internal`            | CSS presi dalla radice del deploy ( quelli del framework )
`css.template`            | CSS presi dalla cartella del template
`css.cached`              | copia locale degli esterni, **popolata dal framework**: non si scrive
`js.external`             | JavaScript caricati da un URL esterno
`js.internal`             | JavaScript presi dalla radice del deploy
`js.template`             | JavaScript presi dalla cartella del template
`js.cached`               | copia locale degli esterni, **popolata dal framework**: non si scrive

Nella linea nuova i CSS sono annidati **per media** ( `all`, `print`, `screen` ), i JavaScript
restano un elenco piatto. Un `etc/template.yaml` completo, quello di Aurora:

```yaml
template:
  type: "twig"
  menu:
    main: null
  default: "default.twig"
  login: "login.twig"

css:
  internal:
    all:
      - "_src/_css/_main.css"
  template:
    all:
      - "css/main.css"
    print:
      - "css/main.print.css"
    screen:
      - "css/main.screen.css"
  external:
    all:
      - "https://cdnjs.cloudflare.com/ajax/libs/font-awesome/6.5.1/css/all.min.css"

js:
  internal:
    - "_src/_js/_main.js"
  template:
    - "js/main.js"
  external:
    - "https://cdnjs.cloudflare.com/ajax/libs/jquery/3.6.0/jquery.min.js"
```

Accanto al file principale il framework carica, se c'e', `etc/template.add.yaml`
( `etc/template.add.conf` per l'INI ): serve ad aggiungere direttive senza toccare il file
standard. E vale la solita regola del custom: una copia in `tpl/<nome>/etc/template.yaml`
sostituisce quella standard.

Le risorse dichiarate in `css.external` e `js.external` **vengono copiate su filesystem** al primo
rendering e servite dalla copia locale: il meccanismo, i suoi percorsi e il modo di invalidarlo
stanno in [le strategie di caching](110-caching.html).

il file ext/main.twig
=====================
Fornisce l'impalcatura della pagina, che gli schemi estendono
( https://twig.symfony.com/doc/3.x/tags/extends.html ):

```html
<!DOCTYPE html>
<html lang="{{ localization.language.ietf }}">

    <head>
        {% include '_inc/_page.head.twig' %}
    </head>

    <body>

        {% include '_inc/_page.open.twig' %}

        <header>{% block header %}{% include 'inc/header.twig' %}{% endblock header %}</header>

        <nav>{% block nav %}{% include 'inc/navbar.twig' %}{% endblock nav %}</nav>

        <main>{% block main %}{% endblock main %}</main>

        <footer>{% block footer %}{% include 'inc/footer.twig' %}{% endblock footer %}</footer>

        {% include '_inc/_page.close.twig' %}

        {% block javascript %}{% endblock javascript %}

    </body>

</html>
```

I concetti che tengono in piedi il file sono quattro:

- ogni sezione principale della pagina e' un **blocco**, cosi' uno schema puo' sostituirne una sola;
- `_inc/_page.head.twig` costruisce il tag `head`;
- `_inc/_page.open.twig` e `_inc/_page.close.twig` fanno le operazioni standard di apertura e
  chiusura del contenuto — fra cui l'emissione degli script;
- il JavaScript di pagina sta in un blocco suo, subito prima della chiusura di `body`.

Il codice che si ripete ( header, footer, barra di navigazione ) va in `inc/`, non negli schemi:
cosi' non si ripete, e uno schema particolare puo' comunque includerne un altro.

il file default.twig
====================
Lo schema minimo estende la base e valorizza i soli blocchi che gli servono:

```html
{% import '_lib/_default.twig' as cms %}

{% extends "ext/main.twig" %}

{% block main %}
<div>
    {{ include( template_from_string( page.content[ localization.language.ietf ]|default('') ) | raw ) }}
</div>
{% endblock main %}
```

librerie e include standard
===========================
Il framework mette a disposizione di ogni template le proprie macro, in `_src/_twig/_lib/`. Il
**prefisso di import e' fisso**: si importa sempre con lo stesso nome, in tutti i template, perche'
gli esempi e le macro fra loro ci contano.

libreria                        | import                                              | contenuto
--------------------------------|-----------------------------------------------------|--------------------------------
`_src/_twig/_lib/_default.twig` | `{% import '_lib/_default.twig' as cms %}`          | rende i contenuti delle pagine
`_src/_twig/_lib/_form.twig`    | `{% import '_lib/_form.twig' as frm %}`             | elementi dei form
`_src/_twig/_lib/_navigation.twig` | `{% import '_lib/_navigation.twig' as nav %}`    | elementi di navigazione
`_src/_twig/_lib/_privacy.twig` | `{% import '_lib/_privacy.twig' as prv %}`          | informativa e consensi
`_src/_twig/_lib/_translation.twig` | `{% import '_lib/_translation.twig' as trn %}`  | traduzioni
`_src/_twig/_lib/_cms.twig`     | `{% import '_lib/_cms.twig' as cms %}`              | contenuti, linea nuova

Quello che le singole macro fanno, parametro per parametro, sta in
[le librerie dei template](154-librerie-template.html).

In `_src/_twig/_inc/` stanno invece i pezzi da **includere**, quasi tutti gia' inclusi dai tre
include di pagina; si dichiarano nel template solo quando servono fuori dal loro posto abituale:

file                              | incluso da            | cosa fa
----------------------------------|-----------------------|-------------------------------------
`_page.head.twig`                 | la base del template  | popola il tag `head`
`_page.open.twig`                 | la base del template  | apertura del contenuto
`_page.close.twig`                | la base del template  | chiusura del contenuto e script
`_ads.head.twig`                  | `_page.head.twig`     | tag di Google Ads
`_analytics.head.twig`            | `_page.head.twig`     | tag di Google Analytics
`_clarity.head.twig`              | `_page.head.twig`     | tag di Microsoft Clarity
`_csp.head.twig`                  | `_page.head.twig`     | Content Security Policy
`_facebook.head.twig`             | `_page.head.twig`     | pixel di Facebook
`_facebook.noscript.twig`         | `_page.open.twig`     | pixel di Facebook, versione noscript
`_gtm.head.twig`                  | `_page.head.twig`     | Google Tag Manager
`_gtm.noscript.twig`              | `_page.open.twig`     | Google Tag Manager, versione noscript
`_hotjar.head.twig`               | `_page.head.twig`     | HotJar
`_opengraph.head.twig`            | `_page.head.twig`     | meta tag OpenGraph
`_paypal.head.twig`               | `_page.head.twig`     | SDK di PayPal
`_cookie.overlay.twig`            | `_page.close.twig`    | form dei consensi sui cookie
`_recaptcha.close.twig`           | `_page.close.twig`    | reCAPTCHA
`_chartjs.script.twig`            | lo schema             | grafici ChartJs
`_emailable.close.twig`           | lo schema             | validazione degli indirizzi

Le integrazioni con i servizi di terzi sono trattate nei capitoli
[integrazioni con Google](501-integrazione-google.html),
[integrazioni con Facebook](502-integrazione-facebook.html) e
[integrazioni con ChartJs](500-integrazione-chartjs.html); i consensi e l'overlay dei cookie in
[privacy e cookie](160-privacy.html).

temi
====
Un template puo' avere piu' **temi**: un CSS aggiuntivo che ne cambia l'aspetto senza che si debba
creare un template nuovo. Il file viene cercato in ordine in `css/` e `css/themes/`, dando la
precedenza alla versione custom; un tema inesistente viene ignorato in silenzio.

Il tema si dichiara a livello di sito, in `metadati.theme`:

```json
"sites": {
  "1": {
    "__label__": "sito di esempio",
    "metadati": { "theme": "themes/green.css" }
  }
}
```

oppure a livello di pagina, accanto al percorso del template:

```json
"template": { "path": "_src/_tpl/_athena/", "theme": "themes/green.css" }
```

Fra i template standard solo `_athena` ha una cartella `css/themes/`.

favicon
=======
Le favicon del template stanno in `img/favicons/`, e in uno scenario multisito possono essere
differenziate per sito in `img/favicons/<idSito>/`. I nomi seguono lo schema degli strumenti che
le generano ( `android-icon-<n>x<n>.png`, `apple-icon-<n>x<n>.png`, `favicon-<n>x<n>.png`,
`ms-icon-<n>x<n>.png`, piu' `favicon.ico` ): il framework ricava ruolo e dimensione dal nome con
una espressione regolare, quindi un file fuori schema semplicemente non viene emesso.

> **attenzione** — l'ordine di ricerca e' l'opposto di quello che ci si aspetta: `_src/_api/_pages.php`
> prende **prima** le favicon generiche del template e guarda in `img/favicons/<idSito>/`
> **soltanto se le generiche mancano**. Un template con le favicon generiche presenti non usera'
> mai quelle del sito.

link interni
============
I template vedono l'array di configurazione, quindi un link interno si scrive prendendo l'URL da
`pages`, e non si aggiorna a mano quando il percorso della pagina cambia:

```html
<p><a href="{{ pages.4.url[ localization.language.ietf ] }}">esempio di link interno</a></p>
```

===================

sono raggiungibili tutte:

`_src/_tpl/_cassandra/`   | [Cassandra](tpl-cassandra.html)          | front-end
`_src/_tpl/_lydia/`       | [Lydia](tpl-lydia.html)                  | front-end

> **nota** — la versione di Bootstrap non e' del framework ma **di ogni template**, dichiarata nel
> suo `css.external`. Prima di toccare le classi di un file bisogna guardare che versione carica il
> template che lo usa: i nomi di Bootstrap 5 in Bootstrap 4 non esistono, e viceversa.
