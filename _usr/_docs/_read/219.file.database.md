#### le patch incrementali datate

I file numerati con una data e un'ora portano ai deploy già installati quello che è cambiato nei
file di base dopo l'installazione: ai deploy esistenti i file di base non arrivano più, arrivano
solo questi. Il task /_src/_api/_task/_mysql.patch.php li legge in ordine di nome, **salta un file
intero** se il livello ricavato dal nome è minore o uguale al patch level del database, esegue ogni
blocco quando incontra il marcatore `-- |` successivo e **si ferma al primo errore**. Per questo le
patch recenti sono scritte idempotenti ( CREATE TABLE IF NOT EXISTS, ADD COLUMN IF NOT EXISTS,
INSERT IGNORE ), chiudono con `-- | FINE FILE` e mettono dentro un PREPARE guardato da
information_schema le istruzioni che su uno schema vecchio fallirebbero; ciascuna spiega nel
commento di testa perché esiste e perché ha il numero che ha.

Dal 29/09/2026 il task, `_mysql.upgrade.sh` e `_database.rebuild.check.sh` leggono ed eseguono le patch con le
stesse funzioni `mysqlPatch…()` di /_src/_lib/_mysql.tools.php, che mandano ogni blocco al server con mysqli così
com'è: `PREPARE`, `EXECUTE` e `DEALLOCATE` girano ovunque, e un'istruzione che il server non conosce ferma
l'applicazione invece di essere registrata come fatta. Le regole sono nel capitolo 300, sezione «aggiornamento del
database e patch».

> **nota** — fino al 29/09/2026 il task eseguiva ogni blocco con mysqlQuery(), che sceglie cosa fare dalla prima
> parola della query e non conosceva `PREPARE`, `EXECUTE` e `DEALLOCATE`: per quelle tre non eseguiva niente, senza
> errore, e il task registrava il blocco come applicato. Sui deploy aggiornati dal task quelle operazioni le recupera
> `_202609300100.prepare.rieseguite.sql`; `_202609301100.chiavi.esterne.sql` mette i suoi controlli dentro una
> procedura per la stessa ragione.

> **attenzione** — rinumerare o correggere una patch già applicata da qualche parte richiede un
> nome con un livello più alto: con lo stesso nome il task la considera già letta e la salta.

#### migrazioni, conversioni ed elaborazioni di dati

Una patch che non si limita a cambiare lo schema ma tocca i dati ricade in uno di tre casi, e ciascuno ha la sua
forma:

- **conversioni che stanno in SQL e sono brevi** ( copiare righe da una tabella all'altra, tradurre un codice in un
  id ): stanno nella patch. I dati si copiano **nella stessa patch** prima di qualunque `DROP`, e la patch si può
  rilanciare senza danni. La rete è il dump che `_mysql.upgrade.sh` fa prima di applicare. Modello:
  `_202610011600.consensi.anagrafica.sql`;
- **elaborazioni lunghe o che vogliono PHP** ( ricalcoli su tabelle grandi, file, librerie ): non stanno nella patch,
  che è una query sola per blocco. La patch aggiunge il nuovo **senza togliere il vecchio**, un job fa la conversione
  a iterazioni, e una patch **successiva** toglie il vecchio quando il job ha finito; nel frattempo il codice deve
  funzionare con tutti e due gli schemi;
- **conversioni che chiedono una decisione** ( dati ambigui, codice di progetto che si appoggia alla forma vecchia ):
  la patch fa la parte sicura, **non indovina**, e scrive quello che non ha fatto in una variabile di note che il
  blocco finale restituisce. Prima di applicarla a un deploy si guarda il deploy: `_mysql.upgrade.sh --fino
  <livello>` smaltisce l'arretrato fermandosi prima. Modello: `_202609301900.id.numerici.sql`.

#### le patch su MySQL

Le patch si scrivono per MariaDB, e si continuano a scrivere così. Su MySQL ( la PROD di gimbe è su Azure, MySQL 8.4 )
le traduce `mysqlPatchTranslate()` di /_src/_lib/_mysql.tools.php, che `mysqlPatchApply()` chiama per ogni blocco:
risolve leggendo lo schema gli `IF [NOT] EXISTS` dell'ALTER che MySQL non conosce, anche in stringa e nel corpo delle
procedure, rende `CREATE OR REPLACE PROCEDURE` un `DROP` più `CREATE`, sistema le collation dei confronti con
information_schema e i tipi delle chiavi esterne fra int e bigint, e tiene conto della chiave primaria invisibile
( `my_row_id` ) che Azure aggiunge alle tabelle create senza. In `__patch__` resta il testo originale, con la nota di
cosa è stato tradotto; una forma che non sa tradurre ferma l'applicazione come un errore.

Una patch nuova con una forma che la traduzione non conosce si prova prima sul banco MySQL 8.4 di web03
( `/opt/mysql84/`, `ricarica.sh <dump> <database> <document root>` ), che fa girare la catena intera su un dump di un
deploy vecchio.
