# il javascript del framework

Il framework porta con sé una libreria JavaScript propria: una base sempre caricata e tredici
librerie che si accendono una per volta, più il JavaScript che ogni tema si porta dietro. Questo
capitolo dice dove vive, come viene caricato, che cosa offre e — soprattutto — **come ci si innesta
il JavaScript di un progetto**, che è il punto in cui il JS si comporta diversamente da tutto il
resto del framework.

Il capitolo affianco, `155.template.md`, descrive il file `etc/template.yaml` in cui il JavaScript
si dichiara; la reference file per file sta in `217.file.risorse.md`.

> **nota** — il framework è a metà del guado fra Bootstrap 4 e Bootstrap 5, e la versione la
> dichiara **ogni template**, non il framework. Prima di toccare una classe o un attributo
> `data-bs-*` si guarda il `etc/template.yaml` del tema su cui si sta lavorando.

dove vive il javascript
=======================

```
_src/_js/
├── _main.js                    la libreria di base, caricata praticamente ovunque
└── _lib/
    ├── _rest.js                le chiamate alle API
    ├── _form.js                la validazione dei form lato client
    ├── _selectbox.js           la tendina intelligente
    ├── _uploader.js            l'upload asincrono
    ├── _crosshow.js            lo scambio di pannelli nei form a linguette
    ├── _paypal.js              il checkout PayPal
    ├── _codemirror.js          l'editor di codice
    ├── _ckeditor.js            l'editor di testo ricco
    └── …                       gli altri editor
```

Vale la **convenzione dell'underscore** come per il PHP: `_src/_js/` è standard e non si modifica.
Dentro un tema l'underscore invece sparisce, perché la cartella del tema è già sua:

    _src/_tpl/_athena/src/js/main.js       il JavaScript del CMS
    _src/_tpl/_minerva/src/js/main.js      il JavaScript di un sito pubblico

I **moduli non hanno una cartella `_js/`**: un modulo che si porta del JavaScript lo mette nel
proprio albero di template — `_mod/<modulo>/_src/_templates/_athena/src/js/<nome>.js` — e lo
dichiara nella definizione della pagina che ne ha bisogno, non nel tema.

Le librerie di terzi — jQuery, Bootstrap, Chart.js, CodeMirror — **non stanno qui**: si dichiarano
per URL nel `etc/template.yaml` del tema e il framework se le copia in locale da sé (vedi più
avanti). L'unica eccezione impacchettata nel framework sono i plugin di CKEditor, in
`_src/_js/_lib/_ext/`.

come viene caricato
===================

I tag `<script>` li emette **un punto solo**, alla chiusura del `<body>`:
`_src/_twig/_inc/_page.close.twig` ( il gemello della generazione vecchia è
`_src/_html/_inc/_page.close.html` ). Nel `<head>` non c'è nessuno `<script src>`: ci stanno solo i
tracker, che sono codice in linea.

i quattro insiemi, in ordine
----------------------------

Prima di tutto il framework dichiara **l'unica variabile che passa dal server al JavaScript**:

```html
<script>
    var siteRoot = '/';
</script>
```

`siteRoot` è la radice del sito, ed è quella che si antepone a ogni indirizzo che il JavaScript
chiama. Poi vengono i quattro insiemi, sempre in questo ordine:

| insieme | da dove viene | come si dichiara |
|---|---|---|
| `js.cached` | copia locale di una risorsa esterna | non si dichiara: ci finisce da sola |
| `js.external` | una URL remota | `js.external` del tema |
| `js.internal` | `_src/_js/` | `js.internal` del tema o della pagina |
| `js.template` | la cartella del tema | `js.template` del tema |

Dentro ciascun insieme vale l'ordine di dichiarazione, e **l'ordine conta**. Il tema del CMS lo
mostra bene ( `_src/_tpl/_athena/etc/template.yaml` ):

```yaml
js:
  internal:
    - "_src/_js/_lib/_rest.js"        # per primo: definisce le funzioni che usano tutti gli altri
    - "_src/_js/_lib/_selectbox.js"
    - "_src/_js/_lib/_uploader.js"
    - "_src/_js/_lib/_crosshow.js"
    - "_src/_js/_lib/_form.js"
    - "_src/_js/_main.js"
  template:
    - "src/js/main.js"                # per ultimo, dopo tutto il resto
```

Tutti i tag vengono emessi con **`defer`**: l'ordine di esecuzione resta quello dei tag, ma girano
tutti dopo che il documento è stato letto. Una funzione dichiarata in uno di questi file è quindi
disponibile a un `onclick` scritto nel markup, ma non a uno `<script>` in linea che venga eseguito
prima.

> **attenzione** — i JavaScript interni escono **senza query di versione**. Dopo aver modificato un
> file di `_src/_js/` i browser già aperti continuano a servire la copia vecchia finché non fanno un
> ricaricamento forzato. È la prima cosa da escludere quando una modifica «non si vede».

la copia locale delle risorse esterne
-------------------------------------

Le URL dichiarate in `js.external` vengono scaricate al primo rendering della pagina e salvate in
`var/cache/js/<host>/<path>`; da lì in avanti l'indirizzo passa in `js.cached` e la risorsa viene
servita dal sito, non dal CDN.

Due cose da sapere: **non c'è né scadenza né aggiornamento automatico** — per rinfrescare una
risorsa si cancella il file a mano, oppure si dichiara una URL che porta la versione nel nome
( `bootstrap@5.3.2/...` ) — e le URL che contengono marcatori Twig non vengono copiate, perché
devono essere risolte a ogni richiesta: restano esterne e vengono renderizzate al volo.

Due indirizzi sono esclusi apposta dalla copia locale: CKEditor, che calcola il percorso dei propri
plugin a partire dal tag che lo ha caricato, e reCAPTCHA, che serve un avviatore minuscolo con
dentro una versione che Google cambia per conto suo.

il javascript di un progetto
============================

> **attenzione** — questa è la sezione da leggere per prima, perché è il punto in cui il JavaScript
> **non** si comporta come il resto del framework.

Per i CSS esiste un quinto insieme, `css.custom`: il framework cerca da sé la controparte senza
underscore di ogni foglio di stile del tema e, se la trova, la carica. **Per il JavaScript non
esiste niente di equivalente**: non c'è nessun `js.custom`, e nessuno va a cercare la controparte
custom di un file `_src/_js/_*.js`.

La conseguenza pratica è secca: **un file messo in `src/js/` e non dichiarato da nessuna parte non
viene caricato mai**, e non lo dice nessuno — nessun errore, nessun avviso, semplicemente la pagina
non lo ha.

I modi per dichiararlo sono tre.

`etc/template.add.yaml` — la strada consigliata
-----------------------------------------------

Il framework cerca, accanto al `etc/template.yaml` del tema, anche un `etc/template.add.yaml`, e lo
cerca **sia fra i file standard sia fra quelli custom**. Quello che ci sta dentro si **aggiunge** a
quanto dichiara il tema, senza sovrascriverlo:

```yaml
# src/tpl/athena/etc/template.add.yaml
js:
  internal:
    - "src/js/progetto.js"
```

È la strada da preferire perché è additiva: il giorno che il tema standard cambia i propri
JavaScript, il progetto se li ritrova senza dover riallineare niente.

la chiave `js` nella definizione della pagina
---------------------------------------------

Quando un JavaScript serve a **una pagina sola** — un editor, una mappa, un grafico — si dichiara
nella definizione della pagina, ed è così che fanno i moduli:

```php
$p['mail.form'] = array(
    // …
    'js' => array( 'internal' => array( '_src/_js/_lib/_codemirror.js' ) ),
);
```

Il percorso è **relativo alla radice del sito**, e viene solo preceduto da `siteRoot`: può quindi
puntare ovunque, anche dentro `_mod/` o dentro `src/`.

> **nota** — le definizioni delle pagine stanno in cache. Dopo aver aggiunto la chiave `js` a una
> pagina, la modifica non si vede finché non si passa da `/task/memcache.clean`.

sostituire il `etc/template.yaml` del tema
------------------------------------------

Se esiste la controparte custom del file di configurazione del tema, il framework usa **quella al
posto** di quella standard. È la via più potente e la meno raccomandabile: si prende in carico
l'intero elenco delle risorse del tema, comprese quelle che cambieranno in futuro.

le librerie del framework
=========================

`_main.js` — la base
--------------------

È il file sempre presente, ed è diviso in quattro gruppi di funzioni più il blocco che si esegue a
documento pronto.

| funzione | cosa fa |
|---|---|
| `strClean( st )` | toglie gli accenti da una stringa |
| `ciEquals( a, b )` | confronta due stringhe ignorando maiuscole e minuscole |
| `basename( path )` | il nome del file da un percorso |
| `getUrlParam( paramName )` | legge un parametro dalla querystring |
| `addDays( date, days, working = true )` | somma giorni a una data, **di default solo lavorativi** |
| `formatDate( date )` | formatta una data come `AAAA-MM-GG` |
| `glisTimestampToIso( v )` | normalizza una data e ora scritta all'italiana in formato ISO |
| `glisNormalizeTimestampFields( form )` | applica la precedente a tutti i campi `timestamp_*` di un form |
| `checkAndSubmit( form )` | normalizza le date, poi valida e invia il form |
| `checkAndDo( form, action )` | come sopra, ma al posto dell'invio esegue una funzione |

Le due funzioni sulle date esistono per un motivo preciso: quando un campo `datetime-local` degrada
a campo di testo, quello che l'utente scrive arriva al server nella forma italiana e verrebbe letto
all'americana, con il giorno e il mese scambiati.

Il blocco eseguito a documento pronto è dove vivono quasi tutti gli agganci al markup: l'avviso dei
cookie, il fuoco automatico su un campo, le finestre modali, i pannelli a scomparsa, il ritorno in
cima alla pagina, il trascinamento, la barra di navigazione e il megamenu. Ci sono anche le due
righe che **accendono i tooltip di Bootstrap 5**: il solo attributo `data-bs-toggle="tooltip"` non
basta, e senza `_main.js` caricato i tooltip non compaiono.

Una finezza da conoscere, perché prima o poi si incontra: una casella di spunta collegata a un campo
nascosto ci scrive `'1'` quando è spuntata e **stringa vuota** quando non lo è, non zero — uno zero
manderebbe fuori strada i filtri degli elenchi.

`_rest.js` — le chiamate alle API
---------------------------------

È la libreria da caricare per prima, perché le sue funzioni le usano tutte le altre.

| funzione | cosa fa |
|---|---|
| `getws( url, params, callback, fail )` | una GET verso un endpoint, con la risposta in JSON |
| `postws( url, params, callback )` | la stessa cosa in POST — **non ha** il parametro `fail` |
| `$.fn.metroWs( ws, callback, method, data )` | chiama un endpoint da un riquadro dell'interfaccia, sostituendo l'icona con un indicatore di attesa e poi con un segno di spunta |
| `$.fn.metroLoopWs( ws, callback, icon, el, count )` | come sopra ma ripete la chiamata finché il lavoro non è finito: è il sondaggio dei lavori lunghi |

`getws()` è la funzione più usata di tutto il framework: è il ponte fra il JavaScript e le API
descritte più sotto.

`_form.js` — la validazione lato client
---------------------------------------

Quattro funzioni di controllo — `checkEmail()`, `checkTelefono()`, `checkRequired()` e
`checkForm()`, che prende **l'id** del form e cicla sui suoi campi — e soprattutto i tre attributi
che esprimono vincoli **fra campi diversi**, descritti nella sezione dedicata più avanti.

le altre librerie
-----------------

| libreria | cosa fa | come si accende |
|---|---|---|
| `_selectbox.js` | trasforma un campo nascosto in una tendina che interroga le API mentre si scrive | classe `selectbox` |
| `_uploader.js` | carica un file a blocchi verso `api/upload` e scrive il percorso risultante in un campo | classe `ajax-uploader` |
| `_crosshow.js` | `crossFade( show, hide )` e `crossShow( show, hide, obj )`, lo scambio di pannelli nei form a linguette | chiamate da `onclick` nel markup |
| `_paypal.js` | i pulsanti PayPal e i campi carta con verifica 3-D Secure | si carica sulla pagina del pagamento |
| `_codemirror.js` | l'editor di codice, con un modo Twig costruito apposta | classe `CodeMirror` su una `textarea` |
| `_ckeditor.js` | l'editor di testo ricco, con l'altezza nell'attributo `height` | classe `ckEditor` |

> **attenzione** — in `_src/_js/_lib/` ci sono anche `_tinyMCE.js`, `_toastEditor.js`,
> `_bootstrap-wysiwyg.js` e `_CLEditor.js`: sono editor alternativi che **nessun tema e nessuna
> pagina dichiarano**. Sono rimasti lì da scelte passate e non vanno considerati disponibili senza
> prima averli provati.

quello che il javascript legge nel markup
=========================================

Il framework governa il proprio JavaScript **dal markup**: attributi e classi sugli elementi, non
chiamate esplicite. Chi scrive i template di un progetto lavora quasi sempre di qui.

> **nota** — il framework usa in gran parte **attributi nudi** ( `also-required`, `uploader-field`,
> `job-id` ) e non `data-*`. È una convenzione storica, non una svista: si scrivono come li scrive
> il resto del framework.

i tre vincoli fra campi
-----------------------

Sono i più utili, e valgono sui tag `<input>`. Il valore è sempre un elenco di **id** separati da
virgola.

| attributo | significato |
|---|---|
| `also-required` | se il campo è valorizzato, i campi elencati diventano obbligatori ( e da disabilitati tornano attivi ); svuotandolo tornano facoltativi e disabilitati |
| `required-equals` | i campi elencati devono avere tutti lo stesso valore, altrimenti il form segnala che «i campi non corrispondono» |
| `required-alternative` | i campi del gruppo sono obbligatori **in alternativa**: finché sono tutti vuoti restano tutti obbligatori, appena uno viene compilato il vincolo cade su tutto il gruppo |

`required-alternative` si dichiara su **ogni** campo del gruppo, elencando gli id degli altri, e i
campi partono obbligatori nel markup — così il vincolo regge anche a JavaScript spento, degradando
in «obbligatori tutti» e non in «obbligatorio nessuno»:

```html
<input type="number" id="numero_colli"  name="…[numero_colli]"  required required-alternative="numero_pallet">
<input type="number" id="numero_pallet" name="…[numero_pallet]" required required-alternative="numero_colli">
```

Tre cose da ricordare:

- **servono gli `id`**: tutti e tre risolvono i campi per id, il `name` non basta;
- **sono solo lato client.** Nessuno dei tre ha una controparte PHP: il backend deve comunque
  accettare o rifiutare esplicitamente una richiesta a cui manchino quei campi, perché un invio
  costruito a mano li scavalca;
- `required-alternative` ascolta anche il cambio di valore e l'incolla, e non il solo tasto
  premuto, perché su un campo numerico il valore cambia anche con le frecce del browser, incollando
  o con un lettore di codici a barre.

gli altri attributi
-------------------

| attributo | letto da | significato |
|---|---|---|
| `populate-api` | `_selectbox.js` | l'entità da interrogare; se è vuoto la tendina è statica |
| `placeholder-api` | `_selectbox.js` | l'entità da cui risolvere l'etichetta del valore corrente |
| `min-filter` | `_selectbox.js` | quanti caratteri servono prima di interrogare le API |
| `restrict-<campo>` | `_selectbox.js` | un vincolo in più sulla ricerca, nella forma `<operatore>:<valore>` |
| `uploader-folder` | `_uploader.js` | la cartella di destinazione del file |
| `uploader-field` | `_uploader.js` | l'id del campo in cui scrivere il percorso del file caricato |
| `job-id` | il tema del CMS | il lavoro di cui seguire l'avanzamento |
| `max` | il tema del CMS | quante righe si possono duplicare al massimo |
| `default` | il tema del CMS | il valore da ripristinare in una riga duplicata |
| `height` | `_ckeditor.js` | l'altezza dell'editor |
| `toggle` | `_main.js` | l'elemento da far comparire e scomparire |
| `img-hover` | `_main.js` | l'immagine alternativa da mostrare al passaggio del puntatore |
| `popup-delay` | `_main.js` | dopo quanti secondi aprire la finestra |
| `popup-scroll` | `_main.js` | a che percentuale di scorrimento aprirla |

le classi che accendono qualcosa
--------------------------------

Si accendono da sole, senza scrivere una riga: `selectbox`, `ajax-uploader`, `ckEditor`,
`CodeMirror` per i campi; `focus-on-load`, `toggler`, `draggable-item`, `back-to-top`, `popup-open`,
`popup-delay`, `popup-scroll` per i comportamenti di pagina.

il dialogo con le API
=====================

Il JavaScript parla col server per mezzo di `getws()` e `postws()`, verso quattro famiglie di
indirizzi:

| indirizzo | a cosa serve |
|---|---|
| `/api/<entità>[/<id>]` | leggere, creare, modificare e cancellare le righe di un'entità |
| `/status/<nome>` | chiedere lo stato di qualcosa senza modificarlo |
| `/task/<nome>` | far eseguire un'operazione |
| `/job/<id>` | far avanzare un lavoro lungo di una iterazione |

Il contratto delle API REST è descritto per esteso nel capitolo dedicato e nel docblock in testa a
`_src/_api/_rest.php`. La chiamata più istruttiva da leggere è quella che la tendina intelligente
costruisce per popolarsi:

```
/api/<entità>?__info__[<entità>][__search__]=<filtro>
             &__info__[<entità>][__fields__][]=id
             &__info__[<entità>][__fields__][]=__label__
             &__info__[<entità>][__restrict__][<campo>][<operatore>]=<valore>
```

`__search__` è il testo digitato, `__fields__` dice quali colonne servono — l'id e l'etichetta, non
tutta la riga — e `__restrict__` porta i vincoli dichiarati con gli attributi `restrict-*`. Il testo
digitato viene sempre codificato: una `&` o un `#` scritti nella casella di ricerca troncherebbero
altrimenti la richiesta.

L'upload segue una strada sua: il file viaggia a blocchi verso `api/upload`, con nome, tipo,
dimensione, numero del blocco e cartella di destinazione **negli header** della richiesta. La
risposta porta il percorso del file salvato, che la libreria scrive nel campo indicato da
`uploader-field`.

il javascript del CMS
=====================

Il tema `_src/_tpl/_athena` si porta il JavaScript del gestionale, in `src/js/main.js`. È l'ultimo
file caricato, e contiene i comportamenti che rendono il CMS quello che è.

la guardia sui form modificati
------------------------------

Un form con la classe `warning-if-changed` — che le macro dei form mettono d'ufficio su quello
principale — viene fotografato all'apertura e riconfrontato quando si prova ad abbandonare la
pagina; se qualcosa è cambiato, il browser chiede conferma.

Due dettagli ne spiegano la forma: gli editor di testo ricco vanno **interrogati a parte**, perché
riversano quello che si è scritto nel campo vero solo al momento dell'invio; e dal confronto sono
esclusi i discendenti dei filtri, dei comandi e della tabella di un elenco, perché cercare e
impaginare è navigare, non modificare.

la duplicazione dei sotto-form
------------------------------

`duplicate( f )` è il cuore dei form di modifica: clona la prima riga del contenitore indicato,
rinumera gli identificativi, rispetta il limite dichiarato nell'attributo `max` e rimette in
funzione le tendine e i caricatori di file della riga nuova. Un insieme di classi governa cosa
succede a ciascun campo nella copia — `remove-on-duplicate`, `show-on-duplicate`,
`protect-value-on-duplicate`, `current-date-on-duplicate`, `default-value-on-duplicate` e le altre.

> **nota** — se una pagina ha bisogno di fare qualcosa di suo a ogni duplicazione, le basta
> dichiarare una funzione `onDuplicate( base )`: il framework la chiama passandole la riga appena
> creata. **È l'unico aggancio con un nome convenzionale di tutto il JavaScript del framework**, ed
> è il punto giusto in cui innestare il JavaScript di un progetto.

la barra di avanzamento dei lavori
----------------------------------

Un elemento con la classe `foreground-job-slider` e l'attributo `job-id` fa partire un sondaggio:
ogni tre secondi il JavaScript chiama `/job/<id>`, aggiorna la barra e, quando il lavoro è finito,
la toglie e scrive al suo posto il riepilogo.

Due cose vanno sapute da chi **scrive** un lavoro, e sono spiegate per esteso in
`121.esecuzione.job.md`:

- il riepilogo di fine barra si legge da `result`, e per arrivarci va scritto nel `workspace` del
  lavoro: è l'unica cosa che il motore risalva fra un'iterazione e l'altra;
- il sondaggio **non si ferma** quando l'ultima riga è stata lavorata, ma quando il lavoro è
  davvero chiuso. La chiusura — e con essa il riepilogo — avviene nell'iterazione successiva a
  quella dell'ultima riga. C'è comunque un'uscita di sicurezza: a righe finite si aspetta la
  chiusura al massimo un minuto.

gli altri comportamenti
-----------------------

Un controllo periodico chiede a `/status/session` quanto manca alla scadenza della sessione e
avvisa prima che scada; il carrello e i segnalibri si ridisegnano da soli dopo una chiamata alle
API; l'albero delle anagrafiche apre e chiude i rami.

il javascript scritto dal CMS
=============================

C'è un secondo modo di mettere JavaScript in una pagina, e non passa dal codice: **si scrive dal
gestionale**. La tabella delle pagine ha una colonna `javascript`, e il CMS della generazione nuova
ha una scheda apposta per compilarla, con un editor di codice completo di numeri di riga e chiusura
automatica delle parentesi. Nel CMS della generazione vecchia quella scheda non c'è, e chi deve
mettere del JavaScript in una pagina lo infila nel sorgente del contenuto.

Il campo passa per il motore dei template prima di finire nella pagina: **dentro ci si possono
usare le variabili Twig della pagina**, esattamente come in uno schema.

Il contenuto di quel campo viene reso nel blocco `javascript` del layout, che lo prende dallo
snippet condiviso `_src/_twig/_inc/_page.javascript.twig`: se il campo è vuoto non esce nessun tag,
se è valorizzato esce uno `<script>` con dentro il risultato. Uno schema che abbia bisogno di altro
nel blocco `javascript` lo sovrascrive come qualunque altro blocco — è quello che fa, per esempio,
la scheda del CMS che monta l'editor di codice.

> **nota** — fino al 21/09/2026 quel blocco era **vuoto in tutti i temi tranne uno**, e il
> JavaScript scritto dalla scheda si salvava senza comparire mai. Oggi lo rendono tutti i temi della
> generazione nuova; restano fuori di proposito le pagine di accesso, dove non ha senso eseguire
> codice preso dalla base dati.

> **attenzione** — resta scoperto un caso: un deploy che monti il **CMS della generazione nuova**
> insieme ai **temi della generazione vecchia** ( `_src/_templates/` ). Lì il campo viene letto dalla
> base dati ma il tema non lo rende, perché il blocco `javascript` di quei temi non è stato toccato.
> Chi si trova in quella combinazione deve portarsi il rendering nel proprio schema.

cose che il framework non ha
============================

Vale la pena dirle, perché sono le prime che chi arriva da un altro ambiente dà per scontate:

- **nessun compilatore e nessun pacchettizzatore**: niente `package.json`, niente moduli, nessun
  passaggio di build. I file si scrivono e si dichiarano, punto;
- **nessuno spazio di nomi**: le funzioni stanno tutte nell'oggetto globale, e l'unica cosa che
  arriva dal server è `siteRoot`;
- **nessun evento proprio**: il framework non emette eventi a cui agganciarsi. Gli unici punti di
  innesto sono `onDuplicate()`, le funzioni di richiamo dei riquadri e il JavaScript dichiarabile
  campo per campo dalle macro dei form;
- **nessuna versione sulle risorse interne**, con la conseguenza già detta sul ricaricamento
  forzato.
